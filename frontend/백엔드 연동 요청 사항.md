# 백엔드 연동 요청 사항

**이 문서는 임시 서버 설명서가 아니다.**
`API 기본 명세서(요약)` / `실시간 소켓 이벤트 명세(요약)`의 **v1.0 계약과 현재 프론트 구현이 어긋난 지점**만 모은 목록이다.
임시 서버(`local-server/`)는 그 어긋난 쪽에 맞춰 구현돼 있을 뿐이고, 실제 백엔드가 명세대로만 만들면 화면이 깨진다.

어긋난 방향은 두 가지다.

| 방향 | 항목 |
|---|---|
| **명세에 없는데 화면이 필요로 함** (추가 요청) | ① `WinnerResult.rounds` · ④ `game:result.roundElapsedMs` |
| **명세에 있는데 구현이 안 따름** (명세 수정 요청) | ② `roulette.pick`/`ladder.start` · ③ `game:progress.optionVotes` |
| **두 명세서가 서로 다름** (문서 동기화) | ⑤ 소켓 명세서 4곳 |

②③은 **명세를 고쳐야 하는 건**이라 백엔드 혼자 결정할 수 없다. 기획·API 담당과 함께 봐야 한다.

**두 명세서가 충돌하면 `API 기본 명세서 요약.md`의 v1.0 정정이 이긴다** — 기존 결정이다.
소켓 명세서(`실시간 소켓 이벤트 명세 요약.md`)는 7/30 수정본이라 일부가 뒤처져 있다. ⑤에 정리했다.

> 왜 중요한가 — 네 건 중 두 건(③④)은 **없어도 에러가 안 난다.** 화면이 조용히 틀린 값을 보여줄 뿐이라
> 통합 테스트에서 놓치기 쉽다. 명세 확정 단계에서 못 박는 편이 훨씬 싸다.

**우선순위:** ① `rounds` → ② `roulette.pick`/`ladder.start` 삭제 → ③ `optionVotes` → ④ `elapsedMs`

## 0. 연결 지점은 이미 준비돼 있다

프론트가 서버 주소를 정하는 곳은 **한 파일뿐**이다.

```ts
// src/api/endpoint.ts
const OVERRIDE = import.meta.env.VITE_SERVER_URL as string | undefined
export const SERVER_URL = OVERRIDE ?? `${location.protocol}//${location.hostname}:4000`
export const API_BASE = `${SERVER_URL}/api`
```

실제 백엔드가 나오면 `.env`에 한 줄만 넣으면 된다. 코드 수정 없음.

```
VITE_SERVER_URL=https://api.example.com
```

REST 경로(`/api/...`)와 소켓 이벤트 이름은 v1.0 명세 그대로다. 계약의 정본은 문서가 아니라
**`src/protocol/types.ts`** 다 — 프론트가 실제로 읽는 타입이 거기 있다.

## ① `WinnerResult.rounds` — 눈치게임 라운드 기록 (가장 무겁다)

> **명세 상태:** `rounds`라는 낱말이 두 명세서 어디에도 없다. 순수 추가 요청이다.
> 현재 명세의 `game:result`는 `roundId, variant, result, resultScreenAt` 네 개뿐이다.

### 초등학생 설명

눈치게임은 여러 판을 한다. 1판에서 두 명이 동시에 눌러서 떨어지고, 2판에서 또 누가 떨어지고…
이렇게 계속하다 마지막 한 명이 남는다.

지금 서버는 **"최종 우승자는 지호입니다"** 한 줄만 알려준다.
그런데 결과 화면은 **"1판: 서연·유진 동시 입력 탈락 / 2판: 민준 시간 초과 탈락 / …"**
이렇게 판마다 누가 어떻게 떨어졌는지 표로 펼쳐서 보여준다.

즉 서버가 **경기 일기장**을 써서 넘겨줘야 한다. 우승자 이름만으로는 중계를 할 수 없다.

### 계약

`WinnerResult`에 선택 필드 `rounds`를 추가했다.

```ts
// src/protocol/types.ts
export interface WinnerResult {
  variant: 'winner'
  topic: string
  winner: RoundMember
  detail?: string[]              // 기존 계약. 그대로 둔다
  rounds?: NunchiRoundLog[]      // ← 추가. 눈치게임에서만 채운다
}

export interface NunchiRoundLog {
  subRound: number
  entered: number                                  // 이 판을 시작한 인원
  // 혼자 눌러 살아남은 사람들, 누른 순서대로. elapsedMs는 이 판 시작부터의 경과(ms)
  passed: { memberId: MemberId; nickname: string; avatarId: string; elapsedMs: number }[]
  // 이 판에서 탈락한 사람들. elapsedMs가 null이면 제한시간까지 아예 안 누른 것
  eliminated: { memberId: MemberId; nickname: string; avatarId: string; elapsedMs: number | null }[]
  reason: 'SIMULTANEOUS' | 'TIMEOUT' | 'LAST_ONE' | 'ALL_PRESSED' | 'DISCONNECTED'
  gapMs?: number                                   // SIMULTANEOUS일 때 가장 가까웠던 두 입력의 간격(ms)
}
```

`reason` 값의 뜻:

| 값 | 언제 |
|---|---|
| `SIMULTANEOUS` | 두 명 이상이 겹쳐 눌러서 같이 탈락 |
| `TIMEOUT` | 제한시간까지 안 누름 |
| `LAST_ONE` | 마지막 한 명만 남아서 판이 끝남 |
| `ALL_PRESSED` | 남은 전원이 눌러버림 |
| `DISCONNECTED` | 연결이 끊겨서 탈락 |

### 안 주면

`ResultScreen`이 눈치 전용 결과 화면을 포기하고 일반 당첨자 카드(Figma `542:1119`)로 되돌아간다.
**화면 자체가 바뀌므로 네 건 중에서는 그나마 눈에 띈다.**

### 백엔드 부담

넷 중 유일하게 **자료구조를 바꿔야 할 수 있다.**
판정만 하고 버리는 구현이면 라운드별 이력을 보관하도록 고쳐야 한다.
`detail`(문장 배열)은 기존 계약대로 남아 있으니 **"detail 채웠으니 됐다"고 넘어가기 쉽다** — 이게 함정이다.

### 확인 방법

눈치게임 한 판을 끝까지 돌린 뒤 `game:result`의 `result.rounds`가 배열로 오는지,
배열 길이가 실제 진행한 판 수와 같은지 본다.

## ② `roulette.pick` / `ladder.start` — 명세에서 지워야 한다

> **명세 상태:** 둘 다 명세에 **정식으로 살아 있다.**
> ```
> API 기본 명세서 요약.md:115 | 룰렛   | `roulette.pick` | `{ }` | host 1회 |
> API 기본 명세서 요약.md:116 | 사다리 | `ladder.start`  | `{ }` | host 1회 (레인 선택 없음, snapshot 순서 자동 배치) |
> ```
> 명세대로 구현하면 **오지 않는 신호를 기다리게 된다.** 명세를 고쳐야 하는 건이다.
>
> 참고로 두 명세서가 서로 다르다 — `실시간 소켓 이벤트 명세 요약.md:32`는 아직 `ladder.pick(전원, laneIndex)`로 적혀 있고,
> `API 기본 명세서 요약.md:18`이 "레인 선택 제거, host의 `ladder.start`만 사용"으로 정정했다.
> **v1.0 정정이 우선**이라는 게 기존 결정이다. 이번에 지울 때 두 문서를 같이 맞춰야 한다.

### 초등학생 설명

예전에는 룰렛에 **"돌리기" 버튼**이, 사다리에 **"사다리 타기" 버튼**이 있었다.
방장이 눌러야 게임이 시작됐다.

그런데 **버튼을 없앴다.** 지금은 게임 설명이 5초 뜨고 나면 아무도 안 눌러도 저절로 시작한다.
그래서 프론트는 이 두 신호를 **영영 안 보낸다.**

설명서에는 아직 "이 버튼이 눌리면 신호가 옵니다"라고 쓰여 있다.
백엔드가 그 말을 믿고 **신호를 기다리면, 오지 않는 신호를 영원히 기다리게 된다.**

### 계약

```ts
// src/protocol/types.ts — 이 두 줄은 지워야 한다
export type GameActionPayload =
  | { roundId: RoundId; type: 'roulette.pick'; payload: Record<string, never> }   // ← 죽은 타입
  | { roundId: RoundId; type: 'ladder.start'; payload: Record<string, never> }    // ← 죽은 타입
  | { roundId: RoundId; type: 'king.opinion'; payload: { text: string } }
  | { roundId: RoundId; type: 'king.vote'; payload: { optionIds: OptionId[] } }
  | { roundId: RoundId; type: 'timer.start'; payload: Record<string, never> }
  | { roundId: RoundId; type: 'timer.stop'; payload: Record<string, never> }
  | { roundId: RoundId; type: 'snipe.vote'; payload: { targetMemberIds: MemberId[] } }
  | { roundId: RoundId; type: 'nunchi.up'; payload: Record<string, never> }
  | { roundId: RoundId; type: 'nunchi.invalid_decision'; payload: { decision: 'RESTART' | 'ABORT' } }
```

**대신 이렇게 동작해야 한다:** 룰렛과 사다리는 가이드가 끝나는 순간 서버가 스스로 판정을 끝내고
`game:result`를 보낸다. 참가자 입력이 아예 없는 게임이다.

임시 서버는 이 액션을 받으면 `INVALID_ACTION`을 돌려준다.
프론트 타입에 두 줄이 남아 있는 이유는 **명세서 계약을 그대로 옮긴 것이라 임의로 지우지 않았기** 때문이다.
실제 계약을 고칠 때 프론트 타입에서도 같이 지운다.

### 안 지우면

룰렛·사다리 라운드가 시작만 되고 끝나지 않을 수 있다. 넷 중 **유일하게 눈에 띄게 터지는** 건이다.

## ③ `GameProgress.optionVotes` — 킹메이커 실시간 득표

> **명세 상태: 빠진 게 아니라 명세가 명시적으로 금지하고 있다.** 넷 중 유일하게 정면 충돌이다.
> ```
> API 기본 명세서 요약.md:145 | `game:progress` | 참가자별 COMPLETE/WAITING만(득표·내용 없음) | 전원 |
> API 기본 명세서 요약.md:189 - `game:progress`는 완료/대기 상태만 (득표·내용 비공개)
> 실시간 소켓 이벤트 명세 요약.md:34   `game:progress`(중간집계, 익명게임은 누가 뭘 선택했는지 안 넣음)
> ```
> 그래서 이건 "필드 하나 채워 달라"가 아니라 **"이 금지 조항을 완화해도 되는가"** 라는 기획 결정 요청이다.
> 아래 설명이 그 근거다. 결정이 "안 된다"로 나면 프론트가 그 화면을 다시 그려야 한다.

### 초등학생 설명

반장 선거를 한다고 하자. 칠판에 후보 이름을 적고, 표가 들어올 때마다 **정(正)자**를 그린다.

지금 서버는 **"6명 중 4명이 투표했어요"** 만 알려준다. 누가 몇 표인지는 안 알려준다.
그래서 칠판의 막대가 **전부 0인 채로 멈춰 있다.**

투표가 끝나면 결과는 정확히 나온다. 하지만 **투표하는 동안 화면이 죽은 것처럼 보인다.**

> 비밀투표인데 표를 세도 되나? → **프론트는 된다고 봤다. 하지만 명세는 안 된다고 적혀 있다.**
> 숨겨야 하는 건 **"누가 어디에 넣었는지"** 지 **"몇 표인지"** 가 아니라고 판단했다.
> `optionId → 표 수`만 보내고 투표자 정보는 안 보내므로 "누가 뭘 골랐는지 아무도 몰라요"는 그대로 지켜진다.
> 게임 기획안이 막는 것도 *투표자 신원*이다.
>
> **다만 이건 프론트의 판단이지 승인된 결정이 아니다.** 명세의 "득표·내용 비공개"를
> "투표자 신원 비공개"로 좁힐지 기획·API 담당이 결정해 줘야 한다.

### 계약

```ts
// src/protocol/types.ts
export interface GameProgress extends Versioned {
  roundId: RoundId
  entries: { memberId: MemberId; state: 'COMPLETE' | 'WAITING' }[]
  // ↓ 추가. 킹메이커 투표 단계에서만 채운다
  optionVotes?: { optionId: OptionId; votes: number }[]
}
```

**언제 채우나:** 킹메이커 `VOTE` 단계에서 표가 들어올 때마다.
후보 전체를 매번 보낸다(0표인 후보도 `votes: 0`으로 포함). 임시 서버 구현:

```js
// local-server/engines.js — king.vote 처리 직후
const { counts } = tallyKingmaker(ctx)
ctx.progress(
  progressFrom(ctx, new Set(st.votes.keys())),
  st.candidates.map((o) => ({ optionId: o.optionId, votes: counts.get(o.optionId) ?? 0 })),
)
```

### 안 주면

프론트가 `optionVotes[o.optionId] ?? 0`으로 읽으므로 **막대가 전부 0으로 굳는다.**
에러도 경고도 없다. 투표와 결과는 정상 동작한다.

```ts
// src/screens/Game/games/KingmakerGame.tsx:137
.map((o) => ({ ...o, votes: optionVotes[o.optionId] ?? 0 }))
```

### 확인 방법

킹메이커 투표 중 `game:progress`를 찍어보고 `optionVotes`가 후보 수만큼 들어 있는지 본다.

## ④ 라운드 소요 시간 — 지금은 프론트가 직접 잰다

> **명세 상태:** 현재 `game:result`는 `roundId, variant, result, resultScreenAt` 네 개뿐이라 이 값이 없다. 추가 요청이다.
>
> ⚠️ **이름 충돌 주의.** 명세에 이미 `elapsedMs`가 있는데 **전혀 다른 값**이다.
> ```
> API 기본 명세서 요약.md:126  시간초: `elapsedMs = stopServerTime - startServerTime`
> ```
> 그건 *시간초 잡기에서 한 사람이 START~STOP 사이에 흘린 시간*이고,
> 여기서 요청하는 건 *라운드 전체가 걸린 시간*이다. `NunchiRoundLog.elapsedMs`(판 시작~누른 시각)까지
> 합치면 같은 이름이 세 군데다. **다른 이름을 쓰는 편이 낫다** — 예: `roundElapsedMs`.

### 초등학생 설명

달리기를 했는데 **심판이 기록을 안 재준다.**
그래서 관중석에 있는 사람들이 각자 스톱워치를 눌러서 잰다.

문제는 **사람마다 시계를 누른 순간이 조금씩 다르다는 것.**
같은 경기인데 누구 화면엔 12.3초, 누구 화면엔 12.9초가 뜬다.
중간에 화면을 새로 켠 사람은 아예 0초가 뜬다.

심판이 재서 알려주면 모두 같은 기록을 본다.

### 지금 상태

**이건 계약에 아예 없는 값이다.** 프론트가 임의로 만든 것.

```ts
// src/store/roomStore.ts:276
elapsedMs: roundStartedAt ? Date.now() - roundStartedAt : 0,
```

`game:started` 받은 시각부터 `game:result` 받은 시각까지를 클라이언트가 직접 뺀다. 가이드 5초도 포함된 값이다.

증상:

- 클라마다 값이 다르다 (네트워크 지연·탭 전환·백그라운드 스로틀링)
- 새로고침하거나 늦게 들어오면 `0`
- 결과 화면에서 **사람마다 다른 숫자를 본다**

> ⚠️ `NunchiRoundLog.elapsedMs`와 **이름은 같은데 출처가 전혀 다르다.**
> 그쪽은 서버가 재는 "판 시작부터 누를 때까지"이고, 이쪽은 클라가 재는 "라운드 전체 소요"다.

### 요청

`game:result`에 **서버가 잰 라운드 소요 시간**을 추가해 달라.

```ts
'game:result': (
  p: Versioned & {
    roundId: RoundId
    variant: ResultVariant
    result: GameResult
    resultScreenAt: string
    roundElapsedMs: number   // ← 추가 요청: 라운드 시작(가이드 포함)부터 판정까지 서버가 잰 ms
  },                          //    (기존 elapsedMs 두 곳과 헷갈리지 않게 이름을 다르게 잡았다)
) => void
```

받으면 `roomStore`의 계측 코드를 지우면 끝이다.

## ⑤ 소켓 이벤트 명세서가 API 명세서보다 뒤처져 있다 (문서 동기화)

앞의 ①~④는 "구현이 명세와 다르다"는 얘기였다. 이건 성격이 다르다 —
**두 명세서가 서로 다르고, `API 기본 명세서 요약.md`(v1.0 정정)가 이긴다는 게 기존 결정이다.**
백엔드가 `실시간 소켓 이벤트 명세 요약.md`만 보고 구현하면 **네 군데가 어긋난다.**

| 소켓 명세서 (뒤처짐) | 실제 계약 (API 명세 + 프론트 타입) | 결과 |
|---|---|---|
| `game:tick` (눈치 타이머 동기화) — `:34` | **`server:tick`** 하나로 통합. 서버시각·phase 남은시간·방 만료를 1초마다 같이 보냄 | 없는 이벤트를 만들게 됨 |
| `ladder.pick`(전원, `laneIndex`) — `:32` | 레인 선택 제거. `ladder.start`만 (그나마 이것도 ②에서 삭제 대상) | 안 오는 입력을 기다림 |
| `room:closed` reason = `HOST_LEFT·EXPIRED` — `:27` | **`HOST_LEFT` \| `EMPTY` \| `INACTIVE`** | `EXPIRED`는 존재하지 않음 |
| `member:left` reason = `LEAVE·KICK·DISCONNECT` — `:27` | **`LEAVE` \| `KICKED` \| `DISCONNECT`** | `KICK` ≠ `KICKED` |

### 특히 `KICK` vs `KICKED`

한 글자 차이라 리뷰에서 절대 안 걸린다. 백엔드가 `'KICK'`을 보내면
프론트의 분기가 조용히 아무 데도 안 걸려서 **강퇴가 "그냥 나감"으로 표시된다.** 예외도 안 난다.

프론트·임시 서버는 전부 `KICKED`를 쓴다 (`types.ts:502`, `server.js:509`).
별도 이벤트 `member:kicked`도 `{ reason: 'KICKED' }`다.

### `INACTIVE`는 타입에만 있고 아무도 안 쏜다

무활동 방 삭제를 없앤 사용자 결정 때문이다. `ROOM_IDLE_MS` 상수와 `expiresAt` / `roomExpiresInMs` 필드는
**API 계약이 요구해서 남겨뒀고 값도 계속 채워 보낸다.** 실제로 방이 만료돼 닫히는 일은 없다.

백엔드가 만료 삭제를 **살릴지 말지 결정해 달라.** 살린다면 `INACTIVE`를 쏘면 되고,
안 살린다면 `room:closed`의 reason에서 `INACTIVE`를 빼고 `roomExpiresInMs`도 의미 없는 값이 된다.

### 요청

소켓 명세서 `:27`, `:32`, `:34`를 v1.0 기준으로 갱신. 새로 만드는 건 없고 문서만 맞추면 된다.

## 요약

| # | 항목 | 어디 | 명세 상태 | 안 주면 | 티가 나나 | 부담 |
|---|---|---|---|---|---|---|
| ① | `WinnerResult.rounds` | `game:result` | 없음 → **추가** | 눈치 결과 화면이 당첨자 카드로 되돌아감 | ⭕ 보임 | **높음** (라운드 이력 보관) |
| ② | `roulette.pick` / `ladder.start` | `game:action` | 있음 → **삭제** | 두 게임 라운드가 안 끝날 수 있음 | ⭕ 터짐 | 명세 수정 (문서 2개 동기화) |
| ③ | `GameProgress.optionVotes` | `game:progress` | **명시적 금지** → 완화 결정 필요 | 킹메이커 득표 막대가 0으로 굳음 | ❌ 조용히 틀림 | 기획 결정 + 구현 낮음 |
| ④ | `roundElapsedMs` | `game:result` | 없음 → **추가** (이름 충돌 주의) | 사람마다 다른 소요 시간을 봄 | ❌ 조용히 틀림 | 낮음 |

| ⑤ | 소켓 명세서 4곳 (`game:tick`, `ladder.pick`, `room:closed`, `member:left`) | 문서 | **뒤처짐** → 갱신 | 없는 이벤트 구현 / `KICK`≠`KICKED`로 강퇴 표시 실패 | ❌ 조용히 틀림 | 문서만 수정 |

②③은 백엔드 혼자 못 정한다 — **명세를 고치는 건**이라 기획·API 담당이 함께 봐야 한다.
①④는 명세에 없던 걸 얹는 순수 추가 요청이다.
⑤는 코드 작업이 없다 — 두 명세서를 맞추기만 하면 되지만, 안 맞추면 백엔드가 **틀린 문서를 보고 구현하게 된다.**
