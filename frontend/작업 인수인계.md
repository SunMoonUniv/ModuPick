# 작업 인수인계

코드·명령어·규칙은 `CLAUDE.md`에, 프레임 옮기는 법과 검증 방법도 거기 있다.
**여기에는 코드를 읽어서는 알 수 없는 것만 적는다** — 확정된 결정, 밟으면 아픈 함정, 아직 답을 못 받은 질문.

## 1. 현재 상태

**프론트가 실제 백엔드(`backend/`) 계약에 맞춰졌다.** 소켓 이벤트·게임 phase·설정 필드·결과 payload를
전부 `backend/app/schemas/events.py` · `app/domain/game_config.py` · `app/domain/games/*.py`의 실제 코드에 맞춰
다시 썼다. `npm run build`와 `npm run lint`가 통과한다.

**그 대가로 임시 서버(`local-server/`)와는 더 이상 통신되지 않는다.** 이벤트 이름부터 다르다
(`server:tick`→`game:tick`, `game:replay` 삭제, `game:decide` 추가). 이제 검증은 `backend/`를 띄워서 한다.

**실제 백엔드 상대 통합 검증을 마쳤다** (2026-08-11). `docker compose up -d` + `npm run dev` + 봇 5명으로
게임 6종을 끝까지 돌렸고, 브라우저에서 6인 대기방·룰렛·킹메이커·눈치(무효 라운드까지)를 직접 확인했다.
그 과정에서 타입만 맞춘 상태로는 드러나지 않던 버그 6건이 나왔고 전부 고쳤다(§2 함정 참고).

## 2. 함정

**아바타 파일 순서.** `src/assets/avatars/a01~a30.png`의 번호는 Figma 캐릭터 시트(`618:5799`)의 나열 순서와 **일치하지 않는다**
(시트 25번째 칸은 박쥐인데 `a25.png`는 물범 광대). 시트에서 뽑은 값을 **인덱스로 배정하면 30종이 전부 어긋난다** — 캐릭터를 보고 짝지어야 한다.
확정된 매핑은 `src/constants/avatarTiles.ts`에 캐릭터 이름 주석과 함께 들어 있다.

**`--color-stage: #2e1a63`** (게임 무대 배경) 은 프레임을 뽑지 않고 스크린샷을 눈으로 맞춘 **추정치**다. 정확한 fill로 교정 필요.

**실연동에서만 드러난 것들 — 다시 밟지 말 것.**

| 무엇 | 증상 | 정본 |
|---|---|---|
| 셀렉터가 새 배열을 만들면 화면이 죽는다 | 대기방 진입 즉시 `Maximum update depth exceeded`로 흰 화면 | `selectableGameIds()`는 순수 함수이고 화면이 `useMemo`로 부른다 |
| 모든 라운드는 `READY`로 시작한다 | phase 유니온에 없어 어느 분기에도 안 걸림 | `round_service.start`가 `game:started` 직후 보낸다 |
| `timer.stop`은 `elapsedMs`를 실어야 한다 | 안 실으면 STOP마다 `game.elapsed_rejected` 오류 토스트 | 서버 관측값과 0.4초 안에서 맞아야 채택된다 |
| 저격 기권은 **보내지 않는 것** | 빈 배열을 보내면 `vote.limit_exceeded`로 거절 | `snipe.py`의 `check_ballot`이 `not picks`를 막는다 |
| 방장은 `member:ready`를 보낼 수 없다 | 보내면 `game.invalid_action` | 방장은 준비 상태를 갖지 않는다(자기를 기다리는 구조 금지) |
| 교착 선택은 다음 phase가 오면 지워야 한다 | 「다시」를 골라 새 라운드가 열려도 선택 창이 남는다 | `roomStore.ts`의 `DECISION_PHASES` |

**봇으로 6인 채우기.** `npm run bots -- MODU-147098 5` (`devtools/bots.mjs`, 의존성 없음).
슬롯 선점 → 프로필 확정(`avatarId: null`이면 서버가 남은 번호를 배정) → 소켓 → READY까지 하고,
게임이 시작되면 6종의 입력을 흉내 낸다. 방장 전용 액션(룰렛·사다리 시작)은 브라우저에서 눌러야 한다.

조용히 실패하는 자리들 — 소켓 `conn:auth`의 코드는 표시용 `MODU-147098`이 아니라 **6자리 숫자(`147098`)** 여야 하고,
`avatarId`를 직접 줄 거라면 **대문자 `A01`**이다. 어느 쪽이 틀려도 REST는 통과했는데 소켓만 거절돼 "명단에는 있는데 READY 0"이 된다.
`game:action`에는 **`roundId`와 `phaseSeq`를 반드시 되실어야 한다** — 빠뜨리면 서버가 조용히 되돌려서
"아무도 입력하지 않은 판"이 되고, 결과 화면으로는 넘어가서 알아채기 어렵다.
대기방으로 돌아오면 서버가 READY를 전부 내리므로, 봇은 `round:closed`를 받고 `member:ready`를 다시 쏴야 연달아 검증할 수 있다.
봇 프로세스를 죽여도 방에서 곧바로 빠지지 않는다 — 이탈 유예(기본 30초)가 지나야 자리가 반환된다.

## 3. 결정된 사항

**프레임이 파운데이션 시트보다 우선한다.**
시트(`543:13`)에서 가져올 것 — 색 팔레트, 테두리 두께(카드5/컨트롤4/얇은3), 하드 그림자, 라디우스.
프레임(`542:xxx`)에서 가져올 것 — 레이아웃, 폰트 패밀리, 폰트 크기.
`tokens.css`의 `--font-size-*`는 강제 규격이 아니라 참고값이다. 프레임이 다른 값을 쓰면 화면 CSS에서 그 값을 써도 된다.

**동점 명단(`game:tie`)은 다음 단계까지 들고 간다.** 서버는 `TIE_NOTICE`에 딱 한 번만 보내고
이어지는 `RUNOFF`·`REMATCH`에서는 다시 알려주지 않는다. 스토어가 `game:phase`마다 `tie`를 비우면
결선인데도 전원이 대상인 것처럼 그려진다(실제로 저격 결선이 그렇게 틀려 있었다).
비우는 시점은 `roomStore.ts`의 `TIE_KEEP_PHASES`에 있다 — 여기 없는 단계로 넘어갈 때만 비운다.
시간초 재대결에서 대상자만 START를 열 수 있는 것도 이 명단이 살아 있어야 가능하다.

**동점 통지와 교착 선택은 `GameScreen`이 한 곳에서 그린다** (`components/game/TieOverlay`).
게임별로 붙이지 않는다 — 6종이 같은 `tie`·`decision` 상태를 쓰기 때문이다. 눈치의 무효 라운드도
같은 오버레이를 쓰므로 게임 컴포넌트 안에 방장 버튼을 다시 만들지 말 것.
킹메이커만 후보가 `OPTION`이라 문구를 투표 단계 payload에서 받아 둬야 한다 —
`TIE_NOTICE` 단계의 payload는 비어 있어서, `GameScreen`이 직전 단계의 후보 문구를 캐시해 쓴다.

**시간초 결과의 순위는 화면이 다시 매긴다** (`Result/adapters.ts`).
백엔드는 `records`를 |오차| **오름차순으로만** 정렬하고 `rank`를 붙인다(`app/domain/games/timer.py`).
`criterion`이 `FARTHEST`인 판에서는 그 1번이 실제 승자(`winnerMemberId`)와 다른 사람이다.
그래서 화면이 기준에 맞춰 정렬하고 기록 없는 사람(`elapsedMs === null`)을 맨 뒤로 보낸다.

**룰렛·사다리의 방장 버튼은 상태 밴드(`GameHud`) 가운데에 있다.** 프레임에 없는 자리라
`GameHud`의 `center` 슬롯을 새로 만들어 얹었다 — 디자인이 오면 그 슬롯 위치만 바꾸면 된다.
룰렛 원판 중앙의 `PICK!`은 표시 전용이다(누르는 버튼이 두 개로 보이지 않게).

**룰렛·사다리는 방장이 눌러야 시작한다** — 되돌렸다.
실제 백엔드에 `ARMED` phase가 있고 `roulette.pick` / `ladder.start`가 **방장 전용 액션으로 살아 있다**
(`app/services/games/roulette.py`의 `ACTIONS`). 30초 안에 안 누르면 서버가 대신 실행한다(`ARMED_MS`).
그래서 두 화면에 방장 버튼을 다시 넣었다. 가이드는 5초가 아니라 **3초**다(`game_service.GUIDE_MS`).

**시간초에도 가이드가 있다.** 임시 서버에서 시간초만 가이드를 건너뛰게 했던 것은 되돌렸다 —
실제 백엔드는 6종 모두 `GUIDE`로 시작한다. START는 `RUNNING`·`REMATCH`에서만 받으므로 그 두 단계가 아니면 버튼을 잠근다.
잠그지 않으면 클라이언트 타이머만 돌고 서버엔 출발 기록이 없어 이어지는 STOP까지 거절당한다 — 기록이 통째로 날아간다.

**표지의 움직임은 프레임에 없는 것을 사용자 요청으로 얹은 것이다.**
아래 슬라이더가 오른쪽으로 계속 흐르고(카드에 마우스를 올리면 관성 있게 멈춘다), 카드를 누르면 오른쪽 패널이 그 게임으로 바뀐다.
미리보기는 게임당 9초짜리 연출이 반복되는 **가짜**다 — 등장인물·결과가 전부 상수라서 서버와 무관하고, 실제 게임 화면과도 다르다.
`DemoPanel`의 시계로 `performance.now()`가 아니라 **`document.timeline.currentTime`** 을 쓴 이유가 있다:
탭을 벗어나면 CSS 애니메이션만 멈추고 실제 시각은 흘러서, 돌아왔을 때 "결과는 떴는데 원판은 아직 도는 중"으로 영구히 어긋난다.

**창 크기 대응은 확대·축소 한 방으로 끝냈다.** (사용자 요청)
화면은 여전히 1920×1080 좌표로만 그리고, `Viewport`가 무대 전체에 `min(창너비/1920, 창높이/1080)` 배율을 먹인다.
브레이크포인트를 새로 만들거나 화면별로 반응형을 넣지 말 것 — 배율 하나로 비율이 유지된다.
대신 `vh`/`vw`는 transform을 무시하고 실제 창을 기준으로 재므로, 무대에 비례해야 하는 값은 1080/1920 기준 px로 쓴다.

**주소는 고정하고 화면만 바뀐다.** `main.tsx`가 `BrowserRouter`가 아니라 **`MemoryRouter`**를 쓴다.
의도된 부작용이라 "버그"로 고치지 말 것 — 브라우저 뒤로가기 안 먹음, 새로고침하면 무조건 홈(=방에서 나가짐), `/room` 딥링크 불가.
되돌리려면 `main.tsx` 한 줄만 바꾸면 된다.

**무활동 10분 방 삭제는 없앴다.** `server.js`의 `withRoom()`과 5초 스위퍼에서 만료 삭제 분기를 뺐다 (pending 슬롯 2분 회수는 유지).
`ROOM_IDLE_MS` 상수와 `expiresAt` / `roomExpiresInMs` 필드는 API 계약이 요구해서 **남겨뒀고 값도 계속 채워 보낸다.**

**오토 레이아웃 프레임을 옮길 때 줄높이를 먼저 맞춘다.**
브라우저의 `line-height: normal`은 Figma의 텍스트 박스보다 한 줄마다 5~6px 크다. 세로 스택에서는 이게 그대로 쌓여
아래로 갈수록 프레임과 어긋난다. Figma 값은 Black Han Sans = 글자 크기의 **1.265배**, Nanum Gothic Coding = **1.0배**,
Gothic A1 = 1.25배다 (`get_metadata`의 text 노드 height로 확인). 스택 컨테이너에 이 값을 먼저 박고 시작할 것.

**킹메이커 투표 중 실시간 득표 막대는 뺐다.** (프레임 `878:684`과 다르게 간 곳)
실제 백엔드가 중간 득표를 **의도적으로 내려주지 않는다** — "득표 수는 싣지 않는다. 다음 회차의 전략이 되기 때문이다"
(`app/schemas/events.py`의 `GameTieData`). `game:progress`에 오는 것은 `{votedCount, totalCount}` 건수뿐이다.
그래서 왼쪽 절반을 순위표가 아니라 **후보 목록 + 참여 현황**으로 바꿨다. 계약을 넓혀 달라고 요청하지 않았다 —
감추는 것이 기획 의도이기 때문이다.

**이건 킹메이커만의 문제가 아니다.** `game:progress`는 어느 게임에서도 **사람별 상태를 주지 않는다.**
그래서 "누가 제출을 마쳤는지"를 사람마다 표시하던 자리(시간초 카드, 저격 조준경, 킹메이커 제출 현황)는
전부 건수 표시로 바뀌었다. 내 제출 여부만 화면이 직접 기억한다.

**투표 화면의 "내 제출" 표시.**
서버가 투표 단계에서 제시자를 감춰 보낸다(phase payload의 `candidates`에 `optionId`와 `label`뿐이다).
그래서 **내가 제출할 때 보낸 본문을 컴포넌트가 기억했다가 본문이 같은 줄을 잠근다.**
서버도 자기 안건 투표는 `vote.self_not_allowed`로 막으므로 판정은 어긋나지 않는다.
(프레임의 컷오프 선은 득표를 알아야 그을 수 있어 함께 사라졌다.)

**집계 결과 화면은 킹메이커 전용이 됐고, 공개되는 것은 투표자가 아니라 제시자다.**
`TALLY`를 내는 엔진은 킹메이커 하나뿐이다(저격은 `WINNER`다). 그리고 **투표자는 어느 설정에서도 나오지 않는다** —
`revealAuthors`가 켜면 나오는 것은 안건을 낸 사람(`rows[].authorMemberId`)이다.
그래서 프레임의 「투표한 사람」 칸을 「제안자」로 바꿔 채웠다.

**기록 결과(`542:2292`)는 시간초의 화면이고 결과 형태는 `RECORD`가 아니라 `WINNER`다.**
시간초 payload는 `WinnerResult.detail`에 `{targetMs, criterion, records}`로 들어온다.
(`RECORD`를 쓰는 건 눈치게임뿐이다.)

**여기서 프레임과 일부러 다르게 간 두 곳.**
① 정확도 막대 길이 — 프레임의 픽셀값에서 역산되는 배율(오차 1.176초에서 0이 되는 선형식)의 근거를 알 수 없어,
`1 - 오차/그 판의 최대 오차`로 정했다. 꼴찌가 항상 빈 막대이고 1위가 거의 꽉 차는 문법은 같지만, 한 명이 크게 빗나가면 나머지가 촘촘해진다.
② 순위표의 닉네임 칸 — 프레임은 2자 기준 40px인데 닉네임은 8자까지 들어와서 88px + 말줄임으로 넓혔다.
그만큼 오른쪽 막대·알약이 프레임보다 약 60px 오른쪽에 놓인다.

**어느 결과 화면을 쓸지는 `variant`가 아니라 `gameId`로 고른다.**
`variant`와 게임이 1:1이 아니다 — 룰렛·시간초·저격이 **모두 `WINNER`** 인데 `detail`의 모양이 셋 다 다르다
(룰렛 `{seed, sliceOrder}` / 시간초 `{targetMs, criterion, records}` / 저격 `{tally, abstainCount, randomFallback}`).
사다리는 `ASSIGN`, 킹메이커는 `TALLY`, 눈치는 `RECORD`다. `ResultScreen`이 `gameId`로 갈라 `adapters.ts`로 넘긴다.

**결과 payload는 사람을 `memberId`로만 준다.** 닉네임·아바타가 없어 `game:started`의 `roster` 스냅샷과 이어 붙여야 한다.
그 접합은 `screens/Result/adapters.ts` 한 곳에 모아 뒀다.

**요약 수치 3개는 서버가 문구까지 확정해 내려준다** (`result.stats`의 `{label, value}`).
화면이 다시 계산하지 말 것 — 게임마다 기준이 갈린다.
프레임에는 사람별 득표수가 아예 없는데, 그러면 게임이 만들어낸 정보가 통째로 사라져서
아래 "비껴간 사람" 알약에만 `세이프! · N표`로 덧붙였다 (0표면 그냥 `세이프!`).
당첨자 카드와 아래 띠는 당첨자 발표(`542:1119`)와 판이 같아 `SafeBand`·`confetti.tsx`로 공통화했다.

**저격 화면에서 프레임과 다르게 간 세 곳.**
① 조준경 — 프레임은 바깥 링·중간 링·아바타 원판이 5~13px씩 어긋나 있다(손으로 놓은 흔적). 동심원으로 맞췄고
십자 조준선도 링 바깥에 대칭으로 붙였다. ② HUD 오른쪽 알약 — 프레임 문구는 "동점 시 서든데스 미니 룰렛"인데
엔진은 동점자끼리 결선 투표를 반복하므로("`ctx.tie`") 문구를 그렇게 고쳤다. ③ 버튼 — 프레임엔 "발사!" 하나뿐이라
아무도 안 고른 상태에서는 같은 자리가 "기권하기"(잉크색)로 바뀐다. 서버는 빈 배열을 기권으로 받는다.
총알 궤적은 **장식이다** — 실제 투표와 이어붙이면 누가 누굴 쐈는지가 드러나므로 발사된 *개수*만큼만 켠다.

**눈치게임에는 탈락이 없다.** 계약을 넓힐 필요가 없었다 — 이미 있었고, 의미가 우리가 생각한 것과 달랐다.
`RECORD` 결과가 `rounds[].rows[]`로 라운드별 판정을 그대로 준다(`{memberId, verdict, elapsedMs}`).
판정값은 4종이고 **어느 것도 「탈락」이 아니다**(`app/domain/games/nunchi.py`의 `Judgment`):

| 값 | 뜻 |
|---|---|
| `SAFE` | 혼자 눌러 **빠져나갔다**. 더 이상 뽑힐 일이 없다 |
| `OVERLAP` | 판정창 안에 겹쳐 눌러 **그대로 남는다** |
| `NO_INPUT` | 누르지 않아 **그대로 남는다** |
| `LAST` | 최후 1인으로 **뽑혔다** |

즉 이 게임은 "살아남기"가 아니라 "빠져나가기"다. 화면 문구를 전부 그 방향으로 뒤집었다
(생존/탈락 → 안전 확정/남음). 프레임(`542:2619`)의 「통과 / 탈락」 두 줄은 「빠져나감 / 남음」으로 바꿨다.

**라운드 판정은 라운드가 끝난 뒤에만 온다** — 진행 중에 보이면 그것이 곧 정답이기 때문이다.
그래서 인게임의 "눌린 순서" 패널은 라운드가 끝나야 채워진다. 대신 **시각이 서버가 잰 값**이라 클라 관측값보다 정확하다.

**눈치 인게임에서 프레임과 다르게 간 두 곳.**
① 남은 초 — 프레임은 게이지 막대 *안*에 넣는데, 게이지가 줄면 글자가 잉크색 띠 위로 나와 안 읽힌다.
그래서 위쪽 설명 줄에 "남은 N초 · 제한시간 M초"로 합쳤다. ② "눌린 순서"의 시각 —
**서버는 완료/대기만 보내고 누른 시각을 안 준다.** 그래서 `game:progress`가 도착하는 순서를 클라가 쌓아 순번을 매기고,
시각은 첫 도착 대비 상대값으로 잰다(단계가 바뀔 때 서버가 progress를 비워 보내서 라운드마다 저절로 초기화된다).
순서 자체는 서버 판정 순서라 정확하지만 초 단위는 클라 관측값이다 — 백엔드가 눌린 시각을 주면 그쪽으로 바꿀 것.

**참가자가 6명을 넘으면 두 화면 모두 스스로 줄어든다.**
프레임은 전부 6인 기준인데 정원은 10명이다. 저격은 조준경 격자를 3열→4열로 늘리고 칸 전체에 `scale`을 먹이고,
눈치는 참가자 카드 폭을 줄여 한 줄에 밀어 넣는다. 6명일 때는 두 경우 다 프레임 값이 그대로 들어간다.

**소요 시간을 클라가 재던 것은 없앴다.** 결과 화면 아래 요약 수치는 전부 서버의 `result.stats`를 그대로 그린다.

---

**`백엔드 연동 요청 사항.md`는 이제 무효다.** 거기 적힌 네 건(`optionVotes`, `WinnerResult.rounds`,
`elapsedMs`, 죽은 액션 타입)은 실제 백엔드 코드를 읽어 전부 정리됐다 — 세 건은 요청할 필요가 없었고
(`rounds`는 이미 있었고, `elapsedMs`는 `stats`가 대신하고, 액션 타입은 살아 있는 계약이었다),
`optionVotes`는 **의도적으로 안 주는 값**이라 요청을 접었다. 새로 넘길 요청은 없다.
