## 1. 문서 읽는 법

### 1.1 기능과 요구사항의 차이

| | 요구사항 (`requirements.md`) | 기능 (이 문서) |
| --- | --- | --- |
| 주어 | 사용자 | 시스템 |
| 문장 | "**참여자로서** 코드만으로 들어가고 싶다" | "초대 코드를 검증하고 슬롯을 선점한다" |
| 검증 | Given/When/Then 수용 기준 | 구현 완료 여부 · 담당 레이어 |
| 쓰는 사람 | 기획 · QA | 개발 · 일정 산정 |

**하나의 스토리가 여러 기능으로 쪼개지고, 하나의 기능이 여러 스토리를 떠받친다.** 두 문서는 [§4 요구사항 커버리지](#4-요구사항-커버리지)에서 양방향으로 맞춰 본다.

### 1.2 ID 체계

요구사항의 `US-` 번호대와 **일부러 같은 자리수를 쓴다**. `F-1xx`를 보면 `US-1xx`를 찾아보면 된다.

| 접두어 | 범위 |
| --- | --- |
| `F-1xx` | 방 생성 · 코드 입장 · 프로필 |
| `F-2xx` | 대기방 |
| `F-3xx` | 게임 설정 · 시작 · 진행 공통 |
| `F-4xx` | 게임 6종 개별 (`41x` 룰렛 · `42x` 사다리 · `43x` 킹메이커 · `44x` 시간초 · `45x` 저격 · `46x` 눈치 · `47x` 동점) |
| `F-5xx` | 결과 · 저장 · 재시작 |
| `F-6xx` | 이탈 · 만료 · 예외 |
| `F-7xx` | 인증 · 에러 · 실시간 인프라 · 화면 규격 · 접근성 |
| `G-xx` | 빈틈 분석에서 발견한 구멍 |

**ID는 재사용하지 않는다.**

### 1.3 레이어 표기

| 값 | 뜻 |
| --- | --- |
| `BE` | 서버가 단독으로 책임진다. 클라이언트는 결과를 받기만 한다 |
| `FE` | 화면 안에서 끝난다. 서버가 알 필요가 없다 |
| `공통` | 양쪽이 각자 몫을 구현해야 완성된다 |

**판정·난수·권한 검증은 예외 없이 `BE`다**([NFR-05](requirements.md#nfr-05--결과-무결성)). `FE`로 표기된 것은 그 기능이 결과에 영향을 주지 않는다는 뜻이다.

### 1.4 구현 상태 표기

| 값 | 뜻 |
| --- | --- |
| `데모` | `mvp/`에 mock 데이터로 동작한다. **방장 시점 단일 시나리오 · 봇 5인 시뮬레이션** 기준이다 |
| `데모 부분` | 화면은 있으나 시나리오 일부만 재현된다 |
| `미착수` | 코드가 없다 |

> **백엔드는 전체가 `미착수`다.** `backend/`에 소스가 없다. 따라서 `BE`로 표기된 기능의 구현 상태는 모두 `미착수`이며, 표에서는 프론트엔드 기준 상태만 적는다.

## 2. 기능 지도

```
ModuPick
├── 진입          F-1xx  방 만들기 · 코드 입장 · 프로필(닉네임·캐릭터 선점)
├── 대기방        F-2xx  참가자 목록 · 채팅 · 준비 완료 · 강퇴
├── 게임 공통     F-3xx  게임 선택 · 설정 · 시작 · 가이드 · 멱등/마감 · 시각 동기화
├── 게임 6종      F-4xx  룰렛 · 사다리 · 킹메이커 · 시간초 · 저격 · 눈치 · 동점 처리
├── 결과          F-5xx  결과 화면 4변형 · PNG 저장 · 다시 하기 · 대기방 복귀
├── 예외          F-6xx  방장 이탈 · 방 만료 · 연결 종료 · 게임 중 이탈
└── 플랫폼        F-7xx  토큰 인증 · 권한 검증 · 에러 규격 · 화면 규격 · 접근성
```

**기능 수: 98건** (필수 72 · 권장 18 · 선택 8)

기능을 뽑고 요구사항과 양방향으로 대조하면서 발견한 것들이다.

### 6.1 규칙이 없던 지점 — 2026-07-29 전건 확정

발견 당시에는 답이 없어 구현할 수 없던 자리다. **모두 확정되어 [`requirements.md §7`](requirements.md#7-확정된-설계-결정)에 `D-` 번호로 들어갔다.**

| ID | 빈틈 | 확정 | 결정 |
| --- | --- | --- | --- |
| G-01 | **익명 저격 `중복 투표 가능`의 표 수** — "같은 대상을 여러 번 지목할 수 있다"만 있고 상한이 없어, 무제한이면 연타 속도가 결과를 정한다 | **1인 2표** · 같은 대상 몰아주기 허용 | [D-39](requirements.md#7-확정된-설계-결정) |
| G-02 | **킹메이커에서 후보 수 < 1인당 투표 수** — 2표인데 내 것을 뺀 후보가 1개면 남는 표를 어떻게 하는지 없다 | **같은 후보에 몰아주기 허용.** 총 표 수만 검증한다 | [D-40](requirements.md#7-확정된-설계-결정) |
| G-03 | **시간초 동점 재대결 방식** — "동점자끼리 한 번 더"만 있고 목표 시간·START 여부가 없다 | 같은 목표 시간으로 **동점자만 `START`부터 재시작**. 30초 회차 제한도 재적용 | [D-41](requirements.md#7-확정된-설계-결정) |
| G-04 | **방 만료 10분의 "요청"이 무엇인가** — heartbeat도 요청인지, 게임 중에도 도는지 없다 | **사용자 행동만** 갱신. `PLAYING` 중에는 정지 | [D-45](requirements.md#7-확정된-설계-결정) |

| G-06 | **결과 화면에서 방장이 나가면 결과가 사라진다** — 게임 직후가 방장이 가장 잘 나가는 시점인데 PNG 저장 전이면 유실된다 | 방은 폭파하되 **결과 화면은 유지**하고 저장만 허용 | [D-44](requirements.md#7-확정된-설계-결정) |
| G-07 | **눈치게임 라운드 사이 간격** — 바로 이어지면 직전 라운드의 클릭이 다음 라운드에 잡힌다 | 라운드 사이 **3초 카운트다운** · 그동안 입력 차단 | [D-46](requirements.md#7-확정된-설계-결정) |
| G-08 | **사다리 결과 항목 중복 입력** — 같은 역할명을 두 번 넣을 수 있는지 없다 | **허용.** 두 명이 같은 역할을 맡을 수 있다 | [D-48](requirements.md#7-확정된-설계-결정) |

### 6.2 요구사항이 없는 기능

기능으로는 반드시 필요한데 `requirements.md`에 대응 스토리가 없는 것들이다. **스토리를 추가해야 QA가 판정 기준을 갖는다.**

| 기능 | 왜 스토리가 필요한가 |
| --- | --- |
| F-325 서버 시각 동기화 | NFR에 원칙만 있고 사용자가 무엇을 보는지(지연 시 표시)가 없다 |
| F-326 이벤트 순서 보장 | 같은 이유 |
| F-327 서버 시드 기록 | 재현 요구가 어디에도 없다. 운영자 스토리로 필요하다 |
| F-607 유효 입력 0건 팝업 | 게임 3종에 흩어져 있고 공통 스토리가 없다 |
| F-608 이탈자 오프라인 표시 | US-411·US-507에 문장으로만 있다 |
| F-708 디자인 시스템 | NFR-07에 규격만 있고 컴포넌트 일관성 요구가 없다 |

### 6.3 문서 간 모순 — `api.md` 정합성 붕괴 6건 (해소 완료)

`requirements.md`는 "2026-07-27 기준 `api.md`에 전건 반영 완료 · 두 문서 정합"이라고 적고 있었다. **[§9.4](requirements.md#94-정합성-점검-방법)의 점검 명령을 그대로 돌린 결과 사실이 아니었다.** 2026-07-29 전건 수정했다.

| ID | 문제 | 위반한 결정 | 조치 |
| --- | --- | --- | --- |
| M-01 | `ladder.pick { laneIndex }`가 살아 있었다 — 참가자 레인 선택 액션 | [D-16](requirements.md#7-확정된-설계-결정) 서버 자동 배치 | 삭제하고 방장 전용 `ladder.start { mode, memberId? }`로 교체 |
| M-02 | **`king.vote { targetMemberId }`** — 멤버 ID로 투표받고 있었다 | [D-21](requirements.md#7-확정된-설계-결정) 후보 ID 투표. **익명성이 구조적으로 무너지는 결함** | `{ candidateId }`로 교정하고 자기 의견 차단을 서버 대조로 명시 |
| M-03 | `room:snapshot`에 `messages` 최근 50건이 들어 있었다 | [D-26](requirements.md#7-확정된-설계-결정) 채팅 서버 미보관 | 스냅샷에서 제거 |
| M-04 | `bio: 0~24자` | Q-18에서 "`api.md`의 값은 전부 폐기" 선언 | **20자**로 교체(D-42) |
| M-05 | 채팅 `text: 1~200자` | 요구사항은 `S-04H` 근거로 **제한 없음** | 제한 없음으로 교체 |
| M-06 | `S-04H`(방장)와 `S-04P`(참여자)가 뒤섞여 있었다 | 화면설계서 규칙 · [D-31](requirements.md#7-확정된-설계-결정) | 8곳을 H=방장 / P=참여자로 통일 |

**원인은 하나 더 있었다.** `requirements.md §9.2` #15가 "삭제 완료"로 기록한 **소켓 명세 초안 섹션(67줄)이 실제로는 그대로 남아** 수정본과 공존하고 있었다. M-01·M-02의 절반이 이 초안에서 나왔다. 초안 섹션을 삭제해 명세를 하나로 합쳤다.

`requirements.md` 내부의 잔재(§9.1 #20 "채팅 200자" · #24 "의견 40자")도 확정값으로 정정했다.

> **교훈: "반영 완료"라고 적기 전에 §9.4를 실제로 실행한다.** 이번 6건은 모두 그 명령 한 번으로 잡혔다.

### 6.4 아직 열려 있는 충돌 — DB 선택
