> **대상**: 전 개발·평가자
> **작성일**: 2026-08-02
> **원천**: frontend/src 전수 정독(App.tsx · lib/ · screens/ · games/ · components/ · styles/global.css) · backend/app 전수(main.py · config.py) · frontend/package.json · docs_legacy/features.md §10(구 구현 현황) · [06_design_decisions.md](./06_design_decisions.md)(확정 제품 결정) · [../README.md](../README.md)(고정 기준)

우선순위 등급의 정의와 **구현 현황**, 그리고 프로토타입이 설계와 어긋난 지점을 담는다. 본 문서의 **구현 정정 목록은 그 어긋남을 등재하는 유일한 자리**이며, 문서를 구현에 맞추지 않고 **구현을 문서에 맞춘다**.

**설계된 것과 구현된 것을 구분한다.** 다른 문서는 설계를 "~한다" 평서체로 쓰되 그것이 이미 동작한다는 뜻은 아니다. 진척은 이 문서와 각 문서의 상태 열(⬜🔶✅)이 말한다.

## 우선순위 정의

| 등급 | 정의 | 판단 기준 |
|------|------|-----------|
| **P0** | 핵심 경로. 없으면 서비스가 성립하지 않는다 | 이것이 빠지면 "링크로 모여 게임 한 판으로 정한다"는 흐름이 끊긴다 |
| **P1** | 실사용 보완. 제품 가치를 크게 높이지만 없어도 핵심 흐름은 돈다 | 없으면 불편하지만 다른 수단으로 판을 끝낼 수 있다 |
| **P2** | 선택·후속. 특정 상황에서만 쓰이거나 대체 가능하다 | 빠져도 대부분의 사용자가 알아채지 못한다 |

**등급은 기능 단위로 매긴다.** F-ID별 P값의 정본은 [../02_features](../02_features/README.md)의 각 도메인 파일이며, 아래 표는 도메인 축의 **개괄**이지 집계가 아니다 — 기능별 값이 확정되면 [../02_features/README.md](../02_features/README.md)가 도메인별 분포를 싣는다.

| 도메인 | 우선순위의 중심 | 이유 |
|--------|-----------------|------|
| 01 방 만들기·입장 | P0 중심 | 입장이 안 되면 아무것도 시작되지 않는다. 초대 링크 공유의 시스템 공유 시트만 P1이다 |
| 02 대기방 | P0 중심 · 채팅 P1 | 준비 완료·시작 게이트·방 정리는 P0다. 채팅은 없어도 판이 돈다 |
| 03 게임 선택·설정 | P0 중심 · 랜덤 선택 P1 | 게임 선택과 시작은 P0, 랜덤 선택과 템플릿 칩 일부는 P1이다 |
| 04 게임 진행 공통 | **전부 P0** | 판정 엔진·도착 시각·멱등·미입력 처리는 6종이 공유하는 토대라 하나라도 빠지면 전 게임이 성립하지 않는다 |
| 05~10 미니게임 6종 | 게임마다 P0 · 연출 P1 | 판정 경로는 P0, 압박 연출·지목선 가리기 같은 연출 강화는 P1이다 |
| 11 결과·저장 | P0 중심 · 공유 시트 P2 | 결과 전환·화면 4형태·이미지 저장은 P0. 시스템 공유 시트는 저장으로 대체되므로 P2다 |
| 12 공통·오류 | **전부 P0** | 연결 관리·모바일 대응·오류 안내·방 상태 머신은 전 도메인이 딛는 바닥이다 |

**게임 6종 사이에는 우선순위를 두지 않는다.** 6종 구성이 곧 제품의 값어치이므로(D-20) 하나를 빼면 "상황에 맞는 방식으로 정한다"가 성립하지 않는다. 착수 순서는 우선순위가 아니라 난이도가 정한다.

## 구현 현황

기준은 frontend/ · backend/의 실제 코드다. **mvp/ 프로토타입은 이관이 끝나 frontend/로 옮겨졌으며 별도 축으로 세지 않는다.**

| 영역 | 상태 | 실측 근거 |
|------|:----:|-----------|
| 설계 문서 | 🔶 | 본 문서군(docs/)을 작성 중이다 |
| frontend 화면·연출 | 🔶 | React 19 + Vite + TypeScript. 표지·방 생성·프로필·대기방·게임 라우터·결과 화면과 게임 6종 화면이 있다(frontend/src/screens · frontend/src/games) |
| frontend 상태 관리 | 🔶 | zustand 단일 스토어(frontend/src/lib/store.ts). 서버가 없어 봇 5인 시뮬레이션으로 동작한다(frontend/src/lib/data.ts의 BOTS) |
| frontend 결과 저장 | 🔶 | html-to-image로 결과 카드를 PNG로 저장한다(frontend/src/screens/Result.tsx) |
| frontend 모바일 대응 | ⬜ | 1920×1080 고정 스테이지를 통째로 축소한다(frontend/src/App.tsx · frontend/src/styles/global.css). 반응형 레이아웃이 없다 |
| backend API | ⬜ | FastAPI 골격만 있다 — 헬스 체크(GET /health)와 소켓 배선 확인용 에코(WS /ws/echo) 두 엔드포인트뿐이다(backend/app/main.py) |
| backend 게임 로직·판정 | ⬜ | 미착수. 판정·난수·시드·도착 시각 기록이 전부 없다 |
| backend 실시간 라우팅 | ⬜ | 미착수. 방 단위 이벤트 라우팅이 없고 에코 소켓만 있다 |
| DB | ⬜ | **의존성만 준비된 상태**다. backend/requirements.txt에 SQLAlchemy · aiomysql · PyMySQL · Alembic이 있고 backend/app/config.py가 접속 문자열을 들고 있으나, 엔진 초기화·세션 관리·alembic.ini·마이그레이션 디렉터리·스키마가 전부 없다 |
| 배포 | ⬜ | 미착수 |

**서버가 없으므로 게임 기능은 어느 것도 완료가 아니다.** 프로토타입이 그린 화면과 연출은 설계의 일부가 구현된 것이지 기능이 완성된 것이 아니다 — 판정이 브라우저에서 일어나는 한 공정(D-05)과 동시(D-09)가 성립하지 않는다.

## 구현 정정 목록

frontend 프로토타입이 본 문서군의 설계와 어긋난 지점이다. **문서가 이기며 구현을 고친다.** 아래는 frontend/src 전수 정독으로 확인한 것이며 파일 경로와 확인된 동작을 함께 적는다. **36건**이다.

번호 열은 본 목록 안에서만 쓰는 일련번호이며 **프로젝트 식별자가 아니다** — 정정이 끝나면 항목을 지우고 다시 센다. 프로젝트 식별자는 F-ID · REQ-ID · D-NN · ADR-NN · AC-NN · 화면 코드 · 에러 코드 일곱 종뿐이다.

### 구현 부재 — 정정이 아니라 미착수

아래는 프로토타입이 잘못 만든 것이 아니라 **서버가 없어서 아직 없는 것**이다. 정정 목록과 구분해 적는다.

| 항목 | 상태 |
|------|------|
| 서버 판정 권위 | 전 게임의 판정이 브라우저에서 일어난다 — 룰렛 당첨자·사다리 구조·저격 집계·킹메이커 개표·눈치 그룹핑이 전부 클라이언트 계산이다. 백엔드 연동 시 서버 재계산으로 대체한다(D-05) |
| 서버 도착 시각 기록 | 없다. 눈치게임의 판정 기준 시각이 클라이언트 시계다(D-06) |
| 시간초 경과 시간 검증 | 클라이언트 단조 시계로 측정하는 부분은 설계와 같으나(D-07) **서버의 범위 검증이 없다.** 측정과 검증이 짝을 이뤄야 D-07이 성립한다 |
| 입력 멱등 처리 | 없다(D-08) |
| 실시간 동기화 | 없다. 다른 참가자는 봇 시뮬레이션이다(frontend/src/lib/data.ts) |
| 방 생명주기·정리 | 없다. 방 삭제 3조건과 10분 무활동 타이머가 없다(D-12) |
| 참가자 내보내기 | 화면 흐름만 있고 서버 처리가 없다(D-14) |
| DB 엔진·세션 | 없다. backend/requirements.txt에 SQLAlchemy · aiomysql · PyMySQL이 올라와 있으나 backend/app 어디에도 엔진 생성·세션 관리 코드가 없다. backend/app/config.py가 접속 문자열 하나를 들고 있을 뿐 그 값을 읽는 코드가 없다 |
| 마이그레이션 형상 | 없다. requirements.txt에 Alembic이 있으나 alembic.ini도 마이그레이션 디렉터리도 없다. **의존성만 준비되고 배선이 시작되지 않은 상태**다 |

## 잔여 작업과 착수 순서

정정 목록을 반영하며 아래 순서로 만든다. 앞 묶음이 없으면 뒤 묶음을 검증할 수 없다.

| 순서 | 묶음 | 이유 |
|:----:|------|------|
| 1 | DB 배선 — 엔진·세션 초기화 · alembic.ini와 마이그레이션 디렉터리 · 테이블 6개 스키마 | 의존성만 올라와 있고 배선이 없다. 방·참가자를 기록할 곳이 없으면 방 생명주기를 만들 수 없다 |
| 2 | 방 생명주기 — 방 생성·코드 발급·입장 검증·방장 이탈 폐기·방 정리·방 상태 머신 | 이것이 없으면 어떤 게임도 붙일 수 없다 |
| 3 | 실시간 기반 — WebSocket 연결 관리·방 단위 라우팅·참가자 목록·채팅·준비 완료·설정 동기화 | 대기방이 돌아야 게임 진입을 시험할 수 있다 |
| 4 | 판정 공통 — 판정 엔진·도착 시각 기록·멱등 처리·진행 상황 동기화·미입력 자동 처리·결과 브로드캐스트 | 6종이 공유하는 토대다 |
| 5 | 서버 난수 2종 — 운명의 룰렛 · 사다리타기 | 참가자 입력이 없어 가장 단순하다 |
| 6 | 참가자 투표 2종 — 킹메이커 · 익명 저격 | 단계가 나뉘고 결선 반복(D-26)과 익명성(D-10)이 걸린다 |
| 7 | 참가자 실력 2종 — 시간초 잡기 · 눈치게임 | 밀리초 판정·판정창 그룹핑·D-07 예외 검증이 걸려 가장 까다롭다 |
| 8 | 결과·저장 — 결과 전환·화면 4형태·이미지 저장·다시 하기 | 게임이 끝나야 검증할 수 있다 |
| 9 | 모바일 대응 — 정정 32 | 전 화면에 걸치므로 화면이 굳은 뒤에 한 번에 한다. **다만 판정 결함이라 배포 전 필수다** |

**정정 목록은 순서와 무관하게 해당 묶음을 만들 때 함께 처리한다.** 특히 **1**(눈치 승패 반전) · **17·18**(중간 집계 노출) · **16**(반복 상한 부재) · **32**(모바일)는 각각 게임 성립·공정성·종료 보장·판정 가능성에 직결되므로 미루지 않는다.
