# ModuPick — 제품 정의

> 모두가 납득하는 유쾌한 선택
> 최종 수정: 2026-07-26 · 소유자: [TEAM.md](../TEAM.md) 참조

---

## 1. 제품 목표

팀 프로젝트 초기의 '결정 장애'와 '눈치 싸움'을 실시간 미니게임으로 전환해,
**모든 팀원이 납득하는 결정을 빠르고 유쾌하게** 내리도록 한다.

---

## 2. 배경 · 문제

조별 과제, 스터디, 사내 TF 등 팀 프로젝트를 시작할 때마다 팀장 선정·역할 분담 같은
사소하지만 필요한 결정에서 시간이 낭비된다. 직접 토론으로 정하면 감정 소모가 따르고,
아무도 나서지 않으면 결정 자체가 지연된다.

**사용자 문제**: 팀장 선정·역할 분담·업무 배분 과정의 눈치 싸움으로 인한 감정 소모와 시간 낭비.

**해결 방안**: 운명의 룰렛, 랜덤 사다리, 킹메이커, 시간초 잡기, 익명 저격, 눈치게임 —
6종의 실시간 미니게임으로 결정 과정 자체를 즐길 거리로 만든다.
결과는 서버가 확정하므로([D-13](../DECISIONS.md#d-13)) 누구도 조작할 수 없고, 그래서 모두가 승복할 수 있다.

## 3. 차별점

| 차별점 | 상태 |
|---|---|
| **로그인·설치 없는 즉시 시작** — `MODU-####` 4자리 코드만으로 입장([D-01](../DECISIONS.md#d-01)) | ✅ MVP 포함 |
| **미니게임 6종의 다양성** — 결정 성격에 따라 게임을 골라 쓴다 | ✅ MVP 포함 |
| **웹소켓 기반 완전 실시간 동기화** — 전원의 화면이 같은 순간 같은 결과를 본다 | ✅ MVP 포함 |
| **Slack/Discord 웹훅 연동** | ⚠️ **범위 밖 · 결정 필요** ([U-03](../DECISIONS.md#h-아직-결정되지-않은-것)) |

> **주의 — 차별점의 실질**
> 2026-07-24 경쟁 서비스 조사에서 **SpinOfLuck이 이미 "실시간 동기화 룰렛 동시 관전"을 제공**하는 것이 확인됐고,
> 그래서 차별점이 "동시 관전"에서 "**미니게임 다양성 + Slack/Discord 웹훅 연동 통합**"으로 재설정됐다.
> 그런데 **Slack/Discord 연동은 어느 설계 문서에도 구현 계획이 없다** —
> [`06_api/01_rest.md`](../06_api/01_rest.md) · [`06_api/02_socket.md`](../06_api/02_socket.md) · [`07_design/00_foundation.md`](../07_design/00_foundation.md) 어디에도 없다.
> 이대로면 실질 차별점은 "미니게임이 6종"뿐이다. MVP 이후 착수 여부를 정해야 한다.

## 4. 타겟 사용자

조별 과제를 진행하는 대학생, 스터디 그룹, 사내 TF·프로젝트 팀.
특히 **20대 초중반의 IT 친화적 사용자** — 새 도구에 대한 거부감이 적고, 링크 하나로 모이는 방식에 익숙하다.

**사용 규모**: 한 방에 2~10명([D-32](../DECISIONS.md#d-32)). 방은 일회성이며 결정이 끝나면 사라진다.

---

## 5. 사용자 시나리오

팀 프로젝트를 막 시작한 대학생 A가 팀장 선정에 어려움을 겪는다. 팀원은 5명인데 모두 눈치만 본다.

1. A가 ModuPick에서 새 방을 만든다 → `MODU-4271` 코드가 발급된다
2. 팀 채팅방에 코드를 공유하고, 팀원 4명이 뒤 4자리를 입력해 들어온다
3. 각자 닉네임과 동물 캐릭터를 고르고 대기방에 모인다
4. 전원이 `준비 완료`를 누르면([D-12](../DECISIONS.md#d-12)) A가 **운명의 룰렛**을 시작한다
5. 5명 화면에서 룰렛이 동시에 돌고, 같은 순간 같은 사람이 팀장으로 뽑힌다
6. 대기방으로 돌아와 이번엔 **랜덤 사다리**로 역할 분담까지 끝낸다
7. 결과 화면을 PNG로 저장해 팀 채팅방에 올리고, 바로 실제 논의를 시작한다

전 과정에 로그인은 없고, 걸리는 시간은 5분 안쪽이다.

## 6. 개발 범위

### MVP 포함

| 영역 | 내용 |
|---|---|
| 방 | 생성 · 초대코드 발급 · 입장 · 정원(2~10) · 방장 폭파 |
| 프로필 | 닉네임(1~8자, 중복 불가) · 동물 캐릭터 15종 선점([D-08](../DECISIONS.md#d-08)) |
| 대기방 | 실시간 참가자 목록 · 채팅 · READY · 강퇴 · 게임 선택 및 설정 |
| 게임 | **6종 전부** — 룰렛 · 사다리 · 킹메이커 · 시간초 · 저격 · 눈치 |
| 결과 | 게임별 결과 화면 · **PNG 이미지 저장** · 다시 하기 · 대기방 복귀 |

## 7. 핵심 지표

**측정 가능한 것** — 서버 로그 집계 기준

| 지표 | 무엇을 보는가 |
|---|---|
| 방 생성 수 (일/주) | 도달 규모 |
| 방당 평균 참가자 수 | 실제로 팀 단위로 쓰이는가 |
| 세션당 게임 플레이 횟수 | 한 번 모여 몇 개의 결정을 하는가 |
| 게임별 선택 비율 | 6종 중 실제로 쓰이는 것은 몇 개인가 |
| 게임 완주율 | `게임 시작` → 결과 화면 도달 비율. 중도 이탈 관측 |
| 대기방 이탈률 | 방을 만들고 게임 없이 소멸한 비율. 온보딩 마찰 관측 |

**측정할 수 없는 것** — 구조적으로 불가능

| 지표 | 왜 불가능한가 |
|---|---|
| MAU · WAU · 재방문율 | 로그인·사용자 식별자가 없다. 같은 사람이 다시 왔는지 알 수 없다 |
| 신규 미니게임 제안 건수 | 제안을 받는 기능 자체가 없다 |

> ⚠️ **측정 수단이 아직 없다.** [D-06](../DECISIONS.md#d-06) 기본안은 방·라운드를 인메모리에만 두므로
> 애플리케이션 DB로는 위 지표를 집계할 수 없다. **서버 접근 로그 집계** 또는 **별도 분석 도구**가 필요하며,
> 어느 쪽도 아직 정해지지 않았다.

## 8. 리스크

| 리스크 | 대응 | 상태 |
|---|---|---|
| 실시간 동기화 지연으로 사람마다 다른 결과가 보임 | 서버가 결과를 미리 확정하고 클라이언트는 애니메이션만 재생([D-13](../DECISIONS.md#d-13)). 시간 판정은 서버 수신 시각([D-14](../DECISIONS.md#d-14)) | ✅ 설계로 해소 |
| **새로고침 한 번에 방에서 빠짐** | 프론트 이탈 경고 또는 grace period 도입 | ⚠️ [D-04](../DECISIONS.md#d-04) 승인 대기 |
| 네트워크가 느린 참가자가 시간 판정에서 불리 | 팀 프로젝트 도구 수준에서 수용 | ✅ 수용([D-14](../DECISIONS.md#d-14)) |
| **차별점 부재** — 경쟁 서비스가 실시간 룰렛을 이미 제공 | Slack/Discord 연동 여부 결정 필요 | ⚠️ §3 참조 |
| 단일 서버 인스턴스 제약으로 동시 방 수 상한 | Redis 도입 또는 `replica=1` 고정 | ⚠️ [D-06](../DECISIONS.md#d-06) 승인 대기 |
| 초대코드 4자리(10,000개) 고갈 | 활성 방만 유일하면 되고 만료 시 회수([D-02](../DECISIONS.md#d-02)) | ✅ 해소 |
| 미니게임 6종으로 흥미가 유지되는가 | 게임별 선택 비율 지표로 관측 후 판단 | 📊 관측 대상 |
