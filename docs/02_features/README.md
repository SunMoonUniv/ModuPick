## 구현 상태

상태는 **frontend/ · backend/의 실제 코드**로만 판정한다. 판정 규칙은 다음과 같다.

| 규칙 | 내용 |
|------|------|
| BE·RT를 포함한 기능 | **전부 ⬜**다. backend/app에는 헬스 체크와 소켓 배선 확인용 되울림 엔드포인트만 있고 방·게임·라운드 라우트가 없다. 단 FE를 함께 가진 기능은 FE 쪽 표면 유무로 🔶가 될 수 있다 |
| FE 단독 기능 | 표면이 명세대로 갖춰졌으면 ✅ · 일부만 있거나 명세와 어긋나면 🔶 · 표면 자체가 없으면 ⬜ |
| 복수 레이어 기능 | 어느 한 레이어의 표면이라도 존재하면 🔶, 전부 없으면 ⬜. **부분 구현을 완료로 올리지 않는다** |
| 화면 연출 | 서버 판정을 받아 그려야 할 연출이 브라우저 난수로 동작하면 완료가 아니라 🔶다. frontend/src는 봇 시뮬레이션 프로토타입이라 서버 판정이 없다 |
| 저장 | frontend/src는 브라우저 저장을 전혀 쓰지 않는다. LS를 포함한 기능은 ⬜다 |

| 상태 | 기능 수 | 뜻 |
|------|:-------:|-----|
| ✅ 완료 | 7 | 서버에 기대지 않는 화면 표면이 명세대로 갖춰졌다 — F-ROOM-01 · F-ROOM-09 · F-LOBBY-01 · F-SETUP-02 · F-TIMER-03 · F-RESULT-02 · F-RESULT-03 |
| 🔶 진행 중 | 56 | 표면 일부가 있으나 서버 판정·동기화·저장이 없거나 명세와 어긋난다 |
| ⬜ 미착수 | 58 | 표면 자체가 없다 |

7 + 56 + 58 = **121**.

접두사별 상태는 ROOM 2·4·11 · LOBBY 1·7·5 · SETUP 1·8·4 · PLAY 0·2·10 · WHEEL 0·4·1 · LADDER 0·5·2 · KING 0·5·4 · TIMER 1·4·4 · SNIPE 0·5·3 · NUNCHI 0·5·4 · RESULT 2·4·3 · CMN 0·3·7 순(✅·🔶·⬜)이며 각 축의 합은 7 · 56 · 58이다.

## 레이어 분포

한 기능이 여러 레이어를 가지므로 **합이 121을 넘는다.** 아래는 각 레이어를 포함하는 기능 수다.

| 레이어 | 포함 기능 수 | 비고 |
|--------|:------------:|------|
| FE | 74 | 화면·입력 표면이 있는 기능 |
| BE | 70 | 서버 판정·검증·저장이 있는 기능. 이 중 화면이 없는 서버 전용 기능이 다수다 |
| RT | 35 | WebSocket으로 상태를 주고받는 기능 |
| LS | 1 | 브라우저 로컬 보관 — F-LOBBY-08(채팅 로컬 보관·복원) 하나뿐이다 |

**판정과 집계는 전부 BE에 있다.** 결과는 서버가 확정한다는 전역 불변식을 지키기 위해서다. 기능 수를 셀 때 서버 전용 기능(화면 없음)을 포함할지 여부로 값이 갈리므로, 본 문서군은 **포함해 세는 축 하나만** 쓴다 — 121은 서버 전용 기능을 포함한 값이다.

## 전 도메인 공통 제약

전역 불변식([../README.md](../README.md))이 기능 설계에 걸리는 방식을 요약한다. 정본은 그쪽이며 본 표는 기능 관점의 요약이다.

| 제약 | 기능 설계에 걸리는 방식 |
|------|------------------------|
| 서버 판정 권위 | 승자·배정·순위·집계는 BE 기능이 확정하고 FE 기능은 확정된 값으로 수렴하는 연출만 그린다. 판정 로직을 FE 기능으로 채번하지 않는다 |
| 시간 기준 | 시간·순서 판정은 서버 도착 시각이며 정수 밀리초로 기록한다. 유일한 예외는 F-TIMER-05이고 서버가 허용 범위를 검증한다 |
| 멱등 | 1회 제한 입력은 최초 1회만 인정한다 — PICK · START · 안건 제출 · 정지 · UP · 다시 하기가 모두 같은 규칙을 쓴다 |
| 명단 스냅샷 | 게임 시작 시 명단이 고정되고 이탈자도 후보로 남는다. 진행 중에는 강퇴·새 입장을 받지 않는다 |
| 재접속 없음 | 연결 종료가 곧 퇴장이다. 상태 복구 기능을 채번하지 않으며 대신 이탈 경고와 재입장 안내를 둔다 |
| 방장 권한 | 이양되지 않는다. 방장 이탈은 방 삭제다. 방장은 준비 상태를 갖지 않는다 |
| 시작 조건 | 방장을 제외한 참가자 전원 준비 완료. 준비 수·대상 수는 서버가 센다 |
| 반복 종료 | 동점 결선·재대결은 최대 3회이며 초과 시 방장이 고른다(F-PLAY-12). 종료가 보장되지 않는 반복 기능을 두지 않는다 |
| 중간 집계 비공개 | 진행 중에는 완료/대기 상태만 내려간다. **방장에게도 예외를 두지 않는다** |
| 익명 | 킹메이커 제출자·저격 지목자는 방장 설정이 공개일 때만, 그것도 개표 후에만 드러난다 |
| 데이터 수명 | 방이 사라지면 참가자·결과·시드가 함께 지워진다. 채팅은 서버에 저장하지 않는다 |
| 가벼움 | 로그인·회원가입·개인정보 수집 기능을 채번하지 않는다. 링크와 닉네임이 참여 절차의 전부다 |

## 에러 코드

각 도메인 파일의 에러 코드 절이 그 도메인에서 **실제로 발생하는** 코드를 등재한다. 네임스페이스가 다른 코드라도 그 동작이 일어나는 도메인 파일에 싣는다 — 예로 vote.self_not_allowed는 킹메이커·익명 저격에서 발생하므로 05_games.md에 있다. 형식은 {네임스페이스}.{snake_case} + HTTP 상태이며 네임스페이스는 **소문자**다.

| 네임스페이스 | 묶는 기준 | 주로 등장하는 도메인 |
|--------------|-----------|----------------------|
| room | 방 자체의 존재·상태·수명 | ROOM · LOBBY · CMN |
| member | 참가자 신원·프로필·권한 | ROOM · LOBBY · SETUP · CMN |
| game | 게임 설정·라운드·입력 마감 | SETUP · PLAY · 게임 6종 · RESULT |
| vote | 투표·지목의 규칙 위반 | KING · SNIPE |
| common | 인증·스키마·내부 오류 | 전 도메인 |

- 게임별 전용 네임스페이스를 두지 않는다. 게임 입력 오류는 game·vote로 채번하고 어느 게임에서 나는지는 코드가 아니라 설명이 밝힌다.
- **전수 등재와 최종 채번의 정본은 [../10_glossary/02_error_codes.md](../10_glossary/02_error_codes.md)다.** 본 폴더의 표는 도메인별 발생 지점을 보이는 파생 뷰이며, 두 문서가 어긋나면 사전이 우선한다. 코드 수를 본 폴더에서 확정하지 않는다.

## 구 스펙과의 관계

구 스펙(docs_legacy/features.md)의 기능 89건을 그대로 옮기지 않고 접두사 체계로 **재설계**했다. 재설계에서 한 일은 셋이다.

| 구분 | 내용 |
|------|------|
| 결번 제거 | 구 목록은 F-111이 빠진 결번이 있어 번호만으로 전수 등재를 확인할 수 없었다. 접두사별 01부터 연속 채번으로 바꿨다 |
| 누락 보강 | 아바타 선점 현황·프로필 확정과 변경 잠금·미확정 슬롯 회수·방 스냅샷·준비 현황 집계·설정값 서버 검증·게임별 설정 항목·반복 상한과 방장 선택·참가자 대기 안내·에러 문구 매핑·이벤트 순서 보장 등을 새로 등재했다 |
| 중복 통합 | 구 F-211(방 상태 조회)을 F-ROOM-05(초대 코드 검증 조회)로 합치는 등 같은 표면을 가리키던 항목을 하나로 모았다 |

폐기한 규칙도 있다. 구 스펙의 **동점 결선 상한 없음**(D-23)은 종료가 보장되지 않아 폐기하고 최대 3회 + 방장 선택으로 바꿨다(F-PLAY-12). 구 ID(F-1xx~F-6xx)는 재사용하지 않으며, **항목 단위 대응표는 [../03_requirements/11_traceability.md](../03_requirements/11_traceability.md)의 부록**에 둔다 — 신 ID 채번이 끝난 뒤 생성되는 파생 자료이므로 추적성 문서가 소유한다.

## 추적성

기능 ID를 추가·변경하면 **같은 변경 단위에서** 아래 축을 갱신한다.

- [../03_requirements/11_traceability.md](../03_requirements/11_traceability.md) — 요구사항 ↔ 기능 ID ↔ 화면 ↔ 테이블, 그리고 구 ID 대응표
- [../08_screen/02_traceability.md](../08_screen/02_traceability.md) — 기능 ID → 화면 코드(미매핑 0 보장). 같은 파일 끝의 화면별 담은 기능 수 표는 파생 집계이므로 함께 갱신한다
- 에러 코드 신설 시 [../10_glossary/02_error_codes.md](../10_glossary/02_error_codes.md) 등재
- 기능 수가 바뀌면 본 README의 접두사별 집계·우선순위 분포·구현 상태·레이어 분포 **네 표를 모두 다시 센다.** 파생 집계를 남겨 두면 정본과 조용히 갈라진다

**화면 없는 서버 전용 기능**(설명에 화면 없음으로 표기한 항목)은 화면 추적성에서 미매핑이 되므로, 08_screen의 미매핑 0 보장은 화면을 갖는 기능만을 대상으로 한다는 점을 그쪽 문서가 명시해야 한다.
