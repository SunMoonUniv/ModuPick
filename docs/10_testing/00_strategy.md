## 언제 채우나

**첫 기능 구현과 동시에** 작성한다. 나중에 붙이려고 미루면 안 붙는다.

## 무엇을 반드시 테스트해야 하는가

ModuPick은 **"모두에게 같은 결과가 보인다"가 제품의 핵심 약속**이다([`01_overview/00_product.md`](../01_overview/00_product.md)).
그 약속이 깨지는 지점이 곧 최우선 테스트 대상이다.

| 우선순위 | 대상 | 왜 |
|---|---|---|
| **최상** | 서버 결과 확정 → 클라이언트 애니메이션 일치 | [D-13](../DECISIONS.md#d-13). 어긋나면 사람마다 다른 당첨자를 본다 |
| **최상** | 킹메이커 익명성 — 제안자가 응답 어디에도 없는지 | [D-18](../DECISIONS.md#d-18). 한 번 새면 게임이 무의미해진다 |
| **최상** | 중복 입력 1회만 인정 (`STOP`·`UP`·투표) | 재전송·더블클릭으로 판정이 흔들리면 안 된다 |
| 높음 | 서버 수신 시각 기준 판정 | [D-14](../DECISIONS.md#d-14). 시간초·눈치의 공정성 근거 |
| 높음 | 정원 초과 차단 (`PENDING` 포함 합산) | [`06_api/01_rest.md`](../06_api/01_rest.md). 11번째 사람이 들어오면 안 된다 |
| 높음 | 아바타 · 닉네임 동시 선점 경합 | 늦게 확정한 쪽이 반드시 실패해야 한다 |
| 높음 | 방장 이탈 → 방 폭파 전파 | [D-05](../DECISIONS.md#d-05) |
| 중간 | 동점 → `TIE` phase → 재투표 | [D-11](../DECISIONS.md#d-11) |
| 중간 | 게임별 설정값 검증 (`INVALID_CONFIG`) | 사다리 결과 항목 > 참가자 수 등 |

## 테스트 종류별 범위

| 종류 | 범위 |
|---|---|
| 단위 | 오차 계산 · 동시 입력 판정 · 사다리 매칭 생성 · 코드 발급 충돌 |
| 통합 | REST 흐름 (방 생성 → 가입 → 프로필 확정 → 정원 초과) |
| **소켓** | **다중 클라이언트 동시 접속 시나리오.** 이게 가장 중요하고 가장 짜기 어렵다 |
| E2E | 방 생성부터 결과 PNG 저장까지 전 흐름 |

## ⚠️ 재접속 정책이 테스트 설계를 바꾼다

[D-04](../DECISIONS.md#d-04)가 미결이다.

- **기본안(재접속 없음)** — "새로고침하면 방에서 빠진다"를 **의도된 동작으로 검증**해야 한다
- **grace period 안** — 끊김 → 복귀 → 상태 복원 시나리오가 통째로 추가된다

같은 코드가 한쪽에서는 통과, 다른 쪽에서는 실패가 되므로 **결정 전에 소켓 테스트를 짜면 버린다.**

## 무엇을 쓸 것인가

- 테스트 프레임워크 선택과 근거 (pytest / Vitest / Playwright 등)
- 다중 클라이언트 소켓 테스트를 어떻게 구성하는가
- 커버리지 목표와 CI 게이트
- 테스트 데이터 — 더미 참가자 6인(지호·서연·민준·하늘·도윤·유진)을 재사용한다
