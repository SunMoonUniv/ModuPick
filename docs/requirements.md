## 1. 문서 읽는 법

### 1.1 스토리 형식

```
#### US-000 · 스토리 제목          ← 실제 번호가 아닌 서식 예시
**누구로서** 무엇을 하고 싶다. **왜냐하면** 어떤 이유 때문이다.

우선순위 `필수` · 출처 `근거 문서 §절`

- **Given** 어떤 상태에서
- **When** 무엇을 하면
- **Then** 무엇이 일어나야 하는가
- **But** 어떤 경우에는 막힌다
```

`Given/When/Then`은 **테스트가 그대로 받아쓸 수 있는 문장**으로 적는다. "잘 동작한다" 같은 판정 불가능한 표현은 쓰지 않는다.

### 1.2 ID 체계

| 접두어 | 범위 |
| --- | --- |
| `US-1xx` | 방 생성 · 코드 입장 · 프로필 설정 |
| `US-2xx` | 대기방 (참가자·채팅·준비·강퇴) |
| `US-3xx` | 게임 설정 · 시작 · 진행 공통 |
| `US-4xx` | 게임 6종 개별 (`US-41x` 룰렛 · `42x` 사다리 · `43x` 킹메이커 · `44x` 시간초 · `45x` 저격 · `46x` 눈치) |
| `US-5xx` | 결과 발표 · 저장 · 재시작 |
| `US-6xx` | 이탈 · 방 폭파 · 만료 · 예외 |
| `NFR-xx` | 비기능 요구사항 |
| `D-xx` | 확정된 설계 결정 |
| `Q-xx` | 미확정 항목 |

**ID는 재사용하지 않는다.** 스토리가 폐기되면 번호를 비워 두고 다음 번호를 쓴다.

### 1.3 우선순위

| 값 | 뜻 |
| --- | --- |
| `필수` | 없으면 제품이 성립하지 않는다. MVP 릴리스 차단 요건 |
| `권장` | MVP 품질을 좌우하지만, 없어도 흐름은 끝까지 돈다 |
| `선택` | 여유가 있으면 넣는다. 일정 압박 시 가장 먼저 뒤로 미룬다 |

### 1.4 다른 문서와의 관계

| 문서 | 이 문서와의 관계 |
| --- | --- |
| **Notion 화면설계서** | **화면 단위 규격의 정본.** 화면마다 UI 요소·진행 순서·예외 처리·기획 근거가 정리돼 있다. 로컬 문서와 어긋나면 Notion이 우선한다 ([§9.3](#93-정본-우선순위)) |
| [`features.md`](features.md) | **같은 내용을 시스템 관점으로 뒤집은 문서.** 이 문서가 *사용자가 무엇을 하고 싶은가*라면, 저쪽은 *그러려면 무엇을 만들어야 하는가*다. 기능 `F-1xx`는 스토리 `US-1xx`와 번호대가 대응한다 |
| `draft_plan.md` | 기획 의도와 기능 목록의 **출처**(요약본). 이 문서는 그것을 검증 가능한 문장으로 옮긴 것이다 |
| `games.md` | 게임 6종의 **상세 판정 규칙**. §4.4는 사용자 관점만 다루고 세부 규칙은 `games.md`를 따른다 |
| `api.md` | REST·소켓 **인터페이스 계약**. 수용 기준의 에러 코드는 `api.md`의 에러 코드 표를 그대로 쓴다 |
| `techstack.md` | 기술 선택과 근거. §5 비기능 요구사항의 전제 |

## 2. 제품 개요와 범위

### 2.1 해결하려는 문제

조별 과제·스터디·사내 TF의 첫 회의마다 "팀장 누가 할래요?"에서 정적이 흐른다. 서로 원하거나 해야 함을 알면서도 먼저 나서지 못하고 눈치만 보는 상황(Mamihlapinatapai)에서 **시간과 감정이 소모된다.**

ModuPick은 그 결정을 **운에 맡기되 모두가 같은 화면을 보게** 해서, 결과에 대한 뒷말과 눈치를 없앤다.

### 2.2 핵심 가치

| 가치 | 요구사항으로의 번역 |
| --- | --- |
| 무지연 실시간 동기화 | 모든 참가자가 같은 순간에 같은 화면을 본다 → [NFR-01](#nfr-01--실시간-반영-지연), [US-306](#us-306--동시-화면-전환) |
| 진입 장벽 제로 | 로그인·설치 없이 코드 6자리로 입장 → [US-103](#us-103--초대-코드로-입장) |
| 결과의 공정성 | 결과는 서버가 정하고 클라이언트는 재생만 한다 → [D-01](#7-확정된-설계-결정), [NFR-05](#nfr-05--결과-무결성) |
| 아이스브레이킹 | 게임 자체가 팀 빌딩이 된다 → [§4.4](#44-게임별-요구사항-us-4xx) |

### 2.3 MVP 범위

**포함한다**

- 방 생성 · 초대 코드 입장 · 프로필 설정
- 실시간 대기방 (참가자 목록 · 채팅 · 준비 상태 · 강퇴)
- 미니게임 6종: 운명의 룰렛 · 랜덤 사다리 · 킹메이커 · 시간초 잡기 · 익명 저격 · 눈치게임
- 결과 발표 화면 · 결과 저장(PNG)
- 다시 하기 · 대기방 복귀

**포함하지 않는다**

| 제외 항목 | 사유 |
| --- | --- |
| 회원가입 · 로그인 · 계정 | 진입 장벽 최소화가 핵심 가치. 게스트 토큰만 사용한다 |
| 게임 기록 영구 보관 · 통계 | 방이 사라지면 데이터도 사라진다 ([NFR-08](#nfr-08--데이터-보존-정책)) |
| Slack App 연동 (`/modupick`) | `draft_plan.md §4`의 확장 계획. MVP 이후 |
| 재접속 · 세션 복구 | 소켓이 끊기면 퇴장으로 간주한다 ([D-11](#7-확정된-설계-결정)) |
| 관전 모드 · 게임 중 입장 | 게임 시작 시점에 참가자를 고정한다 ([US-305](#us-305--참가자-고정)) |
| 결정 축 선택(주제/역할/팀장 구분) | 게임을 "무엇을 정하는 데" 쓸지 고르는 축. 디자인에는 반영됐으나 구현은 MVP 이후 ([D-33](#7-확정된-설계-결정)) |
| 모바일·태블릿 레이아웃 | 시안 24개가 모두 1920×1080 데스크톱 전용. 데스크톱으로 먼저 완성하고 이후 단계에서 대응한다 ([D-17](#7-확정된-설계-결정)) |

### 2.4 사용자 역할

| 역할 | 정의 | 권한 |
| --- | --- | --- |
| **방장(Host)** | 방을 만든 사람. 방마다 정확히 1명 | 게임 선택·설정·시작, 강퇴, 다시 하기, 대기방 복귀 |
| **참여자(Guest)** | 초대 코드로 들어온 사람. 최대 9명 | 준비 완료 토글, 채팅, 게임 입력, 결과 저장 |

**방장 권한은 이양되지 않는다.** 방장이 나가면 방이 사라진다([US-601](#us-601--방장-이탈-시-방-폭파)).

## 3. 용어 정의

| 용어 | 뜻 |
| --- | --- |
| **방(Room)** | 초대 코드로 식별되는 참가자 그룹. 생성부터 폭파까지가 생명주기 |
| **초대 코드** | 방을 가리키는 6자리 숫자. 표시는 `MODU-427132`, API 경로에는 `427132`만 쓴다 |
| **라운드(Round)** | 게임 한 판. `다시 하기`를 누르면 새 `roundId`가 발급된다 |
| **phase** | 라운드의 진행 단계. `READY` → `PLAYING` → (`TIE`) → `RESULT` |
| **PENDING / ACTIVE** | 멤버 상태. 가입만 한 상태가 `PENDING`, 프로필을 확정해 다른 사람 화면에 보이는 상태가 `ACTIVE` |
| **선점(아바타)** | 같은 방에서 한 아바타를 한 사람만 쓸 수 있게 하는 규칙 |
| **가이드 팝업** | 게임 시작 직후 3초간 강제 노출되는 규칙 설명 창 |
| **동시 입력 판정** | 눈치게임에서 두 명 이상의 클릭 간격이 설정값(기본 0.3초) 안일 때 내리는 판정 |

## 4. 사용자 스토리 — 기능 요구사항

### 4.1 방 생성과 입장 (US-1xx)

#### US-101 · 방 만들기

**방장으로서** 방 제목과 최대 인원을 정해 방을 만들고 싶다. **왜냐하면** 팀 규모에 맞는 자리를 먼저 확보해야 하기 때문이다.

우선순위 `필수` · 출처 `draft_plan.md §2①` · `api.md POST /api/rooms`

- **Given** 표지 화면에 있고
- **When** `새 방 만들기`를 눌러 방 이름(1~30자)과 최대 인원(2~10명, **기본값 8명**)을 정하고 `방 만들기`를 누르면
- **Then** 서버가 6자리 숫자 초대 코드를 발급하고 프로필 설정 화면으로 이동한다
- **And** 방장 자신의 멤버 레코드가 `PENDING` 상태로 함께 생성되고 `hostToken`을 받는다
- **And** 입력하는 동안 미리보기 카드에 방 이름·최대 인원·발급될 코드 자리가 실시간으로 반영된다
- **But** 방 이름이 비어 있으면 `방 만들기` 버튼이 **비활성**이라 누를 수 없다
- **But** 30자에 도달하면 **추가 입력 자체가 막힌다.** 잘라내거나 제출 시점에 거부하지 않는다
- **And** 최대 인원은 스테퍼 · 빠른 선택 칩(2/4/6/8/10) · 슬라이더 세 컨트롤이 항상 같은 값을 가리키고, 경계(2·10)에서 해당 방향 버튼이 비활성된다
- **And** 초대 코드는 **서버가 발급**하며 방장이 직접 정할 수 없다. 코드 입력 필드 자체를 두지 않는다
- **And** 최대 인원은 방 생성 시점에 확정되며 **대기방에서 바꿀 수 없다**

#### US-102 · 초대 코드 공유

**방장으로서** 초대 코드를 한 번에 복사하고 싶다. **왜냐하면** 카톡·디스코드에 바로 붙여넣어야 하기 때문이다.

우선순위 `필수` · 출처 `draft_plan.md §3-1`

- **Given** 방이 만들어져 초대 코드가 보이는 상태에서
- **When** 대기방 헤더의 방 코드 뱃지를 누르면
- **Then** 코드가 클립보드에 복사되고 완료 토스트가 뜬다

#### US-103 · 초대 코드로 입장

**참여자로서** 로그인 없이 코드만으로 들어가고 싶다. **왜냐하면** 가입 절차에서 이탈하고 싶지 않기 때문이다.

우선순위 `필수` · 출처 `draft_plan.md §2①` · `api.md GET /api/rooms/{code}`

- **Given** 표지 화면에서
- **When** `MODU-` 뒤 6자리 숫자를 입력하면
- **Then** 6자리가 채워지는 즉시 `참여` 버튼이 활성된다. 그 전까지는 비활성이다
- **And** `MODU-` 접두어는 고정 표기라 입력 대상이 아니다
- **When** `참여`를 누르면
- **Then** 코드가 검증되고 프로필 설정 화면으로 이동한다
- **And** 슬롯이 선점되며 `guestToken`을 받는다
- **But** 없는 코드면 `ROOM_NOT_FOUND` — 입력 필드 **하단에 인라인 에러**로 "방을 찾을 수 없어요"가 뜨고 표지에 머문다
- **But** 정원이 찼으면 `ROOM_FULL` — 같은 방식으로 "인원이 가득 찼어요"가 뜬다
- **But** 이미 게임 중인 방이면 `ROOM_ALREADY_PLAYING` — 배경을 흐린 모달로 `이미 진행중인 방입니다` / `잠시 후 다시 시도해 주세요`를 띄운다
- **And** 모달은 `✕` · 배경 클릭 · `ESC` 중 아무 방법으로나 닫을 수 있고, **액션 버튼은 두지 않는다**
- **And** 닫아도 **입력한 코드는 지워지지 않는다.** 방이 대기 상태로 돌아오면 같은 코드로 다시 시도할 수 있다

> **정원 계산**: `PENDING`(프로필 입력 중) + `ACTIVE`(입장 완료)를 합산한다. 프로필을 아직 안 채운 사람도 한 자리를 차지한다.
>
> **다만 `PENDING`은 3분까지만 자리를 잡고 있는다**([D-43](#7-확정된-설계-결정)). 프로필 화면은 소켓 연결 **전** 단계라 창을 닫아도 서버가 알 수 없기 때문에, 가입 후 3분 안에 프로필을 확정하지 않으면 서버가 슬롯을 회수한다. 회수된 뒤 `대기방 입장하기`를 누르면 `SESSION_EXPIRED`로 거부되고 표지로 돌아간다.

#### US-104 · 닉네임 정하기

**참여자로서** 팀원이 알아볼 닉네임을 쓰고 싶다. **왜냐하면** 게임 결과가 누구를 가리키는지 바로 알아야 하기 때문이다.

우선순위 `필수` · 출처 `draft_plan.md §2①` · `api.md PATCH /members/me`

- **Given** 프로필 설정 화면에서
- **When** 닉네임을 1~8자로 입력하면
- **Then** 글자 수가 `5 / 8` 형태로 실시간 표시되고 미리보기 카드의 이름이 함께 갱신된다
- **But** 8자에 도달하면 **추가 입력 자체가 막힌다**(`NICKNAME_INVALID`는 API 방어용)
- **But** 같은 방에 동일 닉네임이 있으면 `NICKNAME_DUPLICATED` — 입력 필드가 에러 상태(테두리 강조 + 안내 문구)가 되고 입장할 수 없다
- **But** 비어 있으면 입장 버튼이 비활성이라 진행할 수 없다

#### US-105 · 캐릭터 선택

**참여자로서** 남들과 겹치지 않는 캐릭터를 고르고 싶다. **왜냐하면** 게임 화면에서 나를 즉시 찾아야 하기 때문이다.

우선순위 `필수` · 출처 `api.md GET /avatars` · 디자인 시안(프로필 화면)

- **Given** 프로필 설정 화면에서
- **When** 캐릭터 목록을 보면
- **Then** 이미 선점된 캐릭터는 회색 배경 + 점선 테두리에 `🔒 ○○ 선택` 라벨이 붙고 **클릭도 포커스도 되지 않는다**
- **And** 좌우 화살표로 페이지를 넘길 수 있고, 페이지를 이동해도 내 선택 상태는 유지된다
- **When** 타일을 클릭하면
- **Then** `★ 내 캐릭터` 표시가 붙고 좌측 미리보기 카드에 즉시 반영된다
- **And** 다른 타일을 클릭하면 선택이 그쪽으로 옮겨간다
- **When** `🎲 랜덤 뽑기`를 누르면
- **Then** 선점되지 않은 캐릭터 중 하나가 무작위로 선택된다
- **When** 내가 보고 있는 동안 다른 사람이 어떤 캐릭터를 확정하면
- **Then** 해당 타일이 **실시간으로 잠금 처리**된다
- **But** 선택 후 입장하는 순간 다른 사람이 먼저 확정했으면 `AVATAR_TAKEN`이 뜨고 목록이 갱신된다

> 아바타 선점은 **클릭 시점이 아니라 입장 확정 시점**에 결정된다. 동시 클릭은 늦게 제출한 쪽이 걸러진다.
> 캐릭터는 **30종**이며 직접 제작한 동물 그림을 쓴다 — **이모지를 대체물로 쓰지 않는다**([D-15](#7-확정된-설계-결정)).

#### US-106 · 한 줄 소개

**참여자로서** GitHub 아이디 같은 소개를 남기고 싶다. **왜냐하면** 처음 만난 팀원에게 나를 알리는 데 도움이 되기 때문이다.

우선순위 `선택` · 출처 `draft_plan.md §2①`

- **Given** 프로필 설정 화면에서
- **When** 한 줄 소개를 **최대 20자**로 입력하면([D-42](#7-확정된-설계-결정))
- **Then** 미리보기 카드와 대기방 참가자 카드에 `@handle · 역할` 형태로 표시된다
- **But** 20자에 도달하면 **추가 입력 자체가 막힌다**
- **And** 비워 두어도 입장할 수 있다

#### US-107 · 대기방 입장

**참여자로서** 프로필을 확정하고 대기방에 들어가고 싶다.

우선순위 `필수` · 출처 `api.md PATCH /members/me`

- **Given** 프로필 설정 화면에서
- **When** 닉네임과 캐릭터 중 하나라도 비어 있으면
- **Then** `대기방 입장하기` 버튼이 **비활성**이다. 둘 다 충족해야 활성된다
- **When** 활성된 버튼을 누르면
- **Then** 멤버 상태가 `ACTIVE`로 바뀌고 대기방 화면으로 이동한다
- **And** 기존 참가자 전원의 화면에 내 카드가 즉시 나타난다
- **And** 채팅창에 입장 시스템 메시지가 표시된다
- **And** 입장 전 화면에는 내가 몇 번째 참가자인지가 배지로 표시된다 (`오늘의 6번째 참가자!`)

#### US-108 · 게임 소개 둘러보기

**처음 온 사람으로서** 어떤 게임이 있는지 먼저 보고 싶다. **왜냐하면** 이 서비스로 뭘 할 수 있는지 알아야 방을 만들 마음이 생기기 때문이다.

우선순위 `권장` · 출처 디자인 시안(표지 규격 · 게임 슬라이드)

- **Given** 표지 화면에 있고
- **When** 게임 슬라이드를 보면
- **Then** 게임 6종이 아이콘 · 게임명 · 한 줄 부제 형태로 가로 무한 스크롤된다
- **When** 카드를 클릭하면
- **Then** 우측 데모 영역의 시연 영상이 **해당 게임으로 교체**된다
- **But** 이것은 소개용 시연일 뿐 **실제 게임 선택이 아니다.** 게임 선택은 대기방에서 방장만 한다

#### US-109 · 룰렛 데모 미리보기

**처음 온 사람으로서** 게임이 어떻게 굴러가는지 맛보고 싶다.

우선순위 `선택` · 출처 디자인 시안(표지 규격 · 데모 패널)

- **Given** 표지 화면에 있고
- **When** 데모 패널을 보면
- **Then** 기본값인 운명의 룰렛 시연 영상이 재생바와 함께 자동 재생된다
- **And** 함께 보이는 참가자 목록은 **시연용 더미 데이터**이며 실제 접속자가 아니다
- **And** 데모는 실제 방과 무관하며 결과가 어디에도 기록되지 않는다

### 4.2 대기방 (US-2xx)

#### US-201 · 참가자 목록 실시간 반영

**참여자로서** 누가 들어오고 나갔는지 바로 보고 싶다. **왜냐하면** 다 모였는지 알아야 시작할 수 있기 때문이다.

우선순위 `필수` · 출처 `draft_plan.md §2①` · `api.md member:joined / member:left`

- **Given** 대기방에 있고
- **When** 다른 사람이 입장하거나 퇴장하면
- **Then** 별도 새로고침 없이 참가자 카드가 추가·제거된다
- **And** 인원이 `현재 N명 / 최대 M명` 형태로 갱신된다
- **And** 각 카드에는 아바타 · 닉네임 · 한 줄 소개와 함께 상태 배지가 붙는다 (`👑 방장` / `✓ READY` / `준비 중`)
- **And** 내 카드에는 `나` 배지가 붙어 구분된다
- **And** 아직 차지 않은 자리는 `빈 자리 N · 초대 링크로 참여 대기` 플레이스홀더로 보이고, **정원이 다 차면 사라진다**

#### US-202 · 대기방 채팅

**참여자로서** 게임 전에 대화하고 싶다. **왜냐하면** 어색함을 풀고 진행을 맞춰야 하기 때문이다.

우선순위 `필수` · 출처 `draft_plan.md §2①`

- **Given** 대기방에 있고
- **When** 메시지를 입력하고 `Enter`를 누르면 (**글자 수 제한 없음** — `S-04H`)
- **Then** 같은 방 전원의 채팅창에 동일한 순서로 표시된다
- **And** 내 메시지는 오른쪽, 남의 메시지는 왼쪽, 시스템 메시지는 가운데 정렬된다
- **But** 공백만 입력하면 전송되지 않는다

#### US-203 · 채팅 이력 유지

**참여자로서** 게임이 끝나고 돌아와도 아까 대화를 보고 싶다. **왜냐하면** 대화 맥락이 끊기면 다시 설명해야 하기 때문이다.

우선순위 `권장` · 출처 `draft_plan.md §2① 채팅 DB`

- **Given** 대기방에서 채팅한 뒤 게임을 하고 대기방으로 돌아왔을 때
- **When** 채팅창을 보면
- **Then** 게임 전 대화가 그대로 남아 있다
- **And** 채팅 내용은 서버 DB에 영구 저장되지 않는다

> 채팅은 브라우저 로컬 스토리지에 보관한다. 스크롤을 올려 과거 메시지를 더 불러오는 기능은 제공하지 않는다([D-09](#7-확정된-설계-결정)).

#### US-204 · 입력 중 표시

**참여자로서** 누가 지금 타이핑 중인지 보고 싶다.

우선순위 `선택` · 출처 `api.md chat:typing`

- **Given** 대기방에 있고
- **When** 다른 사람이 채팅 입력을 시작하면
- **Then** 채팅창에 `●●●` 표시가 나타난다
- **And** 일정 시간 갱신이 없으면 자동으로 사라진다 (기본 3초 · 정확한 값은 개발 재량)

#### US-205 · 준비 완료

**참여자로서** 준비됐음을 알리고 싶다. **왜냐하면** 방장이 시작 시점을 판단해야 하기 때문이다.

우선순위 `필수` · 출처 `api.md member:ready`

- **Given** 대기방에 있고
- **When** `준비 완료`를 누르면
- **Then** 전원 화면의 `READY n/m` 카운터가 갱신된다
- **And** 분모 `m`은 **방장을 제외한 참여자 수**다([D-22](#7-확정된-설계-결정))
- **And** 내 참가자 카드의 배지가 `✓ READY`로 바뀐다
- **When** 다시 누르면
- **Then** 준비 상태가 해제되고 카운터가 되돌아간다
- **And** 방장은 **항시 준비 상태**로 취급되어 이 버튼이 보이지 않는다
- **And** 하단 밴드는 역할에 따라 다르다 — 참여자는 `[← 나가기] [✓ 준비 완료]`, 방장은 `[🎲 랜덤 게임] [▶ 게임 시작]`

#### US-206 · 참가자 강퇴

**방장으로서** 원치 않는 참가자를 내보내고 싶다. **왜냐하면** 잘못 들어온 사람이나 방해 행위를 막아야 하기 때문이다.

우선순위 `권장` · 출처 `draft_plan.md §2① 인원 관리`

- **Given** 방장이 대기방에 있고
- **When** 참가자 카드의 강퇴 버튼을 누르면
- **Then** **확인 모달**이 먼저 뜬다. 여기서 취소하면 아무 일도 일어나지 않는다
- **And** 강퇴 버튼은 방장 화면에서만 보인다
- **When** 모달에서 강퇴를 확정하면
- **Then** 대상자는 방에서 제거되고 표지 화면으로 이동한다
- **And** 대상자에게 `방장이 퇴장시켰어요` 토스트가 표시된다
- **And** 나머지 전원의 참가자 목록에서 해당 카드가 사라지고 채팅창에 시스템 메시지가 남는다
- **But** 방장 자신을 강퇴할 수 없다
- **But** 참여자가 강퇴를 시도하면 `NOT_HOST`로 거부된다

#### US-207 · 대기방 나가기

**참여자로서** 원할 때 방을 떠나고 싶다.

우선순위 `필수` · 출처 `api.md DELETE /members/me`

- **Given** 대기방에 있고
- **When** `나가기`를 누르면
- **Then** 표지 화면으로 이동하고 나머지 참가자 목록에서 내가 사라진다
- **And** 채팅창에 퇴장 시스템 메시지가 표시된다

### 4.3 게임 설정과 진행 공통 (US-3xx)

#### US-301 · 게임 선택

**방장으로서** 6종 중 하나를 고르고 싶다.

우선순위 `필수` · 출처 `draft_plan.md §2②` · `api.md game:select`

- **Given** 방장이 대기방에 있고
- **When** 게임 카드 하나를 선택하면
- **Then** 선택된 카드에 선택 표시가 붙고 아래 설정 패널이 그 게임의 것으로 즉시 교체된다
- **And** 참여자 전원의 화면에도 선택된 게임이 즉시 표시된다
- **And** 채팅창에 `🎮 방장이 '운명의 룰렛'을 골랐어요` 같은 시스템 메시지가 남는다
- **And** 게임을 바꾸면 **이전 게임의 설정값은 버려지고** 새 패널의 기본값으로 초기화된다
- **But** 현재 인원이 그 게임의 최소 인원에 못 미치면 카드가 비활성화되고 `3명부터 가능` 같은 사유가 함께 표시된다([D-25](#7-확정된-설계-결정))

#### US-302 · 랜덤 게임 뽑기

**방장으로서** 게임을 고르는 것조차 운에 맡기고 싶다.

우선순위 `선택` · 출처 `draft_plan.md §2①` · `api.md game:random`

- **Given** 방장이 대기방에 있고
- **When** `랜덤`을 누르면
- **Then** 서버가 **현재 인원으로 시작 가능한 게임 중에서** 하나를 무작위로 골라 전원에게 동일하게 표시하고, 설정 패널도 함께 교체한다
- **And** 방장 화면과 참여자 화면의 결과가 항상 일치한다
- **But** 시작 가능한 게임이 하나도 없으면 뽑기가 실행되지 않는다

#### US-303 · 게임 설정 실시간 공유

**참여자로서** 방장이 무슨 설정을 하는지 보고 싶다. **왜냐하면** 어떤 규칙으로 하는지 미리 알아야 하기 때문이다.

우선순위 `필수` · 출처 `draft_plan.md §2① 게임 선택/설정`

- **Given** 방장이 게임을 선택한 상태에서
- **When** 방장이 설정값을 바꾸면
- **Then** 참여자 화면의 설정 패널이 같은 값으로 즉시 갱신된다
- **And** 참여자 화면의 게임 카드와 설정 패널은 **모든 컨트롤이 disabled**되고 잠금 표시와 `방장만 변경 가능` 배지가 붙는다
- **And** 조작을 시도하면 `방장만 변경 가능` 툴팁이 뜬다
- **And** 참여자 상태 문구는 `방장이 시작하기를 기다리는 중`으로 표시된다
- **But** 참여자가 설정 변경을 시도하면 `NOT_HOST`로 거부된다
- **But** 설정값이 허용 범위를 벗어나면 `INVALID_CONFIG`로 거부되고 이전 값이 유지된다

#### US-304 · 게임 시작

**방장으로서** 전원이 준비됐을 때 게임을 시작하고 싶다.

우선순위 `필수` · 출처 `games.md §1.2` · `api.md game:start`

- **Given** 방장이 게임과 설정을 마쳤고
- **When** 시작 조건(최소 인원 · 게임 선택 · **참여자 전원 READY**)을 하나라도 못 채우면
- **Then** `게임 시작` 버튼이 비활성이고, 무엇이 모자란지 상태 문구로 안내된다 (`READY k/N`)
- **When** 조건을 모두 채운 뒤 `게임 시작`을 누르면
- **Then** 새 라운드가 생성되고 전원 화면이 게임 화면으로 전환된다
- **And** 방 상태가 `PLAYING`으로 바뀌어 이후 입장 시도는 `ROOM_ALREADY_PLAYING`으로 막힌다
- **But** 참가자가 그 게임의 최소 인원(룰렛·사다리·시간초·눈치는 2명, 킹메이커·익명 저격은 3명)에 못 미치면 `NOT_ENOUGH_MEMBERS`로 거부된다([D-25](#7-확정된-설계-결정))
- **But** 참여자 중 준비 완료가 아닌 사람이 있으면 시작할 수 없다
- **But** 설정값이 유효하지 않으면 `INVALID_CONFIG`로 거부된다

> 정원이 다 차지 않아도 **참여자 전원이 준비 완료**면 시작할 수 있다(`games.md §1.1`).

#### US-305 · 참가자 고정

**참여자로서** 게임 도중 인원이 바뀌어 결과가 흔들리지 않기를 바란다.

우선순위 `필수` · 출처 `games.md §1.1`

- **Given** 게임이 시작되었을 때
- **When** 진행 중 누군가 퇴장하거나 연결이 끊겨도
- **Then** 해당 라운드의 후보 목록과 판정 대상은 시작 시점 명단 그대로 유지된다
- **And** 게임 중인 방에는 새 참가자가 들어올 수 없다

#### US-306 · 동시 화면 전환

**참여자로서** 나만 늦게 화면이 바뀌지 않기를 바란다. **왜냐하면** 시작 타이밍 차이가 곧 유불리가 되기 때문이다.

우선순위 `필수` · 출처 `draft_plan.md 핵심 가치` · `games.md §1.3`

- **Given** 방장이 게임을 시작했을 때
- **When** 전원의 화면을 비교하면
- **Then** 모두 같은 게임 화면으로 전환되어 있다
- **And** 타이머가 있는 게임은 서버 기준 시각으로 동시에 시작한다

#### US-307 · 게임 가이드 강제 노출

**참여자로서** 처음 보는 게임의 규칙을 알고 시작하고 싶다.

우선순위 `필수` · 출처 `games.md §1.2`

- **Given** 게임이 시작되면
- **When** 게임 화면이 열리는 순간
- **Then** 배경을 흐린 가이드 모달이 3초간 표시된다
- **And** 한 줄 요약 · `STEP 1~3` · TIP 순으로 규칙을 안내한다
- **And** 3초가 지나면 자동으로 닫히고 서버 기준으로 게임이 시작된다
- **When** `알겠어요, 시작!` 또는 `✕`로 먼저 닫으면
- **Then** 모달만 사라지고 **게임 시작 시각은 앞당겨지지 않는다** (서버 기준이라 전원이 같은 순간에 시작한다)
- **And** 가이드가 떠 있는 3초 동안 배경의 게임 화면은 대기 상태로 유지된다
- **But** **동점 재대결 · 전원 탈락 후 재시작 · `다시 하기`로 재시작한 경우에는 가이드를 표시하지 않는다**([D-34](#7-확정된-설계-결정))

#### US-308 · 가이드 다시 보기

**참여자로서** 게임 중에도 규칙을 다시 확인하고 싶다.

우선순위 `권장` · 출처 `games.md §1.2-7`

- **Given** 게임 진행 화면에 있고
- **When** `?` 버튼을 누르면
- **Then** 같은 가이드 내용이 다시 표시되고 **게임은 멈추지 않는다** (실시간 게임이라 일시정지가 없다)
- **And** 모달 하단의 `이 게임 가이드 다시 보지 않기`를 체크하면 **그 게임에 한해** 자동 노출이 억제된다 (브라우저 로컬에 저장)
- **And** 처음 들어온 사람에게는 `?` 버튼 옆에 코치마크가 3초간 떴다가 사라진다

#### US-309 · 중복 입력 방지

**참여자로서** 버튼을 두 번 눌러 결과가 꼬이지 않기를 바란다.

우선순위 `필수` · 출처 `games.md §1.3`

- **Given** 1회 제한 액션(STOP·UP·투표·의견 제출)을 이미 제출했고
- **When** 같은 액션을 다시 보내면
- **Then** `ALREADY_SUBMITTED`로 거부되고 최초 입력만 인정된다
- **And** 네트워크 재전송으로 같은 요청이 중복 도착해도 한 번만 처리된다

#### US-310 · 마감 후 입력 무시

**참여자로서** 늦게 도착한 입력이 결과를 뒤집지 않기를 바란다.

우선순위 `필수` · 출처 `games.md §1.3`

- **Given** 라운드가 이미 종료되었고
- **When** 그 라운드로 향하는 입력이 서버에 도착하면
- **Then** `ROUND_ALREADY_ENDED`로 거부되고 판정에 반영되지 않는다

#### US-311 · 중간 집계 익명성

**참여자로서** 투표 중간에 누가 누구를 찍었는지 새어나가지 않기를 바란다. **왜냐하면** 익명이 아니면 솔직하게 못 찍기 때문이다.

우선순위 `필수` · 출처 `games.md §4 판정 규칙` · `api.md game:progress`

- **Given** 킹메이커 또는 익명 저격이 진행 중이고
- **When** 중간 진행 상황이 전달되면
- **Then** **누가 무엇을 선택했는지는 어떤 경로로도 전달되지 않는다**
- **And** 킹메이커는 `4 / 6 투표` 진행률과 함께 **후보별 득표수·순위를 실시간으로 보여 준다** — 감추는 것은 투표자이지 득표 집계가 아니다
- **And** 익명 저격은 `N / 6 발사` 진행률만 보여 주고 **피격 수는 마감 후에 공개**한다
- **And** 킹메이커 화면에는 `제출자도 투표자도 비공개` 고지가 상시 표시된다

### 4.4 게임별 요구사항 (US-4xx)

> 판정 규칙의 정본은 `games.md`다. 여기서는 **사용자가 화면에서 무엇을 하고 무엇을 보는가**만 규정한다.

#### US-411 · 운명의 룰렛 — 한 명 뽑기

**방장으로서** 팀장·발표자 한 명을 무작위로 뽑고 싶다.

우선순위 `필수` · 출처 `games.md §2`

- **Given** 룰렛 게임이 시작되었고
- **When** 화면을 보면
- **Then** 참가자 전원이 동일한 크기의 룰렛 조각으로 배치되어 있다
- **And** 모든 조각의 당첨 확률이 같다 (6명이면 각 16.7%)
- **When** 방장이 뽑기 버튼을 누르면
- **Then** 전원 화면에서 동일한 회전 애니메이션이 재생된다
- **And** 회전은 **3~5초** 이어지고, 멈추는 각도는 서버가 미리 확정한 값이다. 클라이언트가 난수를 만들지 않는다
- **And** 회전 중에는 모든 조작이 차단되고 `?` 가이드만 열어볼 수 있다 (가이드를 열어도 게임은 멈추지 않는다)
- **And** 회전 중 서버 기준 카운트다운 `3 → 2 → 1`이 표시된다
- **But** 뽑기 버튼을 두 번 눌러도 최초 1회만 인정된다
- **And** 참여자에게는 버튼이 비활성으로 보이고 대기 문구가 표시된다
- **And** 한 라운드에 추첨은 **한 번만** 한다. 여러 명을 연속으로 뽑지 않는다([D-24](#7-확정된-설계-결정))
- **And** 결과 화면에는 당첨자와 함께 방장이 설정한 **결과 항목**도 표시된다
- **And** 애니메이션 도중 참가자가 나가도 룰렛 조각과 결과는 그대로 유지되고, 우측 참가자 목록에만 오프라인으로 표시된다

#### US-412 · 룰렛 결과 항목 설정

**방장으로서** 무엇을 뽑는 룰렛인지 적어 두고 싶다.

우선순위 `권장` · 출처 `games.md §2.2`

- **Given** 룰렛을 선택한 상태에서
- **When** `무엇을 정할까`에 문구(예: `팀장`)를 입력하면
- **Then** 게임 화면 상단에 `팀장을 뽑습니다`, 결과 화면에 `팀장 — 지호` 형태로 표시된다
- **And** 이 값은 **표시용 라벨일 뿐**이며 추첨 횟수나 당첨 결과에 영향을 주지 않는다([D-24](#7-확정된-설계-결정))

#### US-421 · 랜덤 사다리 — 역할 한 번에 배분

**방장으로서** 여러 역할을 한 번에 나누고 싶다. **왜냐하면** 한 명씩 뽑으면 시간이 오래 걸리기 때문이다.

우선순위 `필수` · 출처 `games.md §3`

- **Given** 사다리 게임이 시작되었고
- **When** 화면을 보면
- **Then** 상단에 참가자, 하단에 방장이 입력한 역할이 배치되어 있다
- **And** 참가자마다 고유색이 부여되고 세로선이 그 색을 따른다
- **When** 방장이 진행 방식을 고르면 — 참가자 노드를 클릭해 **그 사람 경로만 개별 실행**하거나, `동시 시작`으로 **전원을 한꺼번에** 출발시킨다
- **Then** 서버 시작 시각을 기준으로 경로 추적이 시작된다
- **And** 참가자는 노드를 클릭할 수 없다. 진행 조작은 방장 전용이다
- **But** 시작 버튼을 두 번 눌러도 최초 1회만 인정된다
- **And** 추적 중에는 조작이 차단되고 `?` 가이드만 열어볼 수 있다
- **And** 경로가 끝난 참가자부터 매칭 현황이 순차로 확정된다 (확정 전은 회색, 확정 후는 강조 표시)
- **Then** 각 참가자의 경로가 애니메이션으로 표시되고 최종 `참가자 → 역할` 연결이 공개된다
- **And** 화면 크기나 기기가 달라도 최종 배정 결과는 모두 동일하다
- **And** 참가자는 출발 위치(레인)를 직접 고르지 않는다. 사다리 구조와 참가자 배치를 모두 서버가 정한다([D-16](#7-확정된-설계-결정))

#### US-422 · 사다리 결과 항목 설정

**방장으로서** 나눌 역할을 직접 적고 싶다.

우선순위 `필수` · 출처 `games.md §3.2`

- **Given** 사다리를 선택한 상태에서
- **When** 역할 항목을 입력하면
- **Then** 항목은 **최소 1개, 최대 참가자 수**까지 넣을 수 있다
- **But** 항목 수가 참가자 수를 넘으면 `INVALID_CONFIG`로 시작할 수 없다
- **And** 항목이 참가자 수보다 적으면 남는 자리는 `X`로 표시되고, 그 자리에 도착한 참가자는 **배정 없음**으로 처리된다
- **And** 같은 항목을 **여러 번 넣을 수 있다**([D-48](#7-확정된-설계-결정)). `자료조사`가 두 자리면 두 명이 같은 역할을 맡는다
- **And** 결과 화면에서는 그 참가자의 역할 자리가 **빈 배지**로 남는다

#### US-423 · 사다리 진행 속도

**방장으로서** 긴장감을 조절하고 싶다.

우선순위 `선택` · 출처 `games.md §3.3`

- **Given** 사다리를 선택한 상태에서
- **When** 진행 속도를 `빠르게 / 보통 / 느리게` 중 고르면
- **Then** 경로 애니메이션의 길이가 그에 맞게 달라진다
- **And** 속도와 무관하게 배정 결과는 동일하다

#### US-431 · 킹메이커 — 익명 의견 제출

**참여자로서** 팀명 아이디어를 눈치 보지 않고 내고 싶다.

우선순위 `필수` · 출처 `games.md §4`

- **Given** 킹메이커가 시작되었고
- **When** 제한 시간 **2분** 안에 의견(최대 **120자**)을 제출하면
- **Then** 제출 완료 표시가 나타나고 `N / 6 제출` 진행 상황이 갱신된다
- **And** 한 사람이 **한 건만** 낼 수 있고 제출 후에는 수정도 취소도 할 수 없다
- **And** `0 / 120자` 카운터가 표시되고, 120자에 도달하면 추가 입력이 차단된다
- **And** 제출하면 입력창이 비활성되고 **수정도 취소도 할 수 없다**
- **And** 아직 안 낸 사람 자리는 점선 카드로 표시된다
- **When** 전원이 제출하거나 제한 시간이 끝나면
- **Then** 제출이 마감되고 작성자 정보 없이 후보 텍스트만 전원에게 공개된다
- **And** 전원 제출이 완료되면 **즉시** 투표 화면으로 넘어간다
- **But** 제한 시간 안에 못 낸 참가자는 **후보 없이 투표에만 참여**한다
- **But** 아무도 제출하지 않으면 후보가 0개이므로 방장에게 재시작 / 대기방 복귀 팝업이 뜬다

#### US-432 · 킹메이커 — 투표

**참여자로서** 마음에 드는 후보를 고르고 싶다.

우선순위 `필수` · 출처 `games.md §4`

- **Given** 후보가 공개되었고
- **When** 제한 시간 **1분** 안에 후보 하나를 선택하면
- **Then** 투표가 접수되고 전원의 진행 카운터가 갱신된다
- **But** 자기가 낸 후보는 **비활성 카드에 `내 제출` 배지**가 붙어 고를 수 없다 (서버에서도 거부한다)
- **But** 방장이 설정한 1인당 투표 수를 넘겨 행사하면 서버가 거부하고 안내 토스트를 띄운다
- **And** 2표 이상 설정이면 **같은 후보에 몰아줄 수 있다**([D-40](#7-확정된-설계-결정)). 투표 가능한 후보가 내 것을 빼고 1개뿐일 때도 표가 버려지지 않는다
- **And** 투표를 확정하면 변경할 수 없고 상태가 `✓ 투표 완료`로 바뀐다
- **When** 전원이 투표를 마치면
- **Then** 투표가 종료되고 **최다 득표** 후보가 선정된다. 룰렛 등 다른 결정 방식은 제공하지 않는다([D-18](#7-확정된-설계-결정))
- **But** 최다 득표가 동점이면 **동점 후보만 남기고 결선 투표**를 한다. 기존 투표는 초기화하고 후보를 다시 제출받지는 않으며, **단독 최다 득표가 나올 때까지 반복**한다
- **And** 결선에 들어갈 때 `여기까지 생존 · N위부터 탈락` 안내로 후보가 줄어드는 것을 알리고, **가이드는 표시하지 않는다**
- **But** 제한 시간이 끝났는데 아직 투표하지 않은 사람이 있으면 **그 시점 집계로 판정**한다
- **But** 투표 도중 나간 참가자의 **이미 행사한 표는 유효**하고, 아직 안 쓴 표는 소멸한다

#### US-433 · 킹메이커 — 실명 공개 설정

**방장으로서** 아이디어를 낸 사람을 결과에서 밝힐지 정하고 싶다.

우선순위 `권장` · 출처 `api.md 확정 8`

- **Given** 킹메이커를 선택한 상태에서
- **When** `1인당 투표 수`, `투표 결과 익명/실명`, `의견 주제`를 설정하면
- **Then** 참여자 화면에도 같은 값이 표시된다
- **And** `실명`이면 결과 화면의 후보마다 **투표자 아바타·닉네임 칩**이 붙고, `익명`이면 그 영역 자체가 없다
- **And** `실명`에서는 **아이디어 제안자도 함께 공개**한다
- **But** **투표가 진행되는 동안에는 어느 모드에서든 익명**이다. 서버는 결과가 확정된 시점에만 투표자 명단을 내려보낸다
- **And** 1인 2표 설정이면 같은 사람이 서로 다른 후보의 투표자 목록에 중복해서 나타난다
- **And** 투표자가 많으면 칩을 `+N` 더보기로 접는다
- **And** 득표가 0인 후보는 목록에서 빼지 않고 `0표`로 함께 보여 준다

#### US-441 · 시간초 잡기 — 타이머 정지

**참여자로서** 목표 시간에 맞춰 버튼을 누르고 싶다.

우선순위 `필수` · 출처 `games.md §5`

- **Given** 시간초 잡기가 시작되었고
- **When** 가이드 팝업이 사라지면
- **Then** `START` 대기 화면이 뜨고 **참가자 전원에게 각자 활성된** 버튼이 보인다 (방장 전용이 아니다)
- **And** `개별 타이머` 안내 배지가 함께 표시된다 — "내 타이머는 내가 START를 누른 순간부터 흘러요"
- **When** 내가 `START`를 누르면
- **Then** 서버가 그 시각을 기준으로 **내 개인 타이머만** 시작한다([D-20](#7-확정된-설계-결정))
- **And** 타이머는 참가자마다 따로 존재하므로 시작 시각이 서로 달라도 무방하다
- **And** 다른 사람 카드에는 **START 여부만**(`▶ 진행 중` / `⏸ 아직 시작 전`) 보이고 **경과 시간은 공개되지 않는다**
- **And** `2 / 6 시작` 같은 진행 칩이 실시간으로 동기화된다
- **But** `START`를 두 번 눌러도 최초 1회만 인정된다
- **And** 내 화면에 2초까지만 시간이 표시되고 그 뒤로는 `?.??`로 가려진다. **타이머 자체는 계속 흐른다**
- **And** 가려지는 동안 서버는 **경과 값을 클라이언트로 아예 보내지 않는다.** 화면만 덮는 방식이 아니라서 개발자 도구로 열어봐도 값을 알 수 없다
- **And** 목표 시간 배지는 계속 보인다. 숨기는 것은 경과 시간뿐이다
- **And** 가려지는 순간 타임라인의 참가자 마커도 함께 사라져 **누가 언제 멈췄는지 드러나지 않는다**
- **When** `STOP`을 누르면
- **Then** 경과 시간이 정수 밀리초로 기록된다. 판정 기준은 **서버가 받은 `START`와 `STOP`의 시각 차이**이고, 클라이언트가 보낸 시각은 참고용이다
- **And** 버튼이 즉시 비활성되고 기록이 확정된다
- **And** 다른 참가자에게는 **정지 여부만** 보이고 기록과 오차는 결과 화면에서 공개된다
- **And** `4 / 6 정지 · 2명 STOP 대기` 진행 칩이 실시간 갱신된다
- **And** 다시 누를 수 없다
- **But** **내 `START`로부터** 목표 시간 + 3초가 지나도록 `STOP`을 누르지 않으면 자동으로 최하위 처리된다 (제한 시간도 참가자별로 따로 흐른다)
- **But** `START` 자체를 누르지 않은 참가자는 **가이드가 끝난 뒤 30초**가 지나면 최하위로 마감된다([D-37](#7-확정된-설계-결정))
- **But** 아무도 기록을 남기지 않아 **전원이 미입력**이면 순위를 매길 수 없으므로, 방장에게 재시작 / 대기방 복귀 선택 팝업이 뜬다
- **And** `START` 전에 퇴장한 참가자도 최하위로 처리하고, 남은 참가자의 판정은 그대로 진행한다

#### US-442 · 시간초 잡기 — 기준 설정

**방장으로서** 목표 시간과 당첨 기준을 정하고 싶다.

우선순위 `필수` · 출처 `games.md §5.2`

- **Given** 시간초 잡기를 선택한 상태에서
- **When** `무엇을 정할까`(`팀장` · `발표자` · 직접 입력), 목표 시간(5초 / 7초 / 10초), 선정 기준(오차가 가장 작은 사람 / 가장 큰 사람)을 고르면
- **Then** 참여자 화면에도 같은 값이 표시된다
- **And** 결과 판정이 그 기준을 따른다
- **And** `무엇을 정할까`는 **표시용 라벨**이라 판정에 영향을 주지 않는다([D-24](#7-확정된-설계-결정))

#### US-443 · 시간초 잡기 — 순위 확인

**참여자로서** 내가 몇 등인지, 얼마나 빗나갔는지 보고 싶다.

우선순위 `필수` · 출처 `games.md §5.3-9`

- **Given** 라운드가 끝났을 때
- **When** 결과 화면을 보면
- **Then** 참가자별 정지 시간과 목표 대비 오차가 부호와 함께(`+0.03초`, `-0.09초`) 표시된다
- **And** 순위 목록의 **정렬 방향은 방장이 고른 기준을 따른다** (오차 적은 순 / 큰 순)
- **And** 목표 시간 · 1위 오차 · 참가자 수가 요약 수치로 보이고, `목표 7.00초 → 내 기록 7.02초` 같은 개인화 문구가 표시된다
- **And** `STOP`을 누르지 않은 사람은 **최하위에 고정**되고 기록 자리에 `미입력`으로 표기된다
- **And** 미입력자가 여럿이면 그들끼리 순서를 임의로 매기지 않고 **동순위**로 표기한다

#### US-451 · 익명 저격 — 지목

**참여자로서** 질문에 어울리는 사람을 익명으로 지목하고 싶다.

우선순위 `필수` · 출처 `games.md §6`

- **Given** 익명 저격이 시작되어 질문과 제한 시간이 공개되었고
- **When** 제한 시간 안에 자신을 제외한 참가자 한 명을 고르면
- **Then** 투표가 접수되고 이후 변경할 수 없다
- **But** 자기 자신은 **후보 목록에 아예 나타나지 않는다.** 고를 수 없게 막는 게 아니라 화면에서 제외한다
- **And** 아무도 고르지 않고 시간이 지나면 미투표로 처리된다
- **And** 마감 후 결과는 총알 궤적(레이저 선) 연출로 공개된다
- **But** 발사 요청을 두 번 보내도 최초 1회만 인정된다
- **But** 투표 도중 나간 참가자의 **이미 행사한 표는 유효**하고, 안 쓴 표는 미투표가 된다
- **And** 지목 내역은 **서버에만 보관하고 클라이언트로 내려보내지 않는다**
- **And** 마감 후 **최다 피격자와 그 사람의 피격 수만** 공개된다
- **But** 나머지 사람은 `세이프!`로만 표시되고 **개별 피격 수는 공개하지 않는다.** 몇 표씩 받았는지가 드러나면 서로 민망해지기 때문이다
- **And** 익명 저격에는 **실명 모드가 없다.** 지목자는 결과 화면에서도 끝까지 공개하지 않는다 (킹메이커와 다른 점)
- **But** 유효 투표가 한 건도 없으면 당첨자를 정할 수 없으므로 방장에게 재시작 / 대기방 복귀 팝업이 뜬다

> 익명 저격은 **3명 이상**일 때만 시작할 수 있다. 2명이면 지목 대상이 1명뿐이라 익명성이 성립하지 않는다([D-25](#7-확정된-설계-결정)).

#### US-452 · 익명 저격 — 질문 설정

**방장으로서** 질문을 고르거나 직접 쓰고 싶다.

우선순위 `필수` · 출처 `games.md §6.3`

- **Given** 익명 저격을 선택한 상태에서
- **When** 프리셋 질문을 고르거나 직접 입력하고, 투표 시간(기본 10초)과 **중복 투표 여부**(불가 / 가능)를 정하면
- **Then** 게임 시작 시 전원에게 같은 질문과 시간이 표시된다
- **And** `중복 투표 가능`이면 한 참가자가 **2표**를 갖고, 같은 대상에 두 표를 몰아줄 수도 있다([D-39](#7-확정된-설계-결정))
- **But** 2표를 넘기면 `ALREADY_SUBMITTED`로 거부된다. 제한 시간 동안 무제한으로 누르는 방식이 아니다

#### US-461 · 눈치게임 — UP 누르기

**참여자로서** 남들과 겹치지 않는 타이밍에 버튼을 누르고 싶다.

우선순위 `필수` · 출처 `games.md §7`

- **Given** 눈치게임이 시작되었고
- **When** 제한 시간 15초 안에 `UP`을 누르면
- **Then** 서버가 클릭 시각과 순서를 기록한다
- **And** 15초는 고정값이며 방장이 바꿀 수 없다([D-32](#7-확정된-설계-결정))
- **And** 라운드마다 한 번만 누를 수 있다
- **But** 두 명 이상이 판정 시간(기본 0.3초) 안에 누르면 그 전원이 탈락한다
- **But** 제한 시간까지 누르지 않으면 탈락 처리된다
- **And** 게임이 길어질수록 배경 점멸과 텍스트 흔들림으로 압박이 강해진다
- **And** 혼자 누른 참가자는 통과한다
- **And** 게임 도중 연결이 끊긴 참가자는 즉시 탈락 처리된다
- **And** `생존 N / M · 탈락 K` HUD가 라운드마다 갱신되고, 탈락자 카드는 흐림 처리된다
- **And** 눌린 순서는 실시간으로 쌓이며, 화면 표시는 클라이언트 요청 시각 기준이지만 **판정은 서버가 보정한 수신 시각**을 쓴다

#### US-462 · 눈치게임 — 난이도 설정

**방장으로서** 동시 입력 판정을 얼마나 빡빡하게 할지 정하고 싶다.

우선순위 `권장` · 출처 `games.md §7.2`

- **Given** 눈치게임을 선택한 상태에서
- **When** 판정 시간을 기본(0.3초) 또는 하드 모드(0.5초)로 고르면
- **Then** 그 값으로 동시 입력 판정이 이루어진다

#### US-463 · 눈치게임 — 전원 탈락 처리

**방장으로서** 아무도 살아남지 못했을 때 다음 행동을 고르고 싶다.

우선순위 `필수` · 출처 `games.md §7.5`

- **Given** 모든 참가자가 동시 입력으로 탈락했을 때
- **When** 라운드가 끝나면
- **Then** 방장에게 `처음부터 다시 시작` / `대기방으로 복귀` 선택 팝업이 표시된다
- **And** 참여자에게는 버튼이 비활성이고 `방장이 선택하는 중…` 안내가 보인다
- **And** 탈락 사유가 상황에 맞게 표시된다 (`남은 3명이 0.3초 안에 겹쳤어요` / `15초 동안 아무도 누르지 않았어요`)
- **And** 제한 시간 15초 안에 **아무도 누르지 않아** 전원이 탈락한 경우도 같은 팝업으로 처리한다
- **But** 전원 탈락은 **결과 화면으로 이어지지 않는다.** 벌칙자를 확정할 수 없으므로 방장의 선택으로만 회차가 끝나고 최종 선정자는 **없음**으로 기록된다
- **When** 방장이 `처음부터 다시 시작`을 고르면
- **Then** 탈락자 전원이 부활해 라운드 1부터 다시 시작하고, **가이드는 표시하지 않는다**([D-34](#7-확정된-설계-결정))
- **And** 재시작 회차의 참가자는 **직전 회차 시작 시점 명단**으로 고정된다
- **But** 모달이 떠 있는 동안 사람이 나가 **2명 미만이 되면 재시작을 할 수 없고** `대기방으로 복귀`만 활성된다
- **And** 재시작해서 또 전원이 탈락해도 같은 모달이 반복되며 횟수 제한은 없다

#### US-464 · 눈치게임 라운드 반복

**참여자로서** 한 판으로 끝나지 않고 끝까지 살아남는 승부를 하고 싶다. **왜냐하면** 한 번의 실수로 바로 끝나면 긴장감이 짧기 때문이다.

우선순위 `필수` · 출처 `games.md §7.5 최후의 1명까지 반복` · [D-19](#7-확정된-설계-결정)

- **Given** 한 라운드가 끝나 탈락자가 정해졌고
- **When** 생존자가 2명 이상 남아 있으면
- **Then** 탈락자를 제외하고 다음 라운드가 이어서 시작된다
- **And** 라운드 사이에는 **3초 카운트다운**이 들어간다([D-46](#7-확정된-설계-결정)). 직전 라운드의 클릭이 다음 라운드에 잘못 잡히지 않도록 입력을 받지 않는 구간이다
- **And** 서버는 라운드마다 클릭 여부와 순서를 초기화한다
- **And** 탈락자는 관전 상태가 되며 추가 입력은 무시된다
- **When** 생존자가 1명이 되면
- **Then** 그 한 명을 **탈락 처리**하고 결과 화면을 낸다 (정본 7.5 표현)
- **And** 결과 화면에서는 이 사람을 **최종 선정자**로, 나머지를 통과로 표시한다
- **And** 라운드별 탈락자와 클릭 순서가 결과에 함께 표시된다
- **And** 진행 중에는 누른 사람의 순번과 이름이 서버 시각 기준으로 실시간 나열된다
- **And** 결과 화면은 **라운드별 타임라인**으로, 각 라운드마다 통과자와 탈락자를 사유별로 나누어 보여 준다
- **And** 탈락 사유는 `동시 입력 · 0.13초 차`처럼 **그룹 내 시간 차를 함께** 적고, 시간 초과는 따로 구분한다
- **And** 참가자 카드에는 **서버 기준 클릭 시각**이 붙고, 누르지 않은 사람은 `미입력`으로 표기된다
- **And** 상단에 참가자 수 · 통과 · 동시 입력 탈락 · 시간 초과 탈락 4종 집계와 그 회차의 판정 시간(0.3초/0.5초)이 표시된다

> **끝까지 남아 탈락한 그 한 명이 이 게임이 뽑으려던 대상**이다([D-23](#7-확정된-설계-결정)). 정본은 "탈락 처리"라고 쓰지만 의미는 팀장·벌칙 대상 선정이며, 결과 화면에는 탈락 순서도 함께 보여 준다.

#### US-471 · 동점자 재대결

**참여자로서** 동점이 나왔을 때 명확하게 결론이 나기를 바란다.

우선순위 `필수` · 출처 `games.md §4·§5.6·§6.6` · `api.md game:tie`

- **Given** 최다 득표 또는 최소 오차가 동점으로 나왔을 때
- **When** 라운드가 판정 단계에 들어가면
- **Then** 동점자 목록이 담긴 재대결 안내가 전원에게 표시된다
- **And** 재대결은 새 라운드가 아니라 같은 라운드의 `TIE` 단계로 진행된다
- **And** 재대결 반복 횟수에는 상한이 없다. 언제 끝낼지는 방장이 정한다
- **And** 재대결로 다시 시작할 때는 **가이드를 표시하지 않는다**([D-34](#7-확정된-설계-결정))
- **And** 선택 버튼은 방장에게만 활성되고, 참여자에게는 `방장이 선택하는 중…` 안내가 보인다
- **But** 동점자 중 누군가 나가서 **후보가 1명만 남으면 자동으로 확정**되고 곧바로 결과 화면으로 넘어간다
- **But** 버튼을 두 번 눌러도 최초 1회만 인정된다
- **And** 방장이 오래 고르지 않으면 방 만료 규칙(10분 무요청)이 그대로 적용된다

**게임별 동점 처리가 다르다.**

| 게임 | 처리 |
| --- | --- |
| 킹메이커 | 동점 후보만 남기고 **결선 투표**. 기존 투표는 초기화하고 후보를 다시 제출받지 않으며, 단독 최다 득표가 나올 때까지 반복 |
| 익명 저격 | 동점자를 **후보로만 유지**하고 **참가자 전원이 재투표**한다. 재투표할지 대기방으로 돌아갈지는 **방장이 선택**한다. **전원이 미투표여도 같은 팝업**으로 처리한다 |
| 시간초 잡기 | **같은 목표 시간으로 동점자만 `START`부터 다시 진행한다**([D-41](#7-확정된-설계-결정)). 방장 설정을 그대로 쓰고, 회차 제한 시간 30초와 개인 제한 시간(목표+3초)도 다시 적용된다 |

### 4.5 결과와 재시작 (US-5xx)

#### US-501 · 결과 발표 화면 이동

**참여자로서** 결과를 놓치지 않고 확인하고 싶다.

우선순위 `필수` · 출처 `games.md §1.4`

- **Given** 게임 화면에서 결과 연출이 끝났을 때
- **When** 3초가 지나면
- **Then** 전원이 자동으로 결과 발표 화면으로 이동한다
- **And** 결과 화면의 구성은 **게임 성격에 따라 다르다** — 룰렛·저격은 당첨자 한 명을 크게 세우는 **승자형**, 사다리는 `참가자 → 역할` **배정 그리드**, 킹메이커는 후보별 **개표 목록**, 시간초는 **순위표**, 눈치게임은 **라운드별 기록 타임라인**이다
- **And** 게임별 요약 수치가 함께 보인다 — 룰렛은 참가자 수와 당첨 확률(`1 ÷ 참가자 수`), 킹메이커는 총 투표 수와 1위 득표율(`1위 득표수 ÷ 총 투표 수`), 시간초는 목표 시간과 1위 오차
- **And** 당첨자가 하나로 정해지는 게임에서는 나머지 사람도 `세이프!` 라벨을 단 카드로 함께 표시된다
- **And** 참가자를 나열하는 순서는 **회차 시작 시 고정된 순서**를 따른다

#### US-502 · 결과 이미지 저장

**참여자로서** 결과를 이미지로 저장하고 싶다. **왜냐하면** 단톡방에 증거로 올려야 뒷말이 없기 때문이다.

우선순위 `필수` · 출처 `draft_plan.md §3-5` · 디자인 시안(결과 저장 패널)

- **Given** 결과 발표 화면에 있고
- **When** `결과 이미지 저장`을 누르면
- **Then** 결과 카드 영역이 PNG 파일로 저장된다
- **And** 저장된 이미지에는 `modupick · 방 MODU-######` 워터마크가 함께 찍힌다
- **And** 방장·참여자 모두 저장할 수 있다
- **But** 저장에 실패하면 재시도 안내 토스트만 뜨고 결과 데이터에는 영향이 없다

> **저장 수단은 이미지 하나뿐이다**([D-13](#7-확정된-설계-결정)). xlsx 등 표 형식 저장도, SNS 공유(Slack·Discord·카카오)도 제공하지 않는다.
>
> `US-503`(결과 표 저장)은 2026-07-27 폐기되었다. **번호는 재사용하지 않는다.**

#### US-504 · 다시 하기

**방장으로서** 같은 설정으로 한 판 더 돌리고 싶다.

우선순위 `필수` · 출처 `games.md §1.4-7`

- **Given** 방장이 결과 발표 화면에 있고
- **When** `다시 하기`를 누르면
- **Then** 직전 설정 그대로 새 라운드가 시작되고 전원 화면이 게임 화면으로 전환된다
- **And** 새 `roundId`가 발급되어 이전 라운드 입력은 반영되지 않는다
- **And** 이때는 **가이드를 표시하지 않고** 곧바로 게임이 시작된다([D-34](#7-확정된-설계-결정))
- **But** 버튼을 두 번 눌러도 최초 1회만 인정된다

#### US-505 · 대기방 복귀

**방장으로서** 다른 게임을 고르러 대기방으로 돌아가고 싶다.

우선순위 `필수` · 출처 `games.md §1.4-6`

- **Given** 방장이 결과 발표 화면에 있고
- **When** `대기방으로`를 누르면
- **Then** 전원이 대기방 화면으로 이동하고 방 상태가 `WAITING`으로 돌아간다
- **And** 게임 전 채팅 내용이 그대로 보인다 (클라이언트 로컬 스토리지에서 복원)
- **And** 준비 상태는 초기화된다

#### US-506 · 참여자 대기

**참여자로서** 방장이 다음 행동을 고를 때까지 무엇을 기다리는지 알고 싶다.

우선순위 `권장` · 출처 `games.md §1.4-8`

- **Given** 참여자가 결과 발표 화면에 있을 때
- **When** 화면을 보면
- **Then** 방장의 다음 선택을 기다리는 중임이 안내된다
- **And** 참여자에게는 `다시 하기`·`대기방으로` 버튼이 보이지 않는다

#### US-507 · 결과 불변성

**참여자로서** 확정된 결과가 나중에 바뀌지 않기를 바란다.

우선순위 `필수` · 출처 `games.md §1.5`

- **Given** 결과가 확정된 뒤
- **When** 참가자가 나가거나 창을 닫아도
- **Then** 남아 있는 사람들의 결과 화면은 변하지 않는다
- **And** 나간 사람의 카드에는 오프라인 표시만 반영된다

### 4.6 이탈·만료·예외 (US-6xx)

#### US-601 · 방장 이탈 시 방 폭파

**참여자로서** 방장이 사라졌을 때 이유를 알고 싶다. **왜냐하면** 화면이 갑자기 바뀌면 오류로 오해하기 때문이다.

우선순위 `필수` · 출처 `draft_plan.md §2① 방장 이탈`

- **Given** 방장이 대기방이나 게임 중에 이탈했을 때
- **When** 서버가 이를 감지하면
- **Then** 전원에게 "방장이 이탈하였습니다" 팝업이 표시된다
- **And** 전원이 표지 화면으로 이동한다
- **And** 해당 방과 초대 코드는 삭제되어 재사용할 수 없다
- **But** **결과 발표 화면에 있을 때는 화면을 빼앗지 않는다**([D-44](#7-확정된-설계-결정)). 방은 폭파하되 참여자의 결과 카드는 그대로 두고 `방이 종료됐어요` 배너만 띄운다
- **And** 그 상태에서 `결과 이미지 저장`은 계속 동작한다. 결과는 이미 클라이언트가 들고 있으므로 서버 없이 저장된다
- **And** 저장 외의 조작(다시 하기 · 대기방으로)은 비활성된다

#### US-602 · 방 만료

**운영자로서** 버려진 방이 자원을 계속 점유하지 않기를 바란다.

우선순위 `권장` · 출처 `draft_plan.md §2① 방 만료`

- **Given** 방이 만들어져 있고
- **When** 10분간 **사용자 행동이 하나도 없으면**
- **Then** 방이 삭제되고 남아 있던 참가자에게 만료 안내가 표시된다
- **And** 전원이 표지 화면으로 이동한다
- **And** 타이머를 되돌리는 것은 **사람이 한 행동**뿐이다 — 채팅 · 준비 완료 토글 · 게임 선택과 설정 · 게임 입력 · 강퇴([D-45](#7-확정된-설계-결정))
- **But** 소켓 연결이 붙어 있다는 사실이나 heartbeat는 갱신 근거가 되지 않는다. 창만 열어 둔 방은 만료된다
- **But** 방 상태가 `PLAYING`인 동안에는 만료 타이머를 **멈춘다**. 긴 게임 중에 방이 사라지지 않게 한다

#### US-603 · 연결 끊김 = 퇴장

**참여자로서** 내 연결이 끊기면 어떻게 되는지 미리 알고 싶다.

우선순위 `필수` · 출처 `api.md 연결 수명주기`

- **Given** 대기방 또는 게임 화면에 있고
- **When** 새로고침하거나 네트워크가 끊겨 소켓 연결이 종료되면
- **Then** 서버는 즉시 방에서 나를 제거한다
- **And** 다시 들어오려면 초대 코드부터 입력해야 한다
- **And** 게임이 진행 중이면 `ROOM_ALREADY_PLAYING`으로 재입장할 수 없다

> **재접속 개념이 없다는 것이 이 설계의 핵심 제약이다.** 새로고침 한 번이면 방에서 빠지므로, 프론트엔드는 이탈 위험 동작(새로고침·뒤로가기·창 닫기)에 경고를 띄워야 한다([US-604](#us-604--이탈-경고)).

#### US-604 · 이탈 경고

**참여자로서** 실수로 나가는 일을 막고 싶다.

우선순위 `권장` · 출처 [D-11](#7-확정된-설계-결정)의 귀결 (정본에는 없음 — [§10.2](#102-notion-게임-기획안--기획안) 참조)

- **Given** 대기방 또는 게임 화면에 있고
- **When** 새로고침이나 창 닫기를 시도하면
- **Then** 방에서 나가게 된다는 경고가 표시된다

#### US-605 · 게임 중 이탈자 처리

**참여자로서** 누가 중간에 나가도 게임이 멈추지 않기를 바란다.

우선순위 `필수` · 출처 `api.md 확정 3`

- **Given** 게임이 진행 중이고
- **When** 참가자가 입력을 마치기 전에 이탈하면
- **Then** 그 참가자는 자동 기권으로 처리되고 라운드는 계속 진행된다
- **And** 라운드를 취소하지 않는다
- **And** 이탈자를 제외한 나머지로 판정한다
- **When** 이탈이 이어져 남은 참가자가 1명이 되면
- **Then** 라운드를 즉시 종료하고 그 시점까지의 결과를 발표한다([D-30](#7-확정된-설계-결정))

#### ~~US-606 · 미연결 슬롯 자동 해제~~ (MVP 범위 밖)

> **2026-07-28 보류.** 정본에 없는 기능이고 대기 시간도 `api.md` 임의값이었다. 유령 슬롯은 **방 만료 10분 규칙**으로 갈음하고, 정원이 자주 막히는 문제가 실제로 관찰되면 그때 기획에 올린다([D-36](#7-확정된-설계-결정)).
>
> 아래 내용은 참고용으로만 남긴다. **번호는 재사용하지 않는다.**

우선순위 ~~`권장`~~ · 출처 `api.md POST /members` (근거 아님)

- **Given** 누군가 코드를 입력해 슬롯만 선점한 상태에서
- **When** 정해진 시간 안에 소켓 연결이 이루어지지 않으면 (**대기 시간 미정** — [Q-19](#8-미확정-항목--팀-확정-필요))
- **Then** 서버가 해당 슬롯을 자동으로 해제한다
- **And** 정원 카운트가 원래대로 돌아간다

#### US-607 · 오류 안내

**참여자로서** 무엇이 잘못됐는지 한국어로 알고 싶다.

우선순위 `필수` · 출처 화면설계서 각 화면의 「예외 · 에러 처리」

- **Given** 어떤 동작이 거부되었을 때
- **When** 화면에 결과가 표시되면
- **Then** 무엇이 잘못됐는지 **한국어로** 알려 준다 (`방을 찾을 수 없어요` · `인원이 가득 찼어요` · `이미 사용 중인 닉네임이에요`)
- **And** 표시 위치는 화면설계서를 따른다 — 입력값 문제는 **필드 하단 인라인**, 진행 불가 상황은 **모달**, 일시적 실패는 **토스트**
- **And** 오류는 요청한 본인에게만 보이고 다른 참가자 화면에는 나타나지 않는다

> **에러 코드 집합**(`ROOM_NOT_FOUND` 등)은 기획 산출물이 아니라 **구현 계약**이므로 [`api.md`](api.md)에서 개발이 관리한다([D-35](#7-확정된-설계-결정)). 이 문서는 *사용자가 무엇을 보는가*만 규정한다.

## 5. 비기능 요구사항 (NFR)

### NFR-01 · 실시간 반영 지연

우선순위 `필수`

같은 방 참가자 간 상태 반영 편차가 사용자에게 인지되지 않아야 한다.

- 서버가 이벤트를 브로드캐스트한 시점부터 각 클라이언트 화면 반영까지의 **편차 목표는 200ms 이내**다 (일반 가정용 회선 기준). ⚠️ 제안값이며 팀 확정 필요 — [Q-19](#8-미확정-항목--팀-확정-필요)
- 타이머가 중요한 게임(시간초·눈치)은 화면 애니메이션이 아니라 **서버 기준 시각**으로 판정한다.
- 클라이언트는 서버 시각과 자기 시계의 오차를 최초 동기화 시점에 한 번 재고, 이후에는 자체 타이머를 돌린다.
- **오차 보정은 1초 주기로 계속한다**([D-47](#7-확정된-설계-결정)). 서버가 매초 내려보내는 기준 시각으로 오차만 다시 재고, 화면의 숫자를 tick마다 새로 그리지는 않는다 — 네트워크가 튈 때 카운트가 끊겨 보이기 때문이다.

> ⚠️ 200ms는 **내가 제안한 값**이다([Q-19](#8-미확정-항목--팀-확정-필요)). 부하 테스트 합격 기준이 되므로 팀이 확정해야 한다.

### NFR-02 · 이벤트 순서 보장

우선순위 `필수`

네트워크 사정으로 이벤트 순서가 뒤집혀도 화면 상태가 과거로 되돌아가서는 안 된다.

- 방 상태가 바뀔 때마다 증가하는 정수 버전 값을 모든 서버 → 클라이언트 이벤트에 포함한다.
- 클라이언트는 마지막으로 반영한 번호보다 작거나 같은 이벤트를 무시한다.

### NFR-03 · 동시성 규모

우선순위 `권장`

- 방 1개당 최대 10명.
- **동시 운영 방 100개**(최대 동시 소켓 1,000개)를 목표로 한다. ⚠️ 제안값이며 인프라 사이징 근거가 되므로 팀 확정 필요 — [Q-19](#8-미확정-항목--팀-확정-필요)
- 방 상태는 방 생명주기 동안만 유지하면 되므로, 영속 저장 부하보다 **동시 소켓 연결 수**가 병목이다.

### NFR-04 · 인증과 권한

우선순위 `필수`

- 로그인 없이 방 단위 토큰(`guestToken` / `hostToken`)으로만 인증한다.
- 소켓 핸드셰이크 시 토큰과 방 코드를 검증하고, 유효하지 않으면 연결을 거부한다.
- 방장 전용 동작(게임 선택·설정·시작·강퇴·다시 하기·대기방 복귀)은 **서버에서 권한을 검증**한다. 클라이언트에서 버튼을 숨기는 것만으로는 충분하지 않다.
- 권한 위반은 요청자에게만 오류를 돌려주고 브로드캐스트하지 않는다.

### NFR-05 · 결과 무결성

우선순위 `필수`

- 모든 무작위 결과는 **서버가 생성**한다. 클라이언트는 결과를 다시 계산하거나 변경하지 않는다.
- 룰렛·사다리는 결과를 먼저 확정한 뒤 애니메이션을 재생한다. 애니메이션 종료 시점에 결과를 정하지 않는다.
- 재현을 위해 서버 시드를 결과 데이터에 함께 남긴다.
- **감춰야 할 값은 화면에서 가리는 데 그치지 않고 애초에 클라이언트로 보내지 않는다.** 시간초의 2초 이후 경과 시간, 킹메이커·저격의 투표자 정보가 여기 해당한다. 화면만 덮으면 개발자 도구로 열람할 수 있다.
- 결과 판정은 **서버 수신 시각**을 기준으로 한다. 클라이언트가 보낸 시각은 참고용이다.

### NFR-06 · 익명성

우선순위 `필수`

- 킹메이커 의견 제출과 익명 저격 투표는 **작성자·투표자 정보를 클라이언트에 전달하지 않는다.**
- 중복 투표 방지를 위한 투표자 식별은 서버 내부에서만 한다.
- 킹메이커 투표는 **후보 식별자**로 접수한다. 멤버 식별자로 투표받으면 클라이언트가 "누가 어떤 의견을 냈는지"를 알아야 투표할 수 있게 되어 익명성이 구조적으로 무너진다([D-21](#7-확정된-설계-결정)).
- "자기 의견에는 투표할 수 없다"는 제약도 **서버가** 후보와 작성자를 대조해 판정한다. 클라이언트에 작성자를 내려보내 가리는 방식은 쓰지 않는다.
- 실명 공개는 방장이 게임 설정에서 명시적으로 선택했을 때만, 결과 단계에서 이루어진다.

### NFR-07 · 화면 규격

우선순위 `필수`

- 기준 해상도는 **1920×1080 (16:9)**. 디자인 시안 24개 화면이 모두 이 규격이다.
- 콘텐츠 폭 1832px, 좌우 여백 44px, 3단 레이아웃을 기본으로 한다.
- 프레임 컨벤션: 콘텐츠 카드·패널·입력창은 **흰색**(검정 굵은 보더 + 하드 오프셋 섀도우), **검정은 주요 실행 버튼(CTA) 전용**, 캔디색은 선택·활성 상태와 뱃지에 쓴다.
- 폰트: Black Han Sans(디스플레이) · Gothic A1(본문) · NanumGothicCoding(모노).
- **모바일·태블릿은 MVP 범위 밖이다**([D-17](#7-확정된-설계-결정)). 데스크톱으로 먼저 완성하고 이후 단계에서 대응한다. 따라서 MVP 구현에서 반응형 브레이크포인트를 설계하지 않는다.

### NFR-08 · 데이터 보존 정책

우선순위 `필수`

| 데이터 | 보관 위치 | 수명 |
| --- | --- | --- |
| 방·참가자·라운드 상태 | 서버 | 방 폭파 또는 만료까지 |
| 채팅 메시지 | 브라우저 로컬 스토리지 | 브라우저가 지울 때까지. **서버는 저장도 보관도 하지 않는다** |
| 게임 결과 | 서버(라운드 단위) + 사용자가 내려받은 PNG | 방이 사라지면 서버 쪽은 함께 사라진다 |

- 방이 사라지면 초대 코드도 무효가 되고 재사용하지 않는다.
- **서버는 채팅을 DB에 저장하지도, 메모리에 들고 있지도 않는다**([D-26](#7-확정된-설계-결정)). 연결 직후 스냅샷에도 채팅이 포함되지 않으며, 화면 복원은 전적으로 클라이언트 로컬 스토리지가 담당한다. 따라서 **나중에 들어온 사람은 이전 대화를 볼 수 없다.**

### NFR-09 · 오류 응답 일관성

우선순위 `필수`

- REST와 소켓 모두 동일한 공통 응답 객체(`success` / `code` / `message` / `data` / `timestamp`)를 사용한다.
- 날짜·시각은 ISO 8601 + 타임존 포함으로 통일한다.
- `code` 문자열 집합은 `api.md`의 에러 코드 표를 단일 정본으로 삼는다.

### NFR-10 · 배포와 실행 환경

우선순위 `권장` · 출처 `techstack.md`

- 백엔드 Python · FastAPI, 프론트엔드 React + Vite · TypeScript, DB PostgreSQL.
- 실시간은 Native WebSocket을 사용한다. 재접속·상태 복구는 직접 구현하지 않는다(재접속 개념이 없으므로).
- 로컬 개발은 Docker Compose, 배포는 Kubernetes + Nginx, 자동화는 GitHub Actions.

### NFR-11 · 접근성

우선순위 `선택`

- 색만으로 상태를 구분하지 않는다. 준비 완료·탈락·당첨은 텍스트나 아이콘을 함께 쓴다.
- 눈치게임의 배경 점멸 연출은 광과민성 발작 유발 위험이 있으므로 점멸 강도·주기를 제한하거나 끄는 수단을 제공한다.
- **`prefers-reduced-motion`을 존중한다.** 표지의 무한 스크롤 배너처럼 계속 움직이는 장식은 이 설정이 켜져 있으면 정지시킨다.

### 6.1 게임별 설정 항목 (C-05)

설정 패널은 대기방 안에 있고 **방장이 고른 게임에 따라 자동으로 교체**된다. 참여자에게는 같은 패널이 읽기 전용으로 보인다.

| 게임 | 설정 항목 |
| --- | --- |
| 공통 | **`무엇을 정할까?`** — 프리셋 칩 + 직접 입력(최대 16자, 예: `오늘 청소 당번은?`). 직접 입력을 고를 때만 입력 바가 나타난다 |
| 운명의 룰렛 | `무엇을 정할까?` (팀장 / 발표자 / 당첨 / 벌칙 / 직접 입력) |
| 랜덤 사다리 | `무엇을 정할까?` · **결과 항목**(최소 1개 ~ 최대 참가자 수) · **진행 속도**(빠름 / 보통 / 느리게) |
| 킹메이커 | `무엇을 정할까?` (팀장 / 주제 발표 / 의제 / 팀명 / 당번 / 직접 입력) · **1인당 투표 횟수**(기본 1회) · **투표 결과 익명 / 실명** |
| 시간초 잡기 | `무엇을 정할까?` · **목표 시간**(5 / 7 / 10초, 라벨에 "최대 10초") · **당첨 기준**(오차가 적은 사람 / 큰 사람) |
| 익명 저격 | **질문**(프리셋 3종 + 직접 입력, **최대 30자** · D-42) · **중복 투표 여부**(불가 = 1표 / 가능 = **2표** · D-39) · **투표 시간**(스테퍼, 기본 10초) |
| 눈치게임 | `무엇을 정할까?` · **동시 판정 시간**(0.3초 기본 / 0.5초 하드) |

**공통 규칙**

- 선택된 칩은 반전 표시되고, 변경 즉시 전원 화면에 반영된다.
- **게임을 바꾸면 이전 설정값을 버리고** 새 패널의 기본값으로 초기화한다.
- 게임 시작 시점의 설정값이 그 회차에 고정되며, `다시 하기` 때 같은 설정이 그대로 재사용된다.
- 필수 설정이 비어 있으면 `게임 시작`이 비활성이다.
- 사다리 결과 항목이 참가자 수와 같아지면 `+` 버튼이 비활성되고 `참가자 수까지만 입력할 수 있어요`가 안내된다.

## 7. 확정된 설계 결정

`api.md` 「확정이 필요한 부분」에 대한 팀 답변과 이 문서 작성 중 확정한 사항이다. **이 표를 뒤집으려면 이 문서와 `api.md`를 함께 고쳐야 한다.**

| ID | 결정 | 내용 | 영향 |
| --- | --- | --- | --- |
