# 01 서버 판정 권위

> **대상**: 게임별로 서버가 계산하는 값 · 클라이언트가 보낸 값을 쓰는 유일한 예외와 그 검증 방법 · 난수와 시드 생성 · 결과 동시 전달 · 네트워크 지터가 결과에 들어가는 폭

**결과는 서버가 확정한다**(D-05). 클라이언트는 이미 정해진 결과로 수렴하는 연출을 그릴 뿐이며, 화면·기기·네트워크 속도가 결과를 바꾸지 못한다. 이 문서는 그 원칙이 게임마다 구체적으로 무엇을 뜻하는지, 원칙에서 벗어나는 자리가 한 곳 있는데 그 자리를 무엇으로 지탱하는지, 그리고 **서버 판정이 막지 못하는 것이 무엇인지**를 확정한다.

마지막 절을 반드시 함께 읽는다. "서버 도착 시각으로 판정하므로 공정하다"는 절반만 참이다 — 클라이언트가 값을 꾸며 내는 것은 막지만 **전송 경로가 만드는 시각 왜곡은 막지 못한다.**

## 판정 권위의 경계

| 축 | 서버 | 클라이언트 |
|----|------|-----------|
| 결과 확정 | 승자·배정·순위·득표·생존자를 계산하고 확정한다 | 확정된 결과를 받아 연출한다 |
| 난수 | 시드를 뽑고 시드로 초기화한 결정적 생성기에서 필요한 값을 소비한다 | 판정에 쓰는 난수를 만들지 않는다. 결과와 무관한 장식에만 자체 난수를 쓴다 |
| 시각 | 입력의 도착 시각을 자신의 단조 시계로 기록해 판정에 쓴다 | 시각을 재서 보내되 그 값은 시간초 잡기의 경과 시간 한 자리에서만, 서버 검증을 통과할 때만 쓰인다 |
| 신원 | 요청자를 현재 소켓 연결에 바인딩한 값에서 꺼낸다 | 페이로드에 자기 식별자를 실어도 판정에 쓰이지 않는다 |
| 마감 | 단계 마감 시각을 정하고 마감 통과 여부를 판정한다 | 남은 시간을 그린다. 클라이언트가 마감을 선언하지 않는다 |
| 집계 | 준비 수·제출 수·투표 수·생존자 수를 세어 내려준다 | 목록을 자체로 세지 않는다. 화면마다 값이 갈리기 때문이다 |

**클라이언트가 화면에서 버튼을 감추는 것은 사용성 장치이지 판정이 아니다.** 감춘 표면을 직접 호출해도 서버가 같은 조건을 다시 검사한다([../02_features/08_permission_matrix.md](../02_features/08_permission_matrix.md)).

## 게임별 서버 계산 항목

| 게임 | 서버가 계산해 확정하는 값 | 클라이언트가 보내는 것 | 판정에 시각이 들어가는 자리 |
|------|--------------------------|----------------------|---------------------------|
| 운명의 룰렛 | 시드 · 당첨자 인덱스 · 조각 배치 순서(입장 순서) | 방장의 실행 신호 하나 | 없다. 실행 신호의 도착 시각은 추첨에 쓰지 않는다 |
| 사다리타기 | 시드 · 가로선 배치 · 참가자→항목 순열 · 항목 개수 맞춤 결과 | 방장의 실행 신호 하나 | 없다 |
| 킹메이커 | 안건 목록의 표시 순서(섞기) · 안건 식별자 · 자기 안건 차단 판정 · 표 수 상한 · 득표 집계 · 동점 판정 · 결선 후보 | 안건 본문 · 투표 대상 안건 식별자 | 제출·투표·결선의 **마감 통과 여부**만 |
| 시간초 잡기 | 목표 시간 · 개인 제한 시간 · 절대 오차 · 순위 · 승자 · 동점 재대결 대상 · **신고된 경과 시간의 허용 범위 검증** | START·STOP 신호 · **경과 시간(예외)** | 시작 지연 상한·개인 제한 시간의 통과 여부 · 허용 범위 검증의 기준 구간 |
| 익명 저격 | 후보 목록(자기 제외) · 표 수 상한 · 피격 집계 · 동점 판정 · 결선 후보 · 유효표 0일 때의 난수 확정 | 지목 대상 식별자 | 투표 마감 통과 여부만 |
| 눈치게임 | 입력 도착 시각 · **고립 판정(그룹핑)** · 안전 확정자 · 생존자 명단 · 무효 라운드 판정 · 최후 1인 | UP 신호 하나 | **그룹핑 전체.** 라운드 마감 통과 여부도 포함 |

- 룰렛·사다리는 **참가자 입력이 결과에 개입하지 않는 유일한 두 게임**이다(D-27). 방장의 실행 신호는 시작 트리거이지 판정 입력이 아니다.
- 킹메이커·익명 저격의 순위는 표를 세는 계산이라 시각이 들어가지 않는다. 시각은 **마감 안에 들어왔는가**를 가르는 데만 쓰인다.
- 눈치게임만 시각이 순위 계산의 본체로 들어간다. 그래서 지터의 영향도 이 게임이 가장 크다.

## 클라이언트 값을 쓰는 유일한 예외

**시간초 잡기의 경과 시간 하나뿐이다**(D-07). 다른 어떤 게임·어떤 값에도 이 예외를 적용하지 않는다.

### 왜 예외를 두는가

시간초 잡기는 목표 시간과의 절대 오차를 **밀리초 단위**로 비교해 순위를 매긴다. 이 게임에서 서버 도착 시각을 그대로 경과 시간으로 쓰면 다음이 성립한다.

```
서버가 관측한 구간 = (STOP 도착) − (START 도착)
                   = 실제 경과 시간 + (STOP 편도 지연 − START 편도 지연)
```

두 메시지의 편도 지연 차이가 그대로 기록 오차가 된다. 이 게임의 판정 해상도는 밀리초이고, 모바일 환경에서 두 메시지의 지연이 밀리초 단위로 같을 이유가 없다. 즉 **서버 도착 시각을 쓰면 감각이 아니라 회선의 순간 상태가 순위를 정한다.** 예외는 이 게임 하나만 판정 단위가 지연의 변동 폭보다 작기 때문에 생긴다.

반대로 클라이언트가 신고한 값을 검증 없이 믿으면 페이로드를 고쳐 목표 시간과 똑같은 값을 보내는 조작이 그대로 통한다. 그래서 **측정은 클라이언트가, 신뢰 판정은 서버가** 맡는 분리를 둔다.

벽시계가 아니라 **단조 시계**를 쓰는 이유는 별개다. 시스템 시각이 게임 도중 바뀌면(자동 동기화·수동 변경·시간대 전환) 벽시계 차이가 튀어 정상 참가자의 기록이 망가진다. 단조 시계는 그 영향을 받지 않는다.

### 검증 방법

서버는 자신이 관측한 START·STOP 도착 시각의 차이를 기준 구간으로 삼고, 신고된 경과 시간이 그 구간에서 허용 범위 이상 벗어나면 거부한다.

```
onStart(member, arrivalMs):
  if round.phase != PLAYING:               reject(game.round_already_ended)
  if member.startArrival is not null:      reject(game.already_submitted)
  if arrivalMs - round.startedAt > START_DEADLINE_MS:
      member.rank = LOWEST_GROUP(reason = START_MISSING); return
  member.startArrival = arrivalMs

onStop(member, arrivalMs, reportedElapsedMs):
  if member.startArrival is null:          reject(game.invalid_action)
  if member.stopArrival is not null:       reject(game.already_submitted)
  member.stopArrival = arrivalMs
  serverSpan = arrivalMs - member.startArrival
  if serverSpan > targetMs + STOP_GRACE_MS:
      member.rank = LOWEST_GROUP(reason = STOP_MISSING); return
  if reportedElapsedMs < 0 or reportedElapsedMs > targetMs + STOP_GRACE_MS:
      member.rank = LOWEST_GROUP(reason = OUT_OF_RANGE); return
  if abs(serverSpan - reportedElapsedMs) > TOLERANCE_MS:
      member.rank = LOWEST_GROUP(reason = OUT_OF_RANGE); return
  member.elapsedMs = reportedElapsedMs      # 정수 밀리초
```

- **양방향 비교다.** 신고값이 기준 구간보다 크다고 해서 곧바로 거짓은 아니다 — START 메시지가 STOP 메시지보다 느리게 도착하면 기준 구간이 실제 경과 시간보다 짧아진다. 한쪽만 검사하면 정상 입력을 거부한다.
- 거부는 오류 통지가 아니라 **최하위군 편입**으로 처리한다. 판을 멈추지 않기 위해서이며, 미입력 처리와 같은 자리에 놓인다([../05_game_rules/01_common.md](../05_game_rules/01_common.md)의 미입력 처리).
- 허용 범위(TOLERANCE_MS) · 시작 지연 상한(START_DEADLINE_MS) · 정지 여유(STOP_GRACE_MS)의 구체 값은 [../04_architecture/README.md](../04_architecture/README.md)의 시간과 타이밍 문서가 확정한다. 목표 시간과 개인 제한 시간의 값은 D-37이 정한다.

### 안전성 논증

이 예외가 무엇을 막고 무엇을 못 막는지를 정확히 적는다.

| 조작 | 결과 | 근거 |
|------|------|------|
| 경과 시간을 목표 시간과 똑같이 꾸며 신고 | 신고값과 기준 구간의 차이가 허용 범위를 넘으면 거부된다 | 사람의 실제 오차가 허용 범위보다 크면 조작 폭도 그만큼 커져 검출된다 |
| 시스템 시각을 바꿔 경과 시간을 왜곡 | 통하지 않는다 | 측정에 단조 시계를 쓰므로 벽시계 변경이 값에 반영되지 않는다 |
| STOP을 늦게 보내 시간을 벌기 | 통하지 않는다 | 개인 제한 시간(목표 + 여유) 통과 여부는 **서버 도착 시각**으로 판정한다 |
| START를 보내지 않고 기다리기 | 통하지 않는다 | 시작 지연 상한을 넘기면 최하위군이다 |
| STOP을 여러 번 보내 유리한 값 고르기 | 통하지 않는다 | 최초 1회만 인정한다(D-08) |
| **허용 범위 안에서 신고값을 밀기** | **막지 못한다** | 아래 잔여 위험 |

**남는 조작 여지가 있다.** 허용 범위는 지터가 만드는 정상적인 어긋남을 흡수하기 위해 존재하므로, 그 범위 안에서 신고값을 옮기는 조작은 정상 입력과 구분되지 않는다. 허용 범위를 좁히면 정상 입력의 오거부가 늘고 넓히면 조작 여지가 는다 — 이 맞바꿈이 예외의 대가다.

**그럼에도 예외를 두기로 한 판단의 근거**는 셋이다. 첫째, 조작을 완전히 막는 유일한 대안은 서버 도착 시각을 그대로 쓰는 것인데 그러면 **모든 참가자가 회선 변동만큼 무작위로 기록이 흔들린다** — 소수의 조작자를 막으려고 전원의 기록을 망가뜨리는 맞바꿈이다. 둘째, 조작에는 브라우저 개발자 도구로 페이로드를 고칠 수 있는 참가자가 필요하고, 그 참가자는 이미 같은 자리에 있는 팀원이며 얻는 것은 5~10초짜리 판 하나의 승패다. 셋째, 판정 기준이 방장 설정에 따라 **가장 먼 사람**일 수도 있어(D-37) 조작해야 할 방향이 자명하지 않다. 이 잔여 위험은 [05_threat_model.md](./05_threat_model.md)에 등재한다.

## 난수와 시드

- 서버는 라운드마다 **64비트 시드**를 하나 뽑는다. 시드의 출처는 운영체제가 제공하는 암호학적 난수이며, 방 코드·참가자 수·시각처럼 예측 가능한 값에서 유도하지 않는다.
- 시드로 초기화한 **결정적 의사난수 생성기**에서 필요한 값을 정해진 순서로 소비한다. 같은 시드와 같은 입력이면 같은 결과가 나온다.
- 균등 분포가 필요한 자리(당첨자 선택·순열 추출·안건 섞기)에서는 나머지 연산 편향을 없애려 거부 표본추출을 쓴다. 의사코드는 [../05_game_rules/01_common.md](../05_game_rules/01_common.md)에 있다.
- **시드는 결과와 함께 저장되며 방이 사라질 때 함께 삭제된다**(D-44). 저장된 시드로 판정을 다시 돌려 같은 결과가 나오는지 확인할 수 있다.
- 시드를 소비하는 자리는 게임마다 정해져 있고 순서가 고정된다. 순서가 흔들리면 같은 시드로 다른 결과가 나와 재현이 성립하지 않는다.

| 게임 | 시드를 소비하는 자리 |
|------|--------------------|
| 운명의 룰렛 | 당첨자 인덱스 1회 |
| 사다리타기 | 참가자→항목 순열 1회 · 그 순열을 만들어 내는 가로선 배치 |
| 킹메이커 | 안건 표시 순서 섞기 1회(결선마다 다시) |
| 익명 저격 | 유효표가 0일 때의 확정 1회 |
| 시간초 잡기 | 없다 |
| 눈치게임 | 없다 |

**클라이언트는 판정에 쓰는 난수를 만들지 않는다.** 룰렛 회전 각도·사다리 가로선 좌표처럼 화면에 그리는 값도 서버가 준 결과와 시드에서 결정적으로 계산한다.

## 결과 동시 전달

| 장치 | 내용 |
|------|------|
| 단일 페이로드 | 결과는 **한 번의 브로드캐스트**로 같은 페이로드가 전원에게 나간다. 참가자별로 다른 결과·다른 시점을 만들지 않는다 |
| 커밋 후 전송 | 확정 결과를 저장하는 트랜잭션이 커밋된 뒤에만 이벤트를 발행한다. 일부에게만 전달된 뒤 되돌아가는 상태를 만들지 않는다 |
| 단일 인스턴스 | 백엔드는 단일 인스턴스·워커 1개이므로 브로드캐스트 순서가 한 프로세스 안에서 정해진다 |
| 부분 공개 금지 | 진행 중 중간 집계를 누구에게도 보내지 않는다(D-09). 방장에게도 같다 |
| 순차 공개 금지 | 사다리는 전원 경로를 동시에 공개한다(D-29). 순차 공개는 먼저 확정된 사람이 남은 후보를 역산하게 만든다 |
| 전환 시점 통일 | 결과 공개 시점부터 3초 뒤 전원이 결과 화면으로 넘어간다(D-41). 전환 시각을 서버가 지정한다 |

**전송 시각과 도착 시각은 다르다.** 서버가 같은 순간에 보내도 각자의 회선 상태에 따라 화면에 뜨는 순간은 어긋난다. 구 스펙 NFR-02의 "결과 전환 시각 편차 0.5초 이내"는 **설계 목표치이며 실측으로 확인해야 하는 값**이다. 이 문서는 그것이 이미 달성됐다고 적지 않는다.

"먼저 아는 사람을 만들지 않는다"의 실질은 밀리초 단위의 전달 동시성이 아니라 **결과를 미리 알 수 있는 경로를 하나도 두지 않는 것**이다. 중간 집계 비공개 · 개표 전 익명 유지 · 방장 열람 특권 부재 · 순차 공개 폐기가 그 경로들을 닫는다.

**한 가지 예외 상태를 등재한다.** 룰렛·사다리는 서버가 결과를 먼저 확정해 연출 시작 시점에 클라이언트로 내려보내므로, 개발자 도구로 통신 내용을 보면 연출이 끝나기 전에 결과를 알 수 있다. 연출 종료 시점에 결과를 보내는 대안은 그 시점의 연결 상태에 결과 도달이 걸리게 만들어 더 나쁘다. 두 게임은 참가자 입력이 결과에 개입하지 않으므로 미리 알아도 판정을 바꿀 수 없고, 알게 되는 것은 3~5초 뒤 어차피 공개될 값 하나다. **수용하되 유출 경로로 등재한다**([05_threat_model.md](./05_threat_model.md)).

## 네트워크 지터가 결과에 들어가는 폭

서버 도착 시각 기준은 **클라이언트가 시각을 꾸며 내는 것**을 막는다. 그러나 **메시지가 서버에 닿기까지 걸린 시간의 차이**는 그대로 판정에 들어간다. 두 위협은 다르고 서버 판정은 앞의 것만 해결한다.

정확히 말하면 결과에 들어가는 것은 지연의 절대값이 아니라 **참가자 사이의 지연 차이와 그 차이의 시간적 변동**이다. 전원의 지연이 같으면 눈치게임의 그룹핑은 완전히 같은 결과를 낸다.

| 게임 | 판정 단위 | 지터가 결과를 바꿀 수 있는가 | 폭 |
|------|----------|---------------------------|-----|
| 운명의 룰렛 | — | 아니다 | 실행 신호의 도착 시각이 추첨에 들어가지 않는다 |
| 사다리타기 | — | 아니다 | 같다 |
| 킹메이커 | 제출 2분 · 투표 1분 · 결선 30초 | 마감 경계에서만 | 마감 직전에 보낸 입력이 마감 뒤에 도착하면 버려진다. 득표 계산에는 시각이 들어가지 않는다 |
| 익명 저격 | 투표 5~60초(기본 10초) | 마감 경계에서만 | 같다. 기본 10초에서 수백 밀리초의 지연은 마감의 수 퍼센트다 |
| 시간초 잡기 | 순위는 밀리초 · 마감은 초 | **순위에는 들어가지 않는다** | 경과 시간을 클라이언트 단조 시계가 재기 때문이다(D-07). 남는 영향은 두 가지 — 마감 경계 판정과, 지터가 허용 범위를 넘도록 클 때의 오거부다 |
| 눈치게임 | **판정창 0.3초 또는 0.5초** | **들어간다** | 아래 상세 |

### 눈치게임에서 지터가 그룹핑을 바꾸는 조건

두 참가자의 실제 클릭 간격을 Δt, 편도 지연의 차이를 δ라 하면 서버가 관측하는 간격은 Δt + δ다. 판정창을 W라 할 때 그룹핑이 뒤집히는 조건은 다음이다.

```
실제로는 갈라져야 하는데 겹쳐 보인다:   Δt > W  이면서  Δt + δ ≤ W      (δ < 0, |δ| > Δt − W)
실제로는 겹쳐야 하는데 갈라져 보인다:   Δt ≤ W  이면서  Δt + δ > W      (δ > 0, δ > W − Δt)
```

즉 **실제 간격이 판정창 경계에서 |δ| 이내에 있을 때만 뒤집힌다.** 판정창 0.3초는 통상적인 지연 차이보다 큰 단위로 잡은 값이며, 그것이 판정창을 밀리초가 아니라 수백 밀리초 단위로 둔 이유다. 그러나 다음 두 가지는 정직하게 적는다.

1. **뒤집힘 확률이 0은 아니다.** 셀룰러 재전송이나 일시적 혼잡으로 한 참가자의 지연이 순간적으로 튀면 δ가 판정창에 근접하거나 넘을 수 있고, 그때의 그룹핑은 실제 클릭 순서와 다르다.
2. **"느린 회선이 불리하다"는 이 게임에서 정확한 서술이 아니다.** 그룹핑은 절대 시각이 아니라 간격으로 판정하므로 일정한 지연은 상쇄된다. 결과를 흔드는 것은 지연의 크기가 아니라 **변동**이며, 변동이 큰 회선은 유리한 쪽으로도 불리한 쪽으로도 흔들린다.

라운드 마감(10 · 15 · 20초) 통과 여부에는 절대 지연이 들어간다. 마감 직전에 누르면 느린 참가자가 미입력으로 처리될 수 있으며, 폭은 지연(수십~수백 밀리초)과 마감(10~20초)의 비율이다.

### 이 절의 수치에 대한 유보

편도 지연·지터의 구체적인 크기는 **설계 전제로 잡은 값이지 실측이 아니다.** 판정창 0.3초가 실제 사용 환경의 지연 차이보다 충분히 큰지는 배포 전 실측으로 확인해야 하며, 확인 결과에 따라 판정창 기본값을 바꿀 수 있다. 이 문서는 실측하지 않은 수치를 검증된 사실로 단정하지 않는다.
