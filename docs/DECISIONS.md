## A. 방 · 입장

### D-01
**초대코드는 `MODU-` + 숫자 정확히 4자리**

- **상태**: ✅ 확정 (2026-07-26)
- **결정**: `MODU-4271` 형식. 참여자는 뒤 4자리만 입력한다. 직접 설정 불가, 서버 자동 발급.
  API 경로·소켓 룸키에는 접두어 없이 4자리 숫자만 전달한다 (`/api/rooms/4271`, `room:4271`).
- **근거**: `legacy/design.md:93-95`가 4자리를 규정하며 5·6자리를 명시적으로 금지. `legacy/design.md:176`에는 "참여자본 방코드 `427132`(6자리) → `MODU-####` 4자리"라는 **교정 지시**가 기록돼 있어 6자리가 이미 초안의 결함으로 판정된 상태였다. 원본 기획 `legacy/document.md:21-22`도 4자리.
- **폐기**: `legacy/api.md:82` "`MODU-` + 6자리(`MODU-427132`)" 및 파일 전반의 6자리 예시.
- **영향**: [`06_api/01_rest.md`](06_api/01_rest.md) · [`06_api/02_socket.md`](06_api/02_socket.md) · [`07_design/00_foundation.md`](07_design/00_foundation.md)

### D-02
**4자리 코드의 유일성·재사용 정책**

- **상태**: ✅ 확정 (2026-07-26)
- **결정**: 코드 공간은 `0000`~`9999` (10,000개). **활성 방끼리만 유일**하면 된다.
  발급 시 활성 코드와 충돌하면 재추첨하고, 방이 만료·폭파되면 코드를 즉시 회수해 재사용한다.
- **근거**: D-01이 4자리를 확정하면서 새로 필요해진 규칙. 원본 문서 어디에도 없었다.
  방 수명이 짧고([D-03](#d-03)) 동시 활성 방 수가 수천 단위에 이를 일이 없는 팀 프로젝트 도구라 4자리로 충분하다.
- **주의**: 동시 활성 방이 10,000개에 근접하면 발급이 실패한다. 이 경우 `ROOM_CODE_EXHAUSTED`로 응답하고 코드 자릿수 확장을 재논의한다.
- **영향**: [`06_api/01_rest.md`](06_api/01_rest.md) · [`03_architecture/01_data_model.md`](03_architecture/01_data_model.md)

### D-03
**방 만료 = ACTIVE 소켓 0명 상태가 10분 지속**

- **상태**: ⚠️ **승인 대기** — 기본안으로 표기함
- **기본안**: 방에 연결된 소켓이 하나도 없는 상태가 10분 이어지면 방을 삭제한다.
  전원에게 `room:closed { reason: "EXPIRED" }`를 보낼 대상이 없으므로 조용히 삭제된다.
- **근거**: `legacy/api.md:50`의 `ROOM_EXPIRED`("10분 무요청 만료")와 `:107`의 `expiresAt`이 유일한 출처인데, **"무요청"이 무엇인지 정의돼 있지 않았다.** 참조로 적힌 "기획 ①"에 해당하는 문서도 존재하지 않는다.
- **왜 승인이 필요한가**: "무요청"의 해석에 따라 동작이 완전히 달라진다.
  - (A) **기본안** — 소켓 0명 10분. 사람이 있는 방은 몇 시간이든 유지된다.
  - (B) 방 생성 후 10분 절대 만료. `legacy/api.md:107`의 `expiresAt`(생성 +10분)은 이쪽을 시사하는데, 게임 한 판이 10분을 넘으면 진행 중에 방이 사라진다.
  - (C) 만료 규칙 폐기. 방장이 나가면 어차피 폭파되므로([D-05](#d-05)) 별도 만료가 불필요하다는 입장.
- **영향**: [`03_architecture/01_data_model.md`](03_architecture/01_data_model.md) · [`06_api/01_rest.md`](06_api/01_rest.md) · [`06_api/03_error_codes.md`](06_api/03_error_codes.md)

### D-04
**재접속 없음 — 소켓이 끊기면 즉시 퇴장**

- **상태**: ⚠️ **승인 대기** — 기본안으로 표기함
- **기본안**: 소켓 연결이 끊기면 서버는 해당 멤버를 방에서 즉시 제거한다. 같은 토큰으로 다시 붙는 경로는 없다. 새로고침하면 방에서 빠진다.
- **근거**: `legacy/api.md:365-368`(2026-07-24 수정본)이 "**재접속 개념이 없다는 게 이 설계의 핵심**"이라고 설계 의도를 명시. 상태 복구 로직이 없어 구현이 크게 단순해진다.
- **폐기된 상충 서술**:
  - `legacy/games.md:248` "게임 진행 중 새로고침해도 입력 상태를 초기화하지 않는다" — 기본안과 정면 충돌
  - `legacy/games.md:68` · `legacy/design.md:194` — 재접속이 존재한다는 전제의 문구
  - `legacy/api.md:281`(구 초안) "재접속 시 `GET /rooms/{code}/state`" — 해당 엔드포인트는 REST 표에 존재조차 하지 않았다
- **왜 승인이 필요한가**: "새로고침 한 번이면 방에서 빠진다"는 UX 리스크가 크다. 발표 시연 중 사고로 이어질 수 있다.
  - (A) **기본안** — 재접속 없음. 프론트가 이탈 경고(`beforeunload`)를 띄워 완화한다.
  - (B) 15~30초 grace period. 끊긴 멤버를 즉시 지우지 않고 대기 큐에 두었다가 같은 토큰이 돌아오면 복귀시킨다. 서버에 이탈 대기 큐가 필요하다.
  - (C) 게임 중(`PLAYING`)에만 재연결 허용, 대기방은 즉시 퇴장. 리스크가 큰 구간만 방어하는 절충.
- **영향**: [`05_game_rules/00_common.md`](05_game_rules/00_common.md) · [`06_api/02_socket.md`](06_api/02_socket.md) · [`03_architecture/01_data_model.md`](03_architecture/01_data_model.md)

### D-05
**방장이 나가면 방 폭파 · 게스트 토큰 수명은 방 수명과 동일**

- **상태**: ✅ 확정 (2026-07-26)
- **결정**: 방장이 `DELETE /members/me`를 호출하면 전원에게 `room:closed { reason: "HOST_LEFT" }`를 보내고 방을 삭제한다. 토큰은 방에 종속되므로 방이 사라지면 함께 무효가 된다. 별도 만료 시간을 두지 않는다.
- **근거**: `legacy/api.md:202`(방장 퇴장 = 방 폭파) + `legacy/document.md:44`("방장은 나가기 버튼을 클릭하여 방을 아예 무효화(폭파)"). 토큰 수명은 원본에 정의가 없어(`legacy/api.md:63` `SESSION_EXPIRED`만 존재) 여기서 새로 정한다.
- **영향**: [`06_api/01_rest.md`](06_api/01_rest.md) · [`06_api/03_error_codes.md`](06_api/03_error_codes.md)

## B. 데이터

### D-06
**데이터 저장 3계층 — 런타임은 서버 인메모리, PostgreSQL은 정적 메타만**

- **상태**: ⚠️ **승인 대기** — 기본안으로 표기함
- **기본안**:

  | 계층 | 저장 대상 | 수명 |
  |---|---|---|
  | 서버 인메모리 | 방 · 멤버 · 라운드 · 게임 상태 · 채팅 링버퍼 50건 | 방 삭제까지 |
  | PostgreSQL | 게임 메타 6종 · 아바타 카탈로그 15종 | 영구(정적) |
  | 클라이언트 로컬스토리지 | 내 채팅 기록 | 브라우저 세션 |

- **근거**: `legacy/document.md:7`("DB 존재 없음 — 네이버 사다리타기처럼 일회성") + [D-04](#d-04) 재접속 없음 + [D-03](#d-03) 방 만료 → 방·멤버·라운드를 영속할 이유가 없다. `legacy/api.md:653`이 채팅 미영속을 이미 확정했다.
- **해소한 모순**: `legacy/api.md:494`의 `room:snapshot.messages` 50건과 `legacy/api.md:653`의 "로컬스토리지 저장"은 모순으로 보였으나 **층이 다르다.** 서버 링버퍼는 *방에 있는 전원이 공유하는* 최근 50건이고, 로컬스토리지는 *내가 게임 후 되돌아봤을 때 복원할* 클라이언트 캐시다. 둘 다 필요하며 충돌하지 않는다.
- **왜 승인이 필요한가**: `legacy/techstack.md:23`이 PostgreSQL을, `:27`이 K8s를 확정했다. **다중 파드에서 인메모리 상태는 깨진다.**
  - (A) **기본안** — 서버 **단일 인스턴스** 전제. K8s `replica=1`로 고정하고 그 제약을 명시한다. 팀 프로젝트 규모에서는 충분하다.
  - (B) Redis를 방 상태 저장소로 추가. 수평 확장이 가능해지지만 학습·운영할 스택이 1종 늘어난다.
  - (C) PostgreSQL에 방·멤버·라운드까지 영속. `legacy/document.md:7`의 "DB 없음" 기조를 폐기하는 대신 재접속([D-04](#d-04) B안)이 쉬워진다.
- **영향**: [`03_architecture/00_tech_stack.md`](03_architecture/00_tech_stack.md) · [`03_architecture/01_data_model.md`](03_architecture/01_data_model.md)

### D-07
**채팅은 영속하지 않는다**

- **상태**: ✅ 확정 (2026-07-24, 팀 결정 — `legacy/api.md:653`)
- **결정**: 채팅을 DB에 저장하지 않는다. 서버는 최근 50건만 메모리에 들고 있다가 `room:snapshot`으로 내려준다. 그보다 과거 메시지를 불러오는 기능은 없다. 대기방에서 채팅 → 게임 시작 → 게임 종료 후 대기방 복귀 시, 클라이언트가 **로컬스토리지에 보관한 자기 기록**을 복원해 보여주는 것은 가능하다.
- **근거**: `legacy/api.md:653` 원문 — "채팅을 따로 DB에 저장하지 않고 로컬 스토리지에 저장하기 때문. 대기방에서 채팅하다가 게임시작-게임 끝 이후 로컬에 저장되어있던 채팅을 불러오는건 가능"
- **영향**: [`03_architecture/01_data_model.md`](03_architecture/01_data_model.md) · [`06_api/02_socket.md`](06_api/02_socket.md)

### D-10
**게임 가이드 팝업 — 자동 노출본은 `✕` 비활성 · 3초 강제**

- **상태**: ⚠️ **승인 대기** — 기본안으로 표기함
- **기본안**: 방장이 게임을 시작하면 전원 화면에 가이드가 뜨고, **3초 카운트다운이 끝날 때까지 닫을 수 없다.** 게임 진행 중 좌상단 `?`로 다시 열었을 때는 `✕`로 언제든 닫힌다.
- **근거**: `legacy/games.md:43`("x 버튼 클릭으로도 팝업창을 지울 수 없다"). `legacy/design.md:189`가 이미 충돌을 인지하고 "전원 규칙 숙지 보장"을 이유로 games.md를 채택해 뒀다.
- **상충**: `legacy/document.md:55-56`("x 버튼을 클릭하면 팝업창은 곧바로 사라진다 + 3초 뒤 자동")
- **왜 승인이 필요한가**: 3초 강제 대기는 **재시작을 반복할 때 성가시다.** 같은 게임을 5번 돌리면 매번 3초를 기다린다.
  - (A) **기본안** — 3초 강제. 전원이 규칙을 보게 만든다.
  - (B) `✕` 즉시 닫기 허용(`legacy/document.md`). 규칙을 모르는 참가자가 생길 수 있다.
  - (C) 절충 — 같은 방에서 같은 게임 2회차부터는 `✕` 활성. [D-17](#d-17)의 "다시 보지 않기" 체크박스와 함께 두면 자연스럽다.
- **영향**: [`04_requirements/00_user_flow.md`](04_requirements/00_user_flow.md) · [`05_game_rules/00_common.md`](05_game_rules/00_common.md) · [`07_design/00_foundation.md`](07_design/00_foundation.md)
