본 문서는 화면 명세 6본(03~06)이 공통 인용하는 규격이다. 각 화면 명세는 여기서 정한 템플릿·용어·패턴을 그대로 따르며, 개별 화면이 표준과 다른 처리를 두면 그 화면 명세의 비고에 사유를 남긴다. 화면 코드 12본과 요소 13종의 정본은 [README.md](./README.md)이고 본 문서는 그것을 화면 설계 규격으로 옮긴다.

**본 문서는 설계 정본이다.** 반응형 규격(§5)은 현재 frontend/src의 구현과 정면으로 어긋나며, 이 경우 구현을 고친다.

## 1. 접근 권한 규약

### 1-1. 권한 축

ModuPick에는 로그인·계정이 없다. 권한을 가르는 축은 **방 안에 있는가**와 **방장인가** 둘뿐이다.

| 값 | 정의 | 판정 근거 |
|----|------|-----------|
| 방 밖 | 어떤 방에도 속하지 않은 상태. 토큰이 없다 | 참가자 토큰 부재 |
| 슬롯 선점 | 코드 검증을 통과해 자리를 잡았으나 프로필을 확정하지 않은 상태 | 대기 상태 멤버 |
| 참가자(Member) | 프로필을 확정해 명단에 오른 사람 | 활성 상태 멤버 |
| 방장(Host) | 방을 만든 사람. 참가자 권한 전부를 포함한다 | 방이 보유한 방장 멤버 식별자 |

- 화면 명세의 접근 권한 칸은 위 값으로 적고, 같은 화면에서 방장과 참가자의 보이는 것이 다르면 **방장 … / 참가자 …** 형식으로 나눠 적는다.
- **역할 계층은 방장 ⊃ 참가자 2단이다.** 관전자·부방장·운영자를 두지 않는다. 게임이 시작되면 새 입장을 받지 않으므로 방에 있는 사람은 전부 후보다.
- 권한 판정의 정본은 [../02_features/08_permission_matrix.md](../02_features/08_permission_matrix.md)다. 본 문서는 그 판정을 화면 표면 규격으로만 옮긴다.

### 1-2. 화면 노출 제어는 권한 경계가 아니다

방장 전용 버튼을 참가자 화면에서 감추거나 비활성화하는 것은 **사용성 장치**다. 권한 경계는 서버에 있고, 감춘 표면을 직접 호출해도 서버가 같은 조건을 다시 검사해 거부한다. 화면 명세는 두 가지를 함께 적는다 — 무엇을 감추는가와 서버가 어디서 다시 검사하는가.

**참가자에게는 감추지 않고 비활성 + 사유 표시로 둔다.** 버튼 자체를 지우면 참가자는 그 동작이 존재하는지도 모른 채 방장이 무엇을 하고 있는지 알 수 없다. 게임 선택·설정·시작·다시 하기가 여기에 해당하며, 비활성 상태에 "방장이 고르는 중" 같은 사유를 함께 표시한다.

### 1-3. 조용한 거부

권한 위반의 통지는 **보낸 사람에게만** 간다. 브로드캐스트하지 않으므로 다른 참가자의 화면은 흔들리지 않는다. 화면에서는 토스트 한 줄로 처리하고 화면 전환·상태 변경을 하지 않는다.

## 2. 화면 명세 템플릿

### 2-1. 화면 블록

각 도메인 파일의 화면 명세는 아래 블록 구조를 따른다. H2는 **{화면코드} — {화면명}** 으로 고정하고 블록 내부에 H3를 두지 않는다(H3는 §2-2 요소 블록 전용). 블록 사이에는 구분선을 넣는다.

```
## {화면코드} — {화면명}

| 항목 | 내용 |
|------|------|
| 화면코드 | {도메인}-{의미} |
| 진입 조건 | screen 값 (+ selectedGame 값) |
| 접근 권한 | 방장 … / 참가자 … |
| 우선순위 | P0~P2 |
| 구현 상태 | ⬜ / 🔶 / ✅ |

**목적**: 한 줄 요약.

**진입경로**: 어디에서 어떤 조작으로 들어오고 어디로 나가는가.

**화면 기능**

| 기능 | UI/처리 | 기능ID |
|------|---------|--------|
| 기능명 | 처리 방식 | F-XXX-NN |

**주요 UI 요소**: 폼·목록·그리드·카드·버튼·오버레이 등 구성 요소 열거.

**레이아웃·스크롤·모바일**: 데스크톱 배치와 스크롤 소유자(§6), 360px 배치(§5).

**상태 처리**

| 상태 | 처리 |
|------|------|
| 로딩 | … |
| 빈 상태 | … |
| 에러 | {namespace}.{snake_case} / HTTP |
| 권한거부 | … |

**데이터 연동**

- 액션 → 이벤트·API → 서버 처리.

**담은 기능ID**: F-XXX-NN 열거.

**비고**: 엣지·설계 판단 근거·구현 정정 대상.
```

- **요구사항ID 열은 두지 않는다.** REQ 채번 정본은 [../03_requirements/README.md](../03_requirements/README.md)이며 화면 문서가 REQ를 채번하거나 추정하지 않는다. 에러 코드도 마찬가지로 [../10_glossary/02_error_codes.md](../10_glossary/02_error_codes.md)가 채번한 값을 참조만 한다.
- **상태 처리 4행은 전 행을 채운다.** 해당 없으면 "해당 없음"과 사유를 적고 행을 지우지 않는다. 규약은 §4가 정한다.
- 담은 기능ID는 그 화면이 표면을 갖는 기능을 빠짐없이 적는다. 서버 전용이라 화면에 직접 UI가 없는 기능은 **(서버)** 를 병기한다.

### 2-2. 화면 내 요소 블록

[README.md](./README.md)의 요소 13종은 화면코드·진입 조건 축이 없으므로 아래 축약 블록을 쓴다.

```
### {소속 화면코드} 내 요소 — {요소명}

**노출 조건**: 언제 어떤 조작으로 열리고 닫히는가.

**기능**

| 기능 | UI/처리 | 기능ID |
|------|---------|--------|

**주요 UI 요소**: 구성 요소 열거.

**상태·에러**: 로딩·빈 상태·에러·권한거부를 한 단락으로 기술한다.

**데이터 연동**: 액션 → 이벤트·API → 서버 처리.
```

요소 블록은 소속 화면 블록 바로 뒤에 H3로 붙인다 — **화면 인벤토리 집계는 {화면코드} — {화면명} 형식의 H2만 세므로** 요소가 화면 수에 섞이지 않는다. 여러 화면이 공유하는 요소(게임 가이드·방장 이탈 안내 등)는 **대표 소속 화면 뒤에 한 번만** 적고 다른 화면 명세는 그 위치를 가리킨다.

**요소 13종 중 11종이 이 블록을 갖는다.** 나머지 둘(전역 토스트 · 상태 밴드)은 소속 화면이 하나로 정해지지 않는 전역 요소라 블록 대신 §3 공통 패턴 표와 §8 디자인 토큰이 규격을 확정한다. 11 + 2 = 13이다.

## 3. 공통 패턴

전 화면이 아래를 공통 인용한다. 개별 화면 명세는 이 표를 다시 설명하지 않고 화면별 차이만 적는다.

| 패턴 | 원칙 |
|------|------|
| 화면 셸 | 배경 그리드 + 굵은 잉크 보더 + 네 모서리 핑크 코너칩. frontend/src/components/ui.tsx의 Shell이 전 화면에 공통으로 깔린다 |
| 화면 헤더 | 좌측에 제목(굵은 제목 서체) + 영문 라벨 + 부제, 우측에 상태 배지·방 코드·나가기. 게임 화면은 제목 옆에 가이드 재열기 버튼을 둔다 |
| 상태 밴드(HUD) | 화면 하단 고정 밴드. 좌측에 단계 표시 + 현재 상태 문구 + 보조 설명, 우측에 그 화면의 주 동작 버튼을 모은다. **화면의 주 CTA는 항상 상태 밴드 안에 있다** |
| 결과 수렴 연출 | 클라이언트 애니메이션은 **서버가 이미 확정한 결과로 수렴**할 뿐이다. 연출의 길이·속도 설정은 결과를 바꾸지 못한다(D-05) |
| 중간 집계 비공개 | 입력이 진행되는 동안 득표 수·기록·순위를 아무에게도 보이지 않는다. **완료·대기 상태만** 보인다(D-09). 방장에게도 같다 |
| 남은 시간 표시 | 서버가 단계 마감 시각을 내려주고 클라이언트가 그 시각까지 남은 시간을 그린다. 클라이언트가 마감을 스스로 정하지 않는다 |
| 오버레이 단일 레이어 | 오버레이 위에 오버레이를 띄우지 않는다 — §3-1 |
| 전역 토스트 | 화면 상단 중앙, 잉크 배경 · 흰 글자, 2.4초 뒤 자동 소멸. 복사 완료·저장 완료·조용한 거부를 통지한다. 동시에 하나만 띄운다 |
| 확인 모달 | 되돌릴 수 없는 동작(강퇴 · 방 삭제 · 나가기)에만 확인 단계를 둔다. 그 외에는 바로 실행하고 토스트로 알린다 |
| 아바타 표기 | 아바타는 퍼슨 컬러 원판 안의 캐릭터 이미지 한 벌로 통일한다. **이모지 대체 표기를 쓰지 않는다** |
| 익명 표기 | 킹메이커 제출자·저격 지목자는 개표 전에 어떤 화면에서도 드러나지 않는다. 익명 구간에서는 아바타·퍼슨 컬러도 표시하지 않는다 — 색만으로 사람이 식별되기 때문이다 |
| 이탈자 표기 | 게임 도중 이탈한 참가자는 명단에서 지우지 않고 이탈 표시와 함께 남긴다(D-15·D-18) |
| 한국어 카피 톤 | 평서·존중 톤. 뽑힌 사람에게 벌칙·낙인 문안을 쓰지 않고, 미입력·이탈은 사실만 적는다 |

### 3-1. 오버레이 단일 레이어 규약

**화면에 동시에 존재하는 오버레이 레이어는 항상 하나다.**

| 항목 | 규격 |
|------|------|
| 중첩 금지 | 오버레이가 열린 상태에서 다른 오버레이를 열지 않는다. 열려 있는 것을 닫고 여는 방식도 쓰지 않는다 |
| 우선순위 | 방장 이탈·방 삭제 안내가 최우선이다. 다른 오버레이가 열려 있으면 그것을 치우고 대체한다 — 방이 사라진 뒤에는 다른 확인이 의미를 잃기 때문이다 |
| 확인 단계 | 오버레이 안에서 확인이 필요하면 같은 레이어의 상태 전환으로 처리하고 제출 중에는 버튼을 잠근다 |
| 무스크롤 | 오버레이 내부에 스크롤을 만들지 않는다. 넘치면 담을 정보를 줄이거나 단계를 나눈다. 유일한 예외는 게임 가이드 모달이며 §3-2를 따른다 |
| 배경 | 배경을 잉크 62% 딤으로 덮고 배경 스크롤을 잠근다. 포커스를 오버레이 안으로 옮겨 트랩하고 Esc로 닫으며 닫을 때 트리거로 포커스를 되돌린다 |
| 닫기 경로 | 확인이 필요한 오버레이(강퇴·방 삭제·나가기)는 배경 클릭으로 닫히지 않는다. 안내만 하는 오버레이는 배경 클릭·Esc로 닫힌다 |

### 3-2. 게임 가이드 모달의 예외

가이드는 단계 수가 게임마다 다르다(2~4단계). 360px에서 4단계 카드가 세로로 쌓이면 뷰포트를 넘길 수 있으므로 **가이드 모달에 한해 본문 영역의 세로 스크롤을 허용한다.** 헤더·자동 시작 버튼은 스크롤 밖에 고정해 항상 닿을 수 있게 한다.

### 3-3. 나가기 경로

나가기는 두 갈래이며 **문구와 결과가 다르다.** 같은 버튼을 역할에 따라 다른 확인 오버레이로 연결한다.

| 주체 | 확인 문구 | 결과 |
|------|-----------|------|
| 방장 | 방이 사라지고 전원이 표지로 이동한다는 경고 | 방 삭제 · 진행 중이던 판은 결과 없이 종료 · 전원에게 방장 이탈 안내 |
| 참가자 | 다시 들어오려면 코드를 새로 입력해야 한다는 안내 | 본인만 표지로 이동. 게임 중이면 후보로 남아 미입력 처리 |

## 4. 상태 처리 4종

전 화면 명세가 **로딩 · 빈 상태 · 에러 · 권한거부** 네 행을 모두 채운다. 해당 없으면 "해당 없음"과 사유를 적고 행을 지우지 않는다.

| 상태 | 적용 규격 |
|------|-----------|
| **로딩** | 소켓 스냅샷이 도착하기 전 구간을 말한다. 실제 콘텐츠의 레이아웃을 따라가는 스켈레톤을 쓰고 전체 화면 스피너를 쓰지 않는다. **제출 중 로딩은 버튼 안에서 처리한다** — 버튼을 비활성으로 바꾸고 진행 표시를 넣어 중복 제출을 막는다 |
| **빈 상태** | 데이터가 없어도 화면이 정상 표시되고 다음 행동을 안내한다. **없어서 빈 것과 조건 때문에 빈 것을 문안으로 구분한다** — 참가자가 아직 안 들어온 것과 인원이 모자라 게임을 못 고르는 것은 다른 문안이다 |
| **에러** | {namespace}.{snake_case} + HTTP 상태를 받아 사람이 읽는 문구로 바꿔 보여 준다. **입력값을 지우지 않는다.** 입력 자리에서 난 오류는 그 입력 옆에, 화면 전체에 걸린 오류는 상태 밴드에, 일시적 실패는 토스트에 띄운다. 코드 자체를 화면에 노출하지 않고 문의용으로만 남긴다 |
| **권한거부** | 방장 전용 동작을 참가자가 시도한 경우다(member.not_host). 조용한 거부(§1-3)로 처리해 **보낸 사람에게만** 토스트를 띄우고 화면 상태를 바꾸지 않는다. 애초에 그 버튼은 비활성 + 사유 표시 상태였어야 한다 |

**연결 끊김은 네 상태와 별개다.** 소켓이 끊기면 재접속 경로가 없으므로(D-17) 로딩으로 되돌리지 않고 방이 끝났음을 알리는 안내로 넘긴다. 화면을 붙잡아 둔 채 무한 재시도하지 않는다.

## 5. 반응형 규격

### 5-1. 정면으로 다뤄야 할 충돌

현행 구현과 확정된 제품 결정이 정면으로 어긋난다.

| 축 | 현행 구현 | 확정 결정 |
|----|-----------|-----------|
| 기준 | frontend/src/App.tsx가 **1920×1080 고정 스테이지**를 만들고 transform: scale로 뷰포트에 맞춰 축소한다. 배율은 min(뷰포트폭/1920, 뷰포트높이/1080)이다 | **D-47 모바일 우선** — 360px 폭에서 가로 스크롤 없이 모든 화면이 동작한다. 세로·가로 어느 방향이든 결과와 입력 요소가 잘리지 않는다 |
| 분기 | frontend/src/styles/global.css에 **@media 쿼리가 0개**다. 폭에 따라 배치가 바뀌는 코드가 없다 | **D-48** — 터치 표적의 최소 크기를 요구사항으로 둔다 |
| 원천 | 코드 주석이 "발표 화면 대응"을 근거로 든다 | docs_legacy/requirements.md §4.6 US-601도 같은 요구를 담는다 |

**축소 배율을 실제로 계산하면 충돌의 크기가 드러난다.**

| 기기 | 뷰포트 | 배율 | 본문 18px | 눈치 UP 버튼 300×128 | 시간초 STOP 버튼 900×139 |
|------|--------|:----:|:---------:|:--------------------:|:------------------------:|
| 세로 휴대폰 | 360×640 | **0.1875** | 3.4px | **56.3 × 24.0px** | **168.8 × 26.1px** |
| 세로 휴대폰(큰 화면) | 390×844 | 0.2031 | 3.7px | 60.9 × 26.0px | 182.8 × 28.2px |
| 가로 휴대폰 | 640×360 | 0.3333 | 6.0px | 100.0 × 42.7px | 300.0 × 46.3px |
| 태블릿 | 834×1112 | 0.4344 | 7.8px | 130.3 × 55.6px | 391.0 × 60.4px |

세로 휴대폰에서 스테이지 전체가 **360×202.5px**로 그려지고 나머지는 잉크색 레터박스가 된다. 44×44 터치 표적은 8.25px가 되고, 순간 입력이 순위를 가르는 눈치게임 UP 버튼의 **높이가 24px**, 시간초 STOP 버튼의 **높이가 26px**가 된다. 두 버튼 모두 스테이지 좌표에서는 넉넉하지만 실제 화면에서는 세로로 표적을 놓친다. 이것은 표시 결함이 아니라 **판정 결함**이다 — 누르지 못해 미입력 처리되는 참가자가 생기고, 그 사람은 규칙이 아니라 화면 때문에 진다.

### 5-2. 설계 판단 — 고정 스테이지를 폐기하고 반응형으로 전환한다

| 안 | 내용 | 판정 |
|----|------|------|
| A | 1920×1080 고정 스테이지를 유지하고 축소로 대응한다 | **폐기.** §5-1의 계산이 D-47·D-48을 동시에 위반한다. 어떤 배율 보정으로도 터치 표적 최소 크기를 만족할 수 없다 |
| B | 고정 스테이지를 유지하고 모바일 전용 화면을 따로 만든다 | **폐기.** 같은 화면의 정본이 둘로 갈라져 한쪽만 고쳐지는 결함이 반드시 생긴다. 화면 12본을 24본으로 세는 축도 생긴다 |
| C | **고정 스테이지를 폐기하고 유동 레이아웃으로 전환한다** | **채택.** 좌표 절대 배치를 흐름 배치로 바꾸고 브레이크포인트 3종으로 분기한다 |

- **발표 화면 용도는 안 C가 그대로 흡수한다.** 데스크톱 구간에서 콘텐츠 최대 폭을 1920px로 두고 가운데 정렬하면 1920×1080 프로젝터에서 지금과 같은 화면이 나온다. 별도 프레젠테이션 모드를 두지 않는다.
- **전환 비용은 화면 명세가 아니라 구현이 진다.** 현행 6개 화면 컴포넌트와 6개 게임 컴포넌트는 좌표 절대 배치(position: absolute + 고정 px)를 쓰고 있어 전면 재작성이 필요하다. 이 사실은 [../01_overview/05_priorities_roadmap.md](../01_overview/05_priorities_roadmap.md)의 구현 정정 목록에 등재한다.

### 5-3. 브레이크포인트 3종

| 구간 | 폭 | 기준 뷰포트 | 성격 |
|------|----|-------------|------|
| **모바일** | 360 이상 768 미만 | 360×640 | 기본. **최소 지원 폭 360px** |
| **태블릿** | 768 이상 1280 미만 | 834×1112 | 2열까지 편다 |
| **데스크톱** | 1280 이상 | 1920×1080 | 3열까지 편다. 콘텐츠 최대 폭 1920px 가운데 정렬 |

- 브레이크포인트는 이 3종만 쓴다. 화면별 임의 픽셀값으로 분기하지 않는다.
- **모바일이 기본 스타일이고 위 구간이 덧붙는 방향으로 작성한다.** 데스크톱을 기본으로 두고 좁히면 입력 요소가 밀려 나는 것을 늦게 발견한다.
- 높이는 100dvh를 기준으로 잡고 env(safe-area-inset-*)를 반영한다. 하단에 고정하는 게임 입력 버튼이 홈 인디케이터에 가리지 않게 한다.
- **가로 방향(landscape)도 지원한다.** 640×360 같은 낮은 높이에서 게임 입력 버튼이 화면 밖으로 나가지 않도록, 게임 화면은 입력 버튼을 먼저 배치하고 남는 높이로 연출 영역을 잡는다.

### 5-5. 터치 표적 규격

D-48은 터치 표적의 최소 크기를 요구사항으로 둔다. 본 문서는 그것을 화면 규격으로 확정한다.

| 대상 | 최소 크기 | 근거 |
|------|-----------|------|
| 모든 조작 가능 요소 | **44 × 44 CSS px** | 손가락 접촉면의 실측 하한 |
| 게임 입력 버튼(STOP · UP · PICK · START · 투표 · 지목) | **폭 100% − 32px · 높이 64px 이상** | 순간 입력이 순위를 가르므로 조준 시간이 0이어야 한다 |
| 인접 표적 사이 간격 | **8px 이상** | 옆 표적 오입력 방지 |
| 파괴적 동작(강퇴 · 나가기 · 방 삭제) | 44 × 44 이상 + **다른 표적과 16px 이상 이격** | 오입력의 대가가 크다 |

**세 지점이 현행 구현에서 이 규격을 만족하지 못한다.**

| 지점 | 현행(스테이지 좌표) | 360px에서 | 규격 |
|------|---------------------|-----------|------|
| 사다리 레인 | 레인 x 간격 = 1073 ÷ (인원 − 1). 10명이면 **119.2px**이고 도착 항목 칩 폭이 178px이라 **8명부터 칩이 서로 겹친다** | 레인 간격 22.4px | 90도 회전해 행 높이 44px 이상 확보(§5-4). 사다리는 참가자 입력이 없어 표적 문제는 없으나 **판독 가능성**이 판정 신뢰의 조건이다 |
| 눈치 UP 버튼 | 300 × 128 | **56.3 × 24.0px** | 하단 고정 · 폭 100% − 32 · 높이 120px |
| 시간초 STOP 버튼 | 900 × 139 | **168.8 × 26.1px** | 하단 고정 · 폭 100% − 32 · 높이 96px |
| 대기방 강퇴 버튼 | 27 × 27 | 5.1 × 5.1px | 44 × 44 이상 + 파괴적 동작 이격 16px |
| 확인 모달 닫기 버튼 | 크기 지정 없이 글리프 28px — **약 30 × 32px** | 5.6 × 6.0px | 44 × 44 표적 상자를 명시한다 |
| 프로필 아바타 페이징 화살표 | 글리프 44px, 표적 영역 지정 없음 | 표적 자체가 없다 | 44 × 44 표적 상자를 명시한다 |
| 목록 스크롤바 | 폭 8px | 1.5px | 포인터 조작에 스크롤바를 요구하지 않는다. 스크롤은 휠·터치로 처리한다 |

**게임 가이드 모달의 닫기 버튼만 44 × 44를 이미 만족한다.** 나머지는 전부 미달이다.

### 5-6. 결과 이미지와 화면 레이아웃의 분리

결과 이미지 저장(D-42)은 **화면에 그려진 DOM을 그대로 캡처하지 않는다.** 화면 레이아웃은 뷰포트에 따라 달라지므로 그대로 캡처하면 360px 사용자와 1920px 사용자가 서로 다른 이미지를 갖게 된다.

| 항목 | 규격 |
|------|------|
| 캔버스 | 뷰포트와 무관한 **고정 규격 1080 × 1350**(4:5). 메신저·SNS에서 잘리지 않는 비율이다 |
| 내용 | 주제 · 게임 이름 · 결과 · 참가자 · 날짜(D-42) |
| 렌더 | 화면 밖 전용 렌더 트리에 그려 이미지로 굽는다. 화면 표시용 결과 카드와 컴포넌트를 공유하되 레이아웃 값은 캔버스 규격을 따른다 |
| 실패 | 저장 실패는 토스트로 알리고 재시도 경로를 남긴다. 화면 상태는 바꾸지 않는다 |

## 6. 레이아웃·스크롤 규격

**데이터가 많아지면 스크롤은 그 데이터 영역 안에만 생긴다.**

| 항목 | 규격 |
|------|------|
| 스크롤 소유자 | 스크롤 컨테이너는 데이터 영역 하나다. 조상 요소에 스크롤을 중복 지정하지 않는다. 소유자는 참가자 목록 · 채팅 로그 · 설정 패널 · 개표 목록 · 라운드 기록 5종이다 |
| 페이지 스크롤 | **데스크톱·태블릿에서는 발생하지 않는다.** 모바일에서는 콘텐츠 영역의 세로 페이지 스크롤을 허용한다 |
| 가로 스크롤 | **어느 폭에서도 페이지 가로 스크롤을 만들지 않는다.** 넓은 내용(표지 게임 카드 캐러셀 등)은 자체 가로 스크롤 컨테이너 안에서만 흐른다 |
| 고정 요소 | 화면 헤더 · 상태 밴드(HUD) · 게임 입력 버튼 · 남은 시간 표시는 스크롤 밖에 고정한다. **입력 요소가 스크롤 때문에 화면 밖에 있는 순간이 있으면 안 된다** |
| 오버레이 | 내부 스크롤을 만들지 않는다. 예외는 게임 가이드 모달 하나다(§3-2) |
| 자동 스크롤 | 채팅은 새 메시지가 오면 맨 아래로 부드럽게 이동한다. 사용자가 위로 올려 읽는 중이면 이동하지 않고 새 메시지 알림만 띄운다 |
| 무한 증가 목록 | 채팅 로그만 무한 증가한다. 방 수명 동안 브라우저 메모리에만 남으며 서버에 저장하지 않는다(D-45). 표시 상한을 두고 오래된 메시지를 접는다 |

**게임 화면의 높이 배분**은 아래 순서로 잡는다. 위에서부터 자리를 주고 남는 높이를 연출 영역이 받는다.

```
[화면 헤더 · 주제와 게임 이름]      고정
[남은 시간 · 진행 상황]              고정
[연출 영역]                          잔여 높이 전부 (최소 높이 미달이면 스크롤이 아니라 축소)
[게임 입력 버튼]                     고정 · 하단 (모바일)
[상태 밴드 HUD]                      고정 · 하단 (데스크톱)
```

| 공용 컴포넌트 | 화면 셸 · 화면 헤더 · 상태 밴드 · 공정성 pill · 상단 배지 · 진행 바 · 아바타 원판 · 확인 모달 프레임 · 안내 카드 프레임을 화면마다 새로 만들지 않는다 |
| 이질감 | 화면 간 이질감 0. 새 화면이 다른 앱처럼 보이면 기준 미달이다 |
| 브레이크포인트 | §5-3의 3종만 쓴다 |
| 레이아웃 계약 | §6의 스크롤 계약을 지킨다. 화면이 자체 스크롤 컨테이너를 만들어 이중 스크롤을 내지 않는다 |

### 7-2. 프로덕션 완성도

| 항목 | 기준 |
|------|------|
| 상태 4종 완비 | §4의 네 상태를 모두 설계한다. 화면 명세의 상태 처리 표에 빈 행을 두지 않는다 |
| 스켈레톤 형태 | 스켈레톤은 실제 콘텐츠의 레이아웃을 따라간다 |
| 빈 상태의 사유 구분 | 데이터가 없어서 빈 것과 조건 미충족으로 빈 것을 문안으로 구분하고 다음 행동을 안내한다 |
| 중복 제출 방지 | 제출 중 버튼을 비활성화하고 진행 표시를 둔다. 게임 입력은 **최초 1회만** 인정되므로(D-08) 두 번째 누름은 화면에서도 막는다 |
| 낙관적 갱신 금지 | **판정에 관계된 어떤 값도 낙관적으로 갱신하지 않는다.** 내 입력이 접수됐다는 표시(완료 상태)까지만 즉시 반영하고, 결과·순위·득표는 서버 확정을 받아 그린다 |
| 결과 동시성 | 결과는 전원이 같은 순간에 본다. 먼저 아는 사람을 만드는 연출·전환을 두지 않는다 |
| 되돌릴 수 없음의 표시 | STOP · UP · 지목 · 제출처럼 한 번뿐인 입력은 누르기 전에 그 사실을 문구로 알린다 |

### 7-3. 접근성 최소선

이 제품에서 접근성은 편의가 아니라 **공정성**이다. 상태를 잘못 읽거나 표적을 놓치면 판정 결과가 달라진다.

| 항목 | 기준 |
|------|------|
| **색 단독 의존 금지** | 잔류·안전 확정·완료·대기·READY처럼 판정에 직결되는 상태는 색과 함께 **문자 또는 형태**로도 구분한다(D-48). 색각 이상은 남성 20명 중 1명꼴이라 10명 방에서 드문 일이 아니다 |
| **터치 표적** | §5-5의 규격을 지킨다 |
| **모션 저감 대응** | prefers-reduced-motion: reduce를 존중한다. 룰렛 회전 · 사다리 경로 추적 · 컨페티 · 마퀴 · 점멸은 **최종 상태로 즉시 전환**하거나 페이드 한 번으로 대체한다. **결과가 확정되는 시점은 모션 저감 여부와 무관하게 동일하다** — 연출을 건너뛴 사람이 먼저 알게 되면 안 된다 |
| **점멸 상한** | 화면 면적의 큰 부분을 차지하는 점멸은 **초당 3회 미만**으로 제한한다. 붉은 점멸은 광과민성 발작 유발 위험이 특히 높으므로 **판정 상태를 붉은 점멸로 알리지 않는다.** 눈치게임의 라운드 마감 임박·겹침 판정은 점멸 대신 진행 바 감소 + 문자 상태 + 한 번의 색 전환으로 표현한다 |
| 키보드 접근 | 조작 가능한 전 요소가 키보드로 도달·실행 가능하다. 게임 입력 버튼은 Space·Enter로 동작하며 **연타로 중복 제출되지 않는다** |
| 오버레이 접근성 | 열릴 때 포커스를 안으로 옮기고 포커스 트랩을 두며 Esc로 닫고 트리거로 포커스를 되돌린다 |
| 대체 텍스트 | 아바타 이미지는 장식이므로 대체 텍스트를 비우고, 이름은 옆의 텍스트가 담당한다. 아이콘 단독 버튼에는 이름을 붙인다 |
| 상태 변화 알림 | 라운드 전환 · 잔류 · 안전 확정 · 결과 공개는 보조 기술에 알린다. 남은 시간의 매초 갱신은 알리지 않는다 |
| 폰트 크기 | 판정에 필요한 문자(남은 시간 · 상태 문구 · 이름)는 360px에서 16px 이상으로 그린다 |

### 7-4. 현행 연출의 접근성 위험 전수

frontend/src에 **prefers-reduced-motion 대응이 0건**이고 aria 속성은 모달 닫기 버튼 2곳뿐이다. 무한 반복 연출은 아래 넷이며 전부 정지·감쇠 수단이 없다.

| 화면 | 대상 | 연출 | 주기 | 위험 | 규격 |
|------|------|------|:----:|------|------|
| NUNCHI-PLAY | 상태 밴드 1803 × 108(화면 면적의 약 9%) | 흰색 ↔ 연분홍 배경 명멸 | 1.25Hz 무한 | 대면적 명멸. **라운드 2 이상이면 라운드 내내 계속된다.** 원 스펙이 요구한 "붉은 점멸"을 그대로 구현하면 광과민성 발작 위험이 실제화된다 | **판정 상태를 점멸로 알리지 않는다.** 남은 시간은 진행 바 감소 + 숫자 + 한 번의 색 전환으로 표현한다 |
| NUNCHI-PLAY | 무대 카드 1221 × 400 — **UP 버튼을 품고 있다** | 좌우 ±3px 흔들림 | 2Hz 무한 | **표적 자체가 계속 움직인다.** 순간 입력이 순위를 가르는 게임에서 조준을 어렵게 만들므로 접근성이 아니라 공정성 문제다 | 게임 입력 버튼과 그 조상 요소에 이동·변형 애니메이션을 걸지 않는다. 압박은 배경·테두리로만 준다 |
| WHEEL-PLAY | 룰렛 림 점 20개(노랑 ↔ 흰색 교대 고대비) | 회전. 초기 각속도 약 3.9회전/초 | 시작 시 약 78Hz에서 감속하며 **3~60Hz 대역을 통과** | 고대비 점 배열의 고속 회전은 화면 깜박임과 같은 자극이 된다 | 림 점을 단색으로 두거나 회전에서 분리해 고정한다. 모션 저감 시 회전을 생략하고 결과 각도로 즉시 전환한다 |
| TIMER-PLAY · LADDER-PLAY | STOP 버튼 크기 진동(1.1Hz) · 매칭 현황 릴 회전(참가자 수만큼 동시, 0.6~1.1초 주기) | 무한 반복 | — | 크기가 변하는 표적은 조준을 방해한다. 릴은 **실제 배정과 무관한 값**을 돌리므로 오독을 유발한다 | 표적의 크기를 바꾸지 않는다. 결과를 감추는 연출에는 값을 흘리는 대신 가려진 상태를 명시한다 |

**색 단독 의존이 남아 있는 지점**도 함께 고친다 — 익명 저격 후보 카드의 선택 표시(테두리 색과 두께 1px 차이만) · 눈치 눌린 순서 목록(행 배경색만, 판정 문자가 없다) · 사다리 도착 항목 칩(퍼슨 컬러 매칭만, 이름이 없다) · 킹메이커 1위 표시(막대 색만). 넷 다 문자 또는 형태를 병기한다.

## 9. 구현 상태 판정 기준

화면 명세의 구현 상태 칸은 아래 기준으로만 올린다. **화면 연출이 있다는 사실은 완료의 근거가 아니다.**

| 값 | 조건 |
|----|------|
| ⬜ 미착수 | 대응 컴포넌트가 없다 |
| 🔶 진행 중 | 화면 표면이 있으나 **서버 연동·서버 판정 중 하나라도 빠져 있다.** 봇 시뮬레이션·클라이언트 난수로 동작하는 상태를 포함한다 |
| ✅ 완료 | 표면 · 서버 연동 · 서버 판정 · 상태 처리 4종 · 반응형 규격(§5)을 모두 만족한다 |

**현재 12본 전부가 🔶다.** 근거는 넷이다.

1. backend/는 헬스 체크 골격뿐이고 게임 로직·실시간 라우팅이 없다. 어떤 화면도 서버와 통신하지 않는다.
2. 참가자는 frontend/src/lib/data.ts의 고정 봇 5인이고 입장·채팅·준비 완료가 전부 setTimeout 스크립트다.
3. 초대 코드·아바타 랜덤·결과 값이 클라이언트 난수로 만들어진다 — 서버 판정 권위(D-05)가 성립하지 않는다.
4. §5의 반응형 규격을 어느 화면도 만족하지 않는다. @media 쿼리가 0개다.

## 10. 전역 기능 (F-CMN 7건)

아래 7건은 **소속 화면이 하나로 정해지지 않는 횡단 기능**이다. 어느 한 화면의 기능이 아니라 12본 전부가 지키는 규격이므로 본 문서가 대표로 담고, [02_traceability.md](./02_traceability.md)의 화면별 집계에서도 전역 한 줄로 계상한다.

| 기능ID | 기능 | 본 문서의 규격 |
|--------|------|----------------|
| F-CMN-01 | WebSocket 연결 관리 | §4 — 연결 끊김은 상태 4종과 별개이며 재접속을 시도하지 않는다 |
| F-CMN-02 | 방 상태 머신 | §1 — 대기·진행·결과 상태별로 화면이 허용하는 조작이 갈린다 |
| F-CMN-03 | 공통 응답·에러 규격 | §4 — 화면 분기는 에러 코드 문자열로 한다 |
| F-CMN-04 | 에러 문구 매핑 | §4 — 코드를 사람이 읽는 문구로 바꾸고 표시 방식(인라인·상태 밴드·토스트)을 정한다. 매핑되지 않은 코드에도 기본 문구를 준다 |
| F-CMN-08 | 모바일 반응형 | §5 — 브레이크포인트 3종 · 최소 지원 폭 360px · 터치 표적 규격 |
| F-CMN-09 | 방장 권한 검증 | §1-2 · §1-3 — 화면 노출 제어는 권한 경계가 아니며 거부는 보낸 사람에게만 간다 |
| F-CMN-10 | 이벤트 순서 보장 | §4 — 이미 반영한 번호보다 낮은 이벤트를 버린다. 늦게 도착한 이벤트로 화면을 되돌리지 않는다 |

나머지 F-CMN 3건(연결 끊김 안내 · 방 소멸 안내 · 진행 중 입장 거절 안내)은 특정 오버레이 요소가 표면을 가지므로 그 요소의 대표 소속 화면이 담는다([04_lobby.md](./04_lobby.md) · [03_entry.md](./03_entry.md)).
