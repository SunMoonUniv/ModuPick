# docs/ — 설계 정본 작업 지침

> **대상**: docs/ 전체의 작성·수정·검수 규약
> **작성일**: 2026-08-02
> **원천**: docs_legacy/(구 스펙 3본) · frontend/src(프로토타입 구현) · git 529e312(db.md · api.md) · git ecceb11(30문서 체계) · [README.md](./README.md)(고정 기준·전역 불변식)

docs/는 **설계 정본(to-be)** 이다. ModuPick은 아직 구현되지 않았고, 본 문서군은 **앞으로 무엇을 만들 것인가**를 확정해 기술한다. 문서가 확정되면 그대로 구현하며, 구현이 문서와 어긋나면 구현을 고친다. 문서를 고쳐야 할 사유가 생기면 그 근거를 남기고 관련 문서를 같은 변경 단위에서 함께 갱신한다.

## 이 문서군의 성격

**설계 정본이되 구현 상태를 함께 싣는다.** 기능·화면·API·테이블마다 구현 상태를 ⬜(미착수) · 🔶(진행 중) · ✅(완료)로 표기한다. 서술은 "~한다" 평서체 현재형으로 쓰되, 이는 **설계상 그렇게 동작한다**는 뜻이며 이미 그렇게 동작한다는 뜻이 아니다. 진척은 상태 열이 말하고 본문은 설계를 말한다 — 두 축을 섞지 않는다.

**설계된 것과 구현된 것을 구분한다.** frontend/에는 봇 시뮬레이션 프로토타입이 있고 backend/에는 골격만 있다. 프로토타입이 구현한 것을 "완료"로 적지 않는다 — 서버 판정이 없는 화면 연출은 설계의 일부가 구현된 것이지 기능이 완성된 것이 아니다.

**프로토타입이 명세와 어긋난 지점은 문서가 이긴다.** frontend/src의 구현이 본 문서군과 다르면 구현이 결함이다. 그 지점은 [01_overview/05_priorities_roadmap.md](./01_overview/05_priorities_roadmap.md)의 구현 정정 목록에 등재하고, 문서를 구현에 맞추지 않는다.

## 편집 전 필수 절차

1. [README.md](./README.md)의 **고정 기준·ID 규약·전역 불변식**을 먼저 확인한다 — 수치·식별자는 전 문서가 동일하게 인용한다.
2. 사실 서술은 원천에 근거한다 — docs_legacy의 절 번호, frontend/src의 파일 경로, git 히스토리 문서를 근거로 명기한다. 기억·추정으로 수치를 적지 않는다.
3. 같은 폴더에 이미 있는 문서의 골격(메타 블록·H2 순서·표 컬럼)을 우선 따른다 — "동일한 형식, 다른 내용"이 원칙이다.

## 게임 규칙 문서의 필수 요소

05_game_rules의 게임별 문서는 산문 규칙만으로 끝내지 않는다. 아래 다섯을 **전부** 담는다. 하나라도 빠지면 구현자가 임의로 메우게 되고 그것이 결함이 된다.

| 요소 | 내용 |
|------|------|
| 상태 머신 | phase 전이도와 각 전이의 트리거·가드. **모든 (상태 × 이벤트) 칸이 채워져야 한다** — "정의되지 않음"을 남기지 않는다 |
| 판정 알고리즘 | 의사코드. 입력(서버 도착 시각 배열·설정값·명단 스냅샷)에서 출력(판정 결과)이 결정적으로 도출됨을 보인다 |
| 종료 증명 | 모든 입력 조합에서 유한 라운드 안에 끝남을 논증한다. 동점·미입력·전원 동시 입력을 반례 후보로 반드시 검토한다 |
| 경계값 표 | 최소 인원 · 최대 인원(10) · 전원 미입력 · 전원 동시 입력 · 1명 잔류 · 도중 이탈로 유효 인원 감소에서의 동작 |
| 인수 기준 | AC-NN. 입력 → 기대 출력 형태로 검증 가능하게 쓴다 |

**종료 증명 없이 동점 규칙을 쓰지 않는다.** 초기 스펙의 "단독 승자가 나올 때까지 반복(상한 없음)"은 킹메이커·익명 저격·시간초에서 종료하지 않는 조합이 실제로 존재했다. 같은 결함을 되풀이하지 않기 위한 규약이다.

## 추적성 동시 갱신

기능·요구사항·화면·테이블·에러코드를 추가·변경하면 같은 변경 단위에서 갱신한다.

- [03_requirements/11_traceability.md](./03_requirements/11_traceability.md) — REQ ↔ 기능ID ↔ 화면 ↔ 테이블
- [08_screen/02_traceability.md](./08_screen/02_traceability.md) — 기능ID → 화면코드(미매핑 0 보장). **같은 파일 끝의 화면별 담은 기능 수 표는 파생 집계이므로 함께 갱신한다**
- 에러코드 신설 시 [10_glossary/02_error_codes.md](./10_glossary/02_error_codes.md) 등재

**파생 집계는 정본을 고친 같은 변경 단위에서 다시 센다.** 정본 한 줄을 고치고 집계를 두면 두 값이 조용히 갈라지며, 그 상태가 "검증을 통과한 문서"로 남는다.

## 열거의 정합

- **개수를 쓰면 그 자리에서 항목을 세어 맞춘다.**
- **세는 기준이 둘이면 기준을 밝힌다.** 화면은 라우트 축과 오버레이 포함 축이 다르고, 기능 수는 서버 전용 기능 포함 여부로 갈린다. 두 값을 섞어 쓰지 않는다.
- **전수·유일·~만·~뿐으로 단언하기 전에 정본 집합을 확인한다.** 특히 공정성·익명성 서술에서 배타 단언이 틀리면 구현자가 그 문장만 보고 만들어 실제 취약점이 된다.
- **같은 사실의 정본을 둘로 만들지 않는다.** 개괄 표가 상세 표와 어긋나면 개괄임을 명시하고 정본을 가리킨다.

## 범위 규약

본 문서군의 범위는 **MVP로 만들기로 확정한 것**이다. 다음은 범위 밖이며 현행 설계처럼 서술하지 않는다.

로그인·회원가입 · 계정·전적·통계 · 재접속·상태 복구 · 관전 모드 · 방 목록 · Slack 연동 · QR 초대 · AI 팀명 추천 · 혐오 표현 필터링 · 결과 리포트 · 채팅 서버 저장 · 다크 모드.

설계를 설명하려면 범위 밖 항목의 **부정형 언급이 불가피한 경우**가 있다(예: "재접속 경로를 두지 않는다"). 이때는 부정형으로만 쓰고 현행 설계처럼 서술하지 않는다.

**docs_ref는 참조 전용이다.** DayLog라는 다른 제품의 문서이며 형식·품질 기준으로만 인용한다. 그 도메인 내용(RLS · Supabase · 효율 지표 · 팀 RBAC 등)을 ModuPick 문서에 옮기지 않는다.

**docs_legacy는 원천이지 정본이 아니다.** 본 문서군과 어긋나면 본 문서군이 이긴다. 구 ID(US-NNN · F-NNN)는 매핑표로만 남긴다.

## 하지 말 것

- 미구현 기능을 구현 완료로 표기하는 것. 상태 열은 실제 코드 기준으로만 올린다.
- **검증하지 못한 것을 검증된 사실로 단정하는 것.** 특히 성능·지연 수치는 실측 없이 단정하지 않는다.
- 원천 근거 없는 수치·전수 단언, 고정 기준 수치의 임의 변경, 정본 문서 밖에서의 ID 채번.
- **종료가 보장되지 않는 규칙을 쓰는 것** — 반복 규칙에는 반드시 상한 또는 탈출 경로를 둔다.
- **클라이언트를 신뢰하는 서술** — 판정에 쓰는 값은 서버가 계산하거나 서버가 검증한다. 예외를 두는 자리(시간초 잡기의 경과 시간 측정)는 예외임을 명시하고 검증 방법을 함께 적는다.
- 익명성을 보장한다고 적으면서 서버가 가진 식별 정보의 유출 경로를 검토하지 않는 것.
