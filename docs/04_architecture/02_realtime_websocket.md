대기방 진입 이후의 모든 통신은 WebSocket 위에서 일어난다. **Native WebSocket**을 쓰므로 방 관리 · 브로드캐스트 · 하트비트를 직접 구현한다(ADR-06). 재접속과 상태 복구는 설계에 없어 가장 큰 부담이 빠지지만, 대신 **연결이 끊겼다는 판정을 언제 내릴 것인가**가 우리 손에 남는다.

원천 어디에도 그 판정 기준이 없었다. git 529e312 docs/db.md §10은 "연결 종료 시 퇴장 처리"라고만 쓰고 소켓 종료인지 하트비트 타임아웃인지, 몇 초인지 정의하지 않는다. 정의 없이 구현하면 소켓 종료 즉시 퇴장이 되고, 그러면 **모바일에서 탭을 백그라운드로 보낸 사람이 즉시 퇴장하며 방장이면 방이 사라진다.** 방장이 초대 링크를 공유하러 다른 앱으로 전환하는 것은 핵심 사용 흐름이다. 본 문서가 그 기준을 확정한다.

## 연결 수명주기

| 단계 | 시점 | 서버 동작 |
|:----:|------|-----------|
| 1 | 참가 등록 응답 수신 직후 — 참가자 | 참가자 토큰으로 핸드셰이크한다. 프로필 없는 **대기** 상태이며 정원은 차지하나 다른 사람 목록에는 보이지 않는다 |
| 2 | 프로필 확정 직후 — 방장 | 방장 토큰으로 핸드셰이크한다. 방장은 프로필 확정이 방 생성 절차에 포함된다 |
| 3 | 핸드셰이크 | 방 코드와 토큰을 함께 받아 **토큰이 가리키는 참가자의 소속 방 == 접속 대상 방**을 검증한다. 다르면 거부하고 연결을 닫는다(ADR-07) |
| 4 | 수락 직후 | 소켓에 **참가자 식별자 · 방 식별자 · 방장 여부**를 바인딩한다. 이후 모든 이벤트의 주체는 이 바인딩으로만 판정하며 페이로드가 실어 보낸 식별자·역할은 쓰지 않는다 |
| 5 | 바인딩 직후 | **방 스냅샷을 최초 1회** 보낸다. 화면 한 장을 이것만으로 그릴 수 있어야 하며 이후에는 부분 갱신 이벤트만 보낸다 |
| 6 | 프로필 확정 | 참가자가 **활성**이 되고 입장 이벤트가 방에 브로드캐스트된다. 즉 소켓은 붙었으나 아직 보이지 않는 구간이 존재한다 |
| 7 | 미연결 자동 해제 | 참가 등록 후 **15초** 안에 핸드셰이크가 없으면 슬롯을 푼다. 핸드셰이크가 있어도 프로필을 확정하지 않고 방치하면 REST 표면이 정한 시한에 슬롯을 회수한다([../07_api/02_rest.md](../07_api/02_rest.md)) |
| 8 | 종료 | 명시적 나가기 · 강퇴 · 이탈 확정 · 방 삭제 · 서버 재기동 중 하나로 끝난다. **같은 토큰으로 다시 붙는 경로는 없다** |

**정원 계산은 대기 상태와 활성 상태를 합산한다.** 프로필을 아직 안 채운 사람도 슬롯을 차지해야 정원 초과를 정확히 막는다. 반면 **다른 사람 화면에 보이는 것은 활성뿐이다.**

## 방 단위 라우팅

- 룸 키는 **방 코드**다. 표시할 때만 접두어를 붙이고 라우팅 키에는 숫자 6자리만 쓴다.
- 레지스트리는 두 방향 대응을 인메모리로 유지한다 — 방 → 소켓 집합 · 소켓 → 방·참가자 바인딩. 소켓이 닫히면 양쪽에서 함께 제거한다.
- **전송 대상 집합은 세 가지뿐이다.**

| 대상 | 쓰임 |
|------|------|
| 방 전체 | 상태 변화·결과처럼 전원이 같은 순간에 알아야 하는 것 |
| 방 전체에서 발신자 제외 | 입력 완료 표시처럼 발신자에게는 응답으로 이미 알려준 것 |
| 개인 | 거부 응답 · 개인 스냅샷. **거부는 브로드캐스트하지 않는다** — 한 사람의 실패가 다른 사람 화면을 흔들지 않게 한다 |

- 대상 집합을 소켓 목록으로 확정한 뒤 전송한다. 전송 중 목록이 바뀌어도(누가 나가도) 그 회차의 대상은 변하지 않는다.
- **관전자·방 외부 구독자를 두지 않는다.** 방에 바인딩되지 않은 소켓은 어떤 이벤트도 받지 않는다.

## 브로드캐스트

1. **방 단위로 페이로드를 1회만 직렬화한다.** 같은 이벤트를 10명에게 보낼 때 직렬화를 10번 하지 않는다. 부하 추정이 이 규약을 전제로 한다(ADR-26).
2. **수신자별로 독립 전송한다.** 한 소켓의 지연·실패가 다른 소켓의 전송을 막지 않는다.
3. **확인 응답을 기다리지 않는다.** 전원 확인 후 확정하면 한 명의 지연이 전원의 결과 전환을 늦춰 결과 동시성 목표가 깨진다.
4. **DB 커밋 이후에만 발행한다.** 롤백된 사실을 화면에 남기지 않는다(ADR-18).
5. 개인화가 필요한 이벤트는 개인 전송으로 분리한다. 익명 게임의 식별 정보는 **공개 설정이 켜지고 개표가 끝난 뒤에만** 페이로드에 들어간다.
6. 페이로드에는 **방 상태 버전**이 반드시 포함된다.

## 하트비트와 이탈 유예

### 연결 상태 3단계

**소켓이 끊겼다는 사실과 사람이 방을 떠났다는 사실은 다르다.** 둘을 같은 것으로 다루면 백그라운드 전환이 곧 퇴장이 된다. 그래서 상태를 셋으로 나눈다.

```
      핸드셰이크 수락
            │
            ▼
       ┌─────────┐   pong 3회 미수신 / 전송 실패 / 소켓 종료 관측   ┌────────┐
       │  연결   │ ────────────────────────────────────────────▶ │  의심  │
       │ (정상)  │ ◀──────────────────────────────────────────── │        │
       └─────────┘        같은 소켓에서 프레임 도착               └────────┘
            │                                                        │
            │ 명시적 나가기 / 강퇴                    이탈 유예 만료  │
            ▼                                                        ▼
       ┌──────────────────────────────────────────────────────────────┐
       │                      이탈 확정                                │
       │  참가자: 명단에서 제외(대기) · 후보 유지 미입력 처리(진행)      │
       │  방장:   방 삭제                                              │
       └──────────────────────────────────────────────────────────────┘
```

**의심에서 연결로 돌아오는 경로는 같은 소켓에서 프레임이 오는 것뿐이다.** 새 소켓으로 돌아오는 경로를 두지 않는다 — 그것이 재접속이며 설계에 없다(ADR-09). 종료된 소켓에는 복귀 경로가 없으므로, 그 경우 유예는 **복구를 기다리는 시간이 아니라 이탈 확정의 부작용을 늦추는 시간**이다.

**복귀 경로는 실제로는 좁다.** pong 무응답은 uvicorn이 프로토콜 레벨에서 소켓 종료로 처리하므로, 의심에 들어간 시점에는 소켓이 이미 닫혀 있는 경우가 대부분이다. 복귀가 성립하는 것은 전송 실패로 의심에 들어갔는데 소켓이 아직 살아 있는 경우처럼 좁은 구간뿐이다. **그래서 유예의 값어치는 복구가 아니라 예고에 있다** — 방장의 경우 남은 사람들이 "방이 갑자기 사라졌다"가 아니라 "방장 연결이 끊겨 곧 방이 닫힌다"를 60초 동안 보게 되고, 참가자의 경우 순간적 단절로 카드가 사라졌다 나타나는 깜빡임이 없어진다.

### 확정 값

| 항목 | 값 | 근거 |
|------|-----|------|
| 하트비트 방식 | **WebSocket 제어 프레임 ping** | 제어 프레임의 pong은 **브라우저가 JS 실행 없이 돌려준다.** 백그라운드 탭의 타이머 스로틀링·페이지 정지가 하트비트를 죽이지 못한다. 애플리케이션 레벨 ping 이벤트에 클라이언트가 응답하는 방식을 쓰지 않는 이유가 이것이다 |
| ping 주기 | **20초** | Nginx 읽기 타임아웃 75초보다 충분히 짧아 유휴로 끊기지 않고, 60초 창에 3회가 들어간다 |
| pong 대기 | **3주기 = 60초** | 모바일 셀 전환·터널·엘리베이터에서 수십 초 무응답이 실제로 생긴다. 1주기(20초)면 정상 사용자를 끊고, 5주기(100초)면 이탈 확정과 방 정리가 늦다 |
| 이탈 유예 — 참가자 | **30초** | 유예는 남은 사람 화면에 연결 끊김으로 보이는 시간이다. 더 길면 진행을 기다리는 시간이 길어진다 |
| 이탈 유예 — 방장 | **60초** | 방 삭제는 되돌릴 수 없다. 초대 링크를 공유하러 다른 앱에 다녀오는 왕복이 이 창 안에 들어가야 한다 |
| 미연결 슬롯 해제 | **15초** | 참가 등록 후 핸드셰이크가 없으면 슬롯만 차지한다. git 529e312 docs/api.md 연결 수명주기 6항의 값을 승계한다 |

**세 값은 서버 설정으로 뺀다.** 코드에 상수로 박으면 계측 결과를 반영할 때마다 배포가 필요하고, 배포는 곧 진행 중인 방의 소멸이다(ADR-24).

**이탈 확정까지의 최대 지연** — 참가자 60 + 30 = **90초** · 방장 60 + 60 = **120초**. 소켓 종료가 즉시 관측되면 유예만큼(30초·60초)이다. 10분 무활동 만료가 최후 안전망으로 남는다([06_memory_persistence_split.md](./06_memory_persistence_split.md)).

### 즉시 확정되는 경우와 그렇지 않은 경우

| 사건 | 처리 |
|------|------|
| 사용자가 나가기 버튼을 눌러 **명시적 나가기 이벤트**가 도착 | **즉시 이탈 확정.** 유예 없음 |
| 방장이 강퇴 | 즉시 이탈 확정. 유예 없음 |
| 소켓 종료 관측(브라우저 종료 · 탭 닫기 · 네트워크 단절) | **의심 → 유예 만료 시 확정** |
| pong 3회 연속 미수신 | 의심 → 유예 만료 시 확정. 유예 중 프레임이 오면 연결로 복귀 |
| 전송 실패 | 의심. 해당 소켓은 닫는다 |
| 서버 재기동 | 전 소켓 종료. 방은 기동 정리 절차가 삭제한다(ADR-20) |

**클라이언트는 페이지 숨김·가시성 변경으로 나가기 이벤트를 보내지 않는다.** 모바일에서는 앱 전환만으로도 이 사건이 발화하기 때문이다. 나가기 이벤트는 사용자가 나가기 버튼을 눌렀을 때만 보낸다. 창을 닫으려 할 때 이탈 경고를 띄우는 것은 권장하되, 그 경고가 나가기 이벤트를 대신 보내서는 안 된다.

### 유예 중의 취급

| 축 | 대기 상태의 방 | 진행·결과 상태의 방 |
|----|---------------|--------------------|
| 명단 | 목록에 남고 **연결 끊김**으로 표시한다 | 명단 스냅샷에 그대로 남는다 |
| 준비 상태 | **해제한다.** 준비 완료로 세지 않으므로 게임 시작을 막는다 | 해당 없음 |
| 정원 | 슬롯을 계속 차지한다 | 해당 없음 |
| 게임 입력 | 해당 없음 | 입력이 오지 않으므로 게임별 기본값으로 자동 처리한다 |
| 방장 | 방을 삭제하지 않고 대기한다. 시작·설정 변경 등 방장 동작은 그대로 거부된다(입력이 없다) | 진행 중이면 판을 멈추지 않는다. 룰렛·사다리처럼 방장 입력이 필요한 게임은 게임별 미조작 기본 처리를 따른다 |
| 해소 수단 | 방장이 **강퇴**로 즉시 정리할 수 있다(대기 상태에서만 가능) | 없음. 명단 스냅샷이 고정돼 있다 |

**유예를 두어도 재접속은 여전히 불가하다.** 유예 안에 나갔던 사람이 링크를 다시 열면 그는 **새 참가자**이며, 정원에 자리가 있어야 들어오고 진행 중인 판에는 들어오지 못한다. 유예는 그가 남긴 자리를 지켜 주는 장치가 아니라 이탈 확정의 부작용을 늦추는 장치다.

### 남는 위험과 그 수용

**OS가 실제로 브라우저 프로세스를 정지시켜 연결이 끊기면, 유예가 만료되는 순간 방장의 방은 삭제된다.** 제어 프레임 하트비트가 백그라운드 전환의 대부분을 흡수하지만 전부는 아니다 — 장시간 백그라운드·메모리 압박·기기 절전에서는 연결이 실제로 끊긴다. 이 경우의 동작은 **방 삭제가 맞다**고 판단한다. 재접속을 두지 않고 방장 권한을 이양하지 않기로 한 이상 방장 없는 방은 진행할 수 없기 때문이다(ADR-09). 대신 화면은 삭제 사유를 방장 이탈로 알린다.

**유예 값은 실측 대상이다.** 30초·60초는 위 근거로 정한 설계값이며 실제 모바일 환경에서 측정한 값이 아니다. 통합 배포 후 하트비트 타임아웃 발생 수와 이탈 확정 사유 분포를 지표로 남겨 조정 근거를 만든다(ADR-27).

## 순서 보장

- **방 상태 버전**은 방 상태가 바뀔 때마다 1 증가하는 정수이며 모든 서버→클라이언트 이벤트에 실린다.
- 클라이언트는 **마지막으로 반영한 값보다 작거나 같은 이벤트를 버린다.** 스냅샷과 부분 갱신이 뒤섞여 도착해도 화면이 과거로 되돌아가지 않는다.
- 클라이언트가 상태 버전을 실어 보내는 요청은 서버 값과 다르면 거절한다 — 화면이 낡은 상태에서 누른 버튼이 반영되지 않게 한다.
- 상태 버전은 **인메모리 방 상태에서 증가**시키고, 영속 데이터가 바뀌는 이벤트는 DB의 상태 버전 컬럼과 함께 올린다. 두 값이 갈라지지 않도록 증가는 커밋 이후 한 곳에서만 한다.
- **라운드 안의 단계 전이는 방 상태 버전과 별개로 라운드 식별자·단계·반복 회차 3항으로 식별한다.** 게임 입력의 문맥 일치 검사가 이 세 값을 본다([03_judgment_engine.md](./03_judgment_engine.md)).

## 전송 실패 처리

| 상황 | 처리 |
|------|------|
| 개별 소켓 전송 실패 | 기록하고 그 소켓을 닫는다. 해당 참가자는 의심 단계로 간다. 다른 수신자 전송은 계속한다 |
| 방 전체 전송 중 예외 | 남은 수신자에게 계속 보낸다. 중단하지 않는다 |
| 커밋은 됐는데 전송이 전부 실패 | **DB를 되돌리지 않는다.** 결과는 확정된 사실이고, 못 본 참가자는 유예 만료로 이탈 확정된다 |
| 수신 큐 적체 | 소켓별 송신 대기 상한을 두고 초과하면 그 소켓을 닫는다. 느린 한 명이 프로세스 메모리를 잠식하지 않게 한다 |
| 페이로드 상한 초과 | Nginx와 애플리케이션 양쪽에서 상한을 두고 거부한다. 채팅·안건 텍스트의 길이 상한은 기능 명세가 정한다 |
| 잘못된 형식 프레임 | 개인 거부 응답 후 소켓을 닫는다. 방에는 알리지 않는다 |

전송 실패 횟수·비정상 종료 횟수·하트비트 타임아웃 횟수는 모니터링 항목이다([07_deployment_topology.md](./07_deployment_topology.md)).
