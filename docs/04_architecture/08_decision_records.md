ModuPick의 **기술 결정을 ADR로 고정한다.** 본 문서가 ADR 채번의 유일 정본이며 다른 문서는 번호로 인용만 한다. 각 ADR은 **맥락 · 결정 · 버린 대안 · 파급** 네 항목으로 쓴다.

제품 결정(무엇을 만드는가)은 D-NN이고 [../01_overview/06_design_decisions.md](../01_overview/06_design_decisions.md)가 채번한다. 본 문서는 **어떻게 만드는가**만 다룬다 — 저장 경계 · 실시간 · 판정 · 시간 · 배포가 그 범위다. 구 스펙(docs_legacy/requirements.md §6)의 D-01~40 중 기술 성격인 항목은 여기서 ADR로 다시 쓰며, 구 번호를 승계하지 않는다.

**ADR 총수는 27건이다**(ADR-01~27 · 결번 없음).

## ADR-01 — 백엔드 FastAPI · 프론트엔드 React 19 + Vite 분리 구성

- **맥락**: 대기방 진입 이후 전 기능이 실시간 소켓이고, 화면은 SPA 한 벌이면 충분하다. 팀의 언어 경험은 Python과 TypeScript다.
- **결정**: 백엔드는 **FastAPI**(ASGI · uvicorn) 단일 애플리케이션, 프론트엔드는 **React 19 + Vite** SPA로 분리한다. 두 배포 대상은 서로 다른 호스트에 올라가며 CORS와 소켓 오리진으로 연결한다.
- **버린 대안**: ① Next.js 통합 — SSR·SEO가 필요 없고, 실시간 소켓 서버를 Node 런타임에 얹으면 판정 코드가 프런트 저장소와 섞인다. ② NestJS·Spring Boot — 팀의 Python 경험을 버리게 되고 비동기 소켓 처리 학습 비용이 커진다. ③ 프론트와 백엔드 동일 호스트 배치 — 정적 자원 배포마다 소켓 서버를 재기동하게 되고, 재기동이 곧 진행 중 방 소멸이다([ADR-24](#adr-24--배포는-다운타임을-수용한다-배포-시-진행-중-방은-사라진다)).
- **파급**: 프론트 배포와 백엔드 배포가 분리되어 화면 수정이 방을 죽이지 않는다. 대신 오리진이 둘이라 CORS 허용 목록과 소켓 오리진 검사가 배포 구성의 필수 항목이 된다(backend/app/config.py의 cors_origins).

## ADR-02 — 단일 인스턴스 · 워커 1개 고정. 수평 확장·무중단 배포·Redis 미채택

- **맥락**: 방의 진행 중 상태(라운드 단계 · 입력 도착 시각 · 판정창 그룹핑 · 생존자 명단 · 소켓 연결 · 준비 상태)는 프로세스 메모리에 있다([ADR-04](#adr-04--하이브리드-저장--진행-중-상태는-인메모리--영속-6테이블은-mysql-판정-경로에-db-왕복-금지)). 프로세스가 둘이면 같은 방 참가자가 서로 다른 프로세스에 붙어 서로를 보지 못한다.
- **결정**: 백엔드는 **인스턴스 1개 · 워커 1개**로 고정한다. 수평 확장·오토스케일링·무중단 배포를 하지 않으며 **Redis를 도입하지 않는다.** uvicorn을 다중 워커로 띄우지 않는다.
- **버린 대안**: ① Redis 도입(공유 상태·pub/sub) — 밀리초 판정 경로에 네트워크 왕복이 하나 더 들어가고, 운영 대상이 하나 늘며, 방이 일회성이라 공유할 상태의 수명이 분 단위다. 얻는 것은 MVP 범위 밖의 수평 확장뿐이다. ② DB 전면 영속 — 눈치게임 판정창 그룹핑을 DB 왕복으로 하면 지터보다 큰 지연이 판정에 들어간다. ③ 스티키 세션 + 다중 프로세스 — 같은 방이 같은 프로세스에 가도록 라우팅 계층에 방 코드 인지를 심어야 하고, 그 계층이 새 단일 장애점이 된다.
- **파급**: 용량 상한이 단일 프로세스의 메모리·소켓·CPU에 종속된다([ADR-26](#adr-26--부하-목표-100방1000연결-단일-프로세스-수용-여부는-산술-추정으로-판정하고-실측-전에-단정하지-않는다)). 재기동은 곧 전 방 소멸이므로 기동 시 정리 절차가 필수가 된다([ADR-20](#adr-20--서버-재기동-시-db에-남은-방을-전량-정리한다-상태-복구를-시도하지-않는다)). 만료 스위퍼를 중복 실행 걱정 없이 프로세스 안에 둘 수 있다([ADR-21](#adr-21--방-만료-스위퍼--10분-무활동--60초-주기--단일-스케줄러)).

## ADR-03 — Kubernetes 미채택. Docker Compose + 단일 호스트

- **맥락**: 구 스펙(git ecceb11 docs/03_architecture/00_tech_stack.md)은 오케스트레이션으로 Kubernetes를 적었고, 같은 문서가 인메모리 기본안에서는 replicas를 1로 고정해야 하고 무중단 배포가 불가능하다고 스스로 지적했다.
- **결정**: **Kubernetes를 채택하지 않는다.** 백엔드와 MySQL을 EC2 한 대에서 **Docker Compose**로 운영한다.
- **버린 대안**: ① Kubernetes replicas=1 — 복제도 무중단 배포도 오토스케일링도 쓸 수 없는 구성에서 컨트롤 플레인 운영 비용만 남는다. 얻는 것은 헬스 체크 재기동뿐이고 그것은 컨테이너 재시작 정책으로 된다. ② 관리형 컨테이너 서비스 — 같은 이유로 이점이 상쇄되고, 소켓 유휴 타임아웃을 서비스 기본값에 맡기게 된다.
- **파급**: 배포 산출물이 이미지 태그와 Compose 정의로 좁아지고, 롤백이 이전 태그 재기동으로 단순해진다([ADR-24](#adr-24--배포는-다운타임을-수용한다-배포-시-진행-중-방은-사라진다)). liveness·readiness는 컨테이너 헬스 체크와 애플리케이션 엔드포인트로 대신한다.

## ADR-04 — 하이브리드 저장 — 진행 중 상태는 인메모리 · 영속 6테이블은 MySQL. 판정 경로에 DB 왕복 금지

- **맥락**: ModuPick은 밀리초 순서로 판정하는 게임(눈치게임 · 시간초 잡기)을 갖는다. 동시에 방·참가자·투표·확정 결과는 여러 요청이 경합하므로 UNIQUE·FK 같은 DB 제약이 필요하다. 두 요구를 한 저장소로 만족시킬 수 없다.
- **결정**: 저장을 둘로 나눈다.
  - **서버 인메모리** — 라운드 단계 · 입력 도착 시각 · 판정창 그룹핑 · 생존자 명단 · 소켓 연결과 연결 상태 · 준비 상태 · 타이머 핸들.
  - **MySQL 6테이블** — rooms · participants · game_rounds · game_options · votes · game_results.
  - **밀리초 판정 경로에 DB 왕복을 넣지 않는다.** DB에 기록하는 입력은 집계용 표(votes)뿐이며, 시간 판정 입력은 인메모리에서 처리하고 확정 결과만 game_results에 남긴다.
- **버린 대안**: ① 전면 인메모리 — 방·참가자·투표의 동시성 제어를 직접 구현해야 하고, 중복 투표·정원 초과를 막을 제약이 코드에만 남는다. ② 전면 DB — 판정 지연이 커지고 재기동해도 방을 이어갈 수 없다는 사실은 그대로다(준비 상태·소켓은 어차피 복구되지 않는다).
- **파급**: 단일 인스턴스가 강제된다([ADR-02](#adr-02--단일-인스턴스--워커-1개-고정-수평-확장무중단-배포redis-미채택)). 데이터별 소재와 정합 규칙의 정본은 [06_memory_persistence_split.md](./06_memory_persistence_split.md)다. 재기동 시 DB에 방이 남으면 전부 고아가 된다([ADR-20](#adr-20--서버-재기동-시-db에-남은-방을-전량-정리한다-상태-복구를-시도하지-않는다)).

## ADR-05 — MySQL 8.4 채택. PostgreSQL 미채택

- **맥락**: 구 스펙 두 벌이 갈렸다 — git ecceb11 docs/03_architecture/00_tech_stack.md는 PostgreSQL, git 529e312 docs/db.md는 MySQL 8.4 DDL을 확정해 두었다.
- **결정**: **MySQL 8.4**를 쓴다. 세션 시간대는 +00:00, 문자 집합은 utf8mb4, 정렬은 utf8mb4_0900_ai_ci, SQL 모드는 ONLY_FULL_GROUP_BY · STRICT_TRANS_TABLES · ERROR_FOR_DIVISION_BY_ZERO · NO_ENGINE_SUBSTITUTION으로 고정한다. 드라이버는 비동기 드라이버를 쓴다(backend/app/config.py의 기본 접속 문자열).
- **버린 대안**: PostgreSQL — 기능상 부족함이 있어서가 아니라 **이미 확정된 DDL과 잠금 순서 설계가 MySQL 기준으로 존재하기 때문**이다. 두 벌을 유지할 이유가 없고, 스키마가 6테이블뿐이라 DB 고유 기능에 의존하는 부분이 없다.
- **파급**: 격리 수준은 InnoDB 기본값 REPEATABLE READ이며 경합 행만 짧게 잠근다([ADR-18](#adr-18--트랜잭션-경계와-잠금-순서-commit-이후에만-브로드캐스트)). 스키마 정본은 [../06_database/README.md](../06_database/README.md)다.

## ADR-06 — Native WebSocket 채택. Socket.IO 미채택

- **맥락**: 실시간 계층에 필요한 것은 방 단위 그룹 전송과 연결 감지뿐이다. 재접속·상태 복구는 설계상 존재하지 않는다([ADR-09](#adr-09--재접속-불가--방장-권한-비이양--방장-이탈-시-방-삭제)).
- **결정**: **Native WebSocket**을 쓴다(백엔드는 FastAPI의 WebSocket 표면, 프론트는 브라우저 WebSocket API). 방 관리 · 브로드캐스트 · 하트비트를 직접 구현한다.
- **버린 대안**: Socket.IO — 자동 재연결과 폴백 전송이 주된 값어치인데 재연결은 쓰지 않기로 했고, 프로토콜 계층이 하나 더 생기면 프레임 도착 시각을 판정에 쓰는 경로가 라이브러리 큐잉에 가려진다.
- **파급**: 하트비트를 우리가 설계해야 한다([ADR-08](#adr-08--연결-상태-3단계와-하트비트이탈-유예--ping-20초--타임아웃-60초--유예-참가자-30초방장-60초)). 재연결이 없어 Native WebSocket의 가장 큰 부담이 사라진다. 이벤트 순서 보장도 우리 몫이다([ADR-10](#adr-10--순서-보장은-방-상태-버전-단조-증가-역행-이벤트는-클라이언트가-버린다)).

## ADR-07 — 소켓 인증은 토큰 핸드셰이크 + 방 바인딩. 토큰의 방과 접속 방이 다르면 거부

- **맥락**: git 529e312 docs/db.md의 결함 목록 1번이 "다른 방의 참가자가 연결될 수 있음"을 가장 중요한 문제로 지목했다. 방 코드는 숫자 6자리라 추측 가능하고, 토큰만 검사하고 방을 검사하지 않으면 A방 참가자가 B방 소켓에 붙는다.
- **결정**: 핸드셰이크에서 **방 코드와 토큰을 함께 받고, 토큰이 가리키는 참가자의 소속 방이 접속 대상 방과 같을 때만 연결을 수락한다.** 수락 후 소켓에 참가자 식별자·방 식별자·방장 여부를 바인딩하고, 이후 모든 이벤트의 주체는 **소켓 바인딩 값으로만** 판정한다. 페이로드가 실어 보낸 참가자 식별자·역할은 판정에 쓰지 않는다.
- **버린 대안**: ① 토큰만 검사 — 위 결함이 그대로 남는다. ② 이벤트마다 페이로드의 참가자 식별자를 신뢰 — 남을 사칭해 투표할 수 있다.
- **파급**: 권한 판정 지점이 [../02_features/08_permission_matrix.md](../02_features/08_permission_matrix.md)의 서버 검증 열과 일치한다. 연결이 끊기면 바인딩이 폐기되고 토큰은 재사용 경로가 없다([ADR-09](#adr-09--재접속-불가--방장-권한-비이양--방장-이탈-시-방-삭제)).

## ADR-08 — 연결 상태 3단계와 하트비트·이탈 유예 — ping 20초 · 타임아웃 60초 · 유예 참가자 30초·방장 60초

- **맥락**: **어느 원천에도 연결 끊김 판정 기준이 없다.** git 529e312 docs/db.md §10은 "연결 종료 시 퇴장 처리"라고만 하고 소켓 close인지 하트비트 타임아웃인지, 몇 초인지 정의하지 않는다. 정의가 없으면 구현자는 소켓 close 즉시 퇴장으로 만들고, 그러면 **모바일에서 탭을 백그라운드로 보낸 사람이 즉시 퇴장하고 방장이면 방이 사라진다.** 방장이 초대 링크를 공유하러 다른 앱으로 전환하는 것은 핵심 사용 흐름이다.
- **결정**: 연결 상태를 **연결 · 의심 · 이탈 확정** 3단계로 두고 다음 값을 고정한다.

| 항목 | 값 | 근거 |
|------|-----|------|
| 하트비트 | **WebSocket 제어 프레임 ping**, 주기 **20초** | 제어 프레임의 pong은 **브라우저가 JS 실행 없이 돌려준다.** 백그라운드 탭의 타이머 스로틀링이 하트비트를 죽이지 못한다. 애플리케이션 레벨 ping 이벤트를 쓰지 않는 이유가 이것이다 |
| pong 대기 | **3주기 = 60초** | 모바일 셀 전환·터널 통과로 수십 초 무응답이 생긴다. 1주기(20초)면 정상 사용자를 끊고, 5주기(100초)면 방 정리가 늦어진다 |
| 이탈 유예 — 참가자 | **30초** | 유예는 남은 사람 화면에 연결 끊김으로 보이는 시간이다. 더 길면 대기가 길어진다 |
| 이탈 유예 — 방장 | **60초** | 방 삭제는 되돌릴 수 없다. 앱 전환 왕복이 이 창 안에 들어가야 한다 |
| 미연결 슬롯 해제 | **15초** | 참가 등록 후 핸드셰이크가 없으면 슬롯만 차지한다. git 529e312 docs/api.md 연결 수명주기 6항의 값을 승계한다 |

  - **의심으로 가는 조건** — pong 3회 연속 미수신 · 전송 실패 · 소켓 close 관측.
  - **의심에서 돌아오는 조건** — **같은 소켓에서 프레임이 도착하면** 의심을 취소한다. close된 소켓에는 이 경로가 없다. 새 소켓으로 돌아오는 경로는 두지 않는다 — 그것이 재접속이기 때문이다.
  - **이탈이 즉시 확정되는 경우** — 사용자가 나가기 버튼을 눌러 명시적 나가기 이벤트가 도착했을 때와 방장 강퇴뿐이다. **클라이언트는 페이지 숨김·가시성 변경으로 나가기를 보내지 않는다.** 모바일에서 앱 전환만으로도 발화하기 때문이다.
- **버린 대안**: ① 소켓 close 즉시 퇴장 — 위 문제가 그대로 발생한다. ② 애플리케이션 ping 이벤트에 클라이언트가 응답 — 백그라운드 탭에서 타이머가 조여져 정상 사용자가 끊긴다. ③ 유예 안에 새 소켓 접속을 허용 — 재접속을 도입하는 것이고, 그러면 명단 스냅샷·미입력 처리·토큰 수명이 전부 흔들린다.
- **파급**: 이탈 확정 최대 지연은 **방장 120초 · 참가자 90초**다(타임아웃 + 유예). 10분 무활동 만료가 안전망으로 남는다([ADR-21](#adr-21--방-만료-스위퍼--10분-무활동--60초-주기--단일-스케줄러)). 유예 중 참가자는 준비 완료로 세지 않아 게임 시작을 막으며, 방장은 강퇴로 해소한다. **OS가 실제로 연결을 끊으면 유예 만료와 함께 방장의 방은 삭제된다** — 재접속 불가와 방장 비이양을 유지하는 대가이며 이 문서군이 이를 수용한다. 상세는 [02_realtime_websocket.md](./02_realtime_websocket.md)다.

## ADR-09 — 재접속 불가 · 방장 권한 비이양 · 방장 이탈 시 방 삭제

- **맥락**: docs_legacy/requirements.md §3.1의 공통 규칙과 §6의 설계 결정이 확정한 제품 규칙이지만 기술 파급이 커서 여기 함께 고정한다. 재접속을 허용하면 상태 복구·토큰 수명·명단 재바인딩이 전부 필요해진다.
- **결정**: 나갔다 들어오면 **새 참가자**이며 진행 중인 판에는 들어갈 수 없다. 끊긴 사람은 돌아올 수 없지만 명단 스냅샷에 후보로 남아 미입력 처리된다. 방장 권한은 이양하지 않으며 방장 이탈이 확정되면 방을 삭제한다.
- **버린 대안**: ① 유예 안 재접속 허용 — [ADR-08](#adr-08--연결-상태-3단계와-하트비트이탈-유예--ping-20초--타임아웃-60초--유예-참가자-30초방장-60초)에서 함께 검토해 버렸다. ② 방장 권한 자동 이양 — 룰렛·사다리는 입력 주체가 방장뿐이라 원치 않는 사람에게 진행 책임이 넘어간다.
- **파급**: 서버가 유지할 상태가 대폭 줄어 인메모리 설계가 성립한다([ADR-04](#adr-04--하이브리드-저장--진행-중-상태는-인메모리--영속-6테이블은-mysql-판정-경로에-db-왕복-금지)). 대신 이탈 판정을 신중하게 해야 한다는 요구가 [ADR-08](#adr-08--연결-상태-3단계와-하트비트이탈-유예--ping-20초--타임아웃-60초--유예-참가자-30초방장-60초)로 온다.

## ADR-10 — 순서 보장은 방 상태 버전 단조 증가. 역행 이벤트는 클라이언트가 버린다

- **맥락**: 한 소켓 안에서는 순서가 보장되지만, 방 스냅샷과 개별 갱신 이벤트가 경합하거나 클라이언트가 처리 지연으로 뒤늦게 반영하면 화면이 과거 상태로 되돌아갈 수 있다.
- **결정**: 방 상태가 바뀔 때마다 **방 상태 버전을 1 증가**시키고 모든 서버→클라이언트 이벤트에 실어 보낸다. 클라이언트는 **마지막으로 반영한 값보다 작거나 같은 이벤트를 버린다.** 상태 버전은 방 단위로 인메모리에서 증가시키고 영속 데이터가 바뀌는 이벤트는 DB의 상태 버전 컬럼과 함께 올린다. 클라이언트가 보낸 상태 버전이 서버 값과 다르면 그 요청을 거절한다.
- **버린 대안**: ① 타임스탬프 비교 — 같은 밀리초에 두 이벤트가 나면 순서가 결정되지 않는다. ② 이벤트별 시퀀스 번호 — 이벤트 종류마다 축이 생겨 화면 전체의 정합을 판단할 수 없다.
- **파급**: 모든 이벤트 페이로드에 상태 버전 필드가 붙는다(정본은 [../07_api/03_socket_events.md](../07_api/03_socket_events.md)). 스냅샷 재전송 없이도 화면이 뒤로 가지 않는다.

## ADR-11 — 브로드캐스트는 최선 노력. 전송 실패 소켓은 종료하고 DB를 되돌리지 않는다

- **맥락**: 방 10명 중 한 명의 소켓이 막히면 그 사람 때문에 판정 결과를 취소할 수는 없다. 결과는 이미 확정된 사실이다.
- **결정**: 브로드캐스트는 **최선 노력**이다. 전송에 실패한 소켓은 기록하고 종료하며, 그 참가자는 의심 단계로 내려간다([ADR-08](#adr-08--연결-상태-3단계와-하트비트이탈-유예--ping-20초--타임아웃-60초--유예-참가자-30초방장-60초)). **DB commit을 되돌리지 않는다.** 한 수신자의 실패가 다른 수신자의 전송을 막지 않도록 팬아웃은 수신자별로 독립 처리한다.
- **버린 대안**: ① 전원 확인 응답 후 확정 — 한 명의 지연이 전원의 결과 전환을 늦춰 결과 동시성 목표를 깨뜨린다. ② 실패 시 재전송 큐 — 재접속이 없어 큐의 소비자가 돌아오지 않는다.
- **파급**: 전송 실패 횟수가 모니터링 항목이 된다([ADR-27](#adr-27--모니터링-최소-세트를-배포와-같은-단위로-구축한다)). 결과를 못 본 참가자는 유예 만료와 함께 이탈 확정된다.

## ADR-12 — 판정은 서버 단독. 시간·순서 판정은 서버 도착 시각이며 시간초 경과 시간만 예외다

- **맥락**: 클라이언트가 시각을 보내면 조작할 수 있고, 네트워크가 빠른 사람이 유리해지면 공정성이 무너진다. 그러나 시간초 잡기는 **사람이 체감한 경과 시간**을 재는 게임이라 서버 도착 시각으로는 게임이 성립하지 않는다.
- **결정**: 모든 결과는 서버가 확정한다. 시간·순서 판정의 기준은 **서버 도착 시각**이다. **유일한 예외는 시간초 잡기의 경과 시간**이며, 클라이언트 단조 시계가 측정하고 서버가 자신이 관측한 시작·정지 도착 시각 차이로 허용 범위를 검증해 범위 밖이면 거부한다.
- **버린 대안**: ① 시간초도 서버 도착 시각으로 — 왕복 지연이 오차에 그대로 실려 네트워크가 빠른 사람이 이긴다. ② 클라이언트 시각을 서버 시각과 동기화 후 사용 — 동기화 오차와 지터가 남고 조작 표면은 그대로다.
- **파급**: 예외의 검증 방법은 [04_time_and_timing.md](./04_time_and_timing.md)가 확정하고, 이 예외로 남는 잔여 위협은 [../11_fairness/01_server_authority.md](../11_fairness/01_server_authority.md)가 등재한다.

## ADR-13 — 시각 표준 — UTC 저장 · 판정은 서버 단조 시계 정수 밀리초 · 동률은 수신 순서로 정렬

- **맥락**: 벽시계(시스템 시각)는 NTP 보정으로 뒤로 갈 수 있다. 그 위에서 경과 시간을 재면 음수 간격이 나온다. 부동소수점 초 단위 기록은 비교마다 오차가 달라진다.
- **결정**: 저장은 **UTC**, 표시는 사용자 시간대다. **판정에 쓰는 시각은 프로세스 단조 시계의 정수 밀리초**이며 라운드 시작 시각을 원점으로 하는 상대 값으로 기록한다. 벽시계는 표시·감사용으로만 쓴다. 두 입력의 도착 밀리초가 같으면 **수신 순서**로 결정론적으로 정렬한다.
- **버린 대안**: ① 벽시계로 판정 — 시각 보정 시 순서가 뒤집힌다. ② 부동소수점 초 — 같은 값의 비교가 환경에 따라 갈린다. ③ 동률을 난수로 — 재현할 수 없어 사후 검증이 불가능하다.
- **파급**: DB의 판정 시간 컬럼은 정수 밀리초다(정본 [../06_database/README.md](../06_database/README.md)). 판정 함수는 시각을 인자로 받고 내부에서 읽지 않아 순수 함수가 된다([03_judgment_engine.md](./03_judgment_engine.md)).

## ADR-14 — NFR-03의 ±10ms 구분을 폐기하고 판정창 그룹핑으로 재정의

- **맥락**: docs_legacy/requirements.md §5 NFR-03은 "눈치 동시 판정은 서버 도착 시각 기준 ±10ms 이내로 구분한다"고 적었다. **이 목표는 달성할 수 없다.** 모바일 네트워크의 왕복 지연 편차(지터)는 50~100ms 수준이고, 이는 10ms보다 크다. 서버 도착 시각이 10ms 차이라는 사실은 두 사람이 실제로 10ms 차이로 눌렀다는 뜻이 아니라 **회선 상태 차이**를 뜻한다.
- **결정**: ±10ms 구분 요구를 **폐기하고** 다음으로 재정의한다.
  1. 시간 기반 판정은 **정수 밀리초로 기록한다**(원 요구의 이 부분은 유지).
  2. **동시 판정의 단위는 게임 설정의 판정창**이다 — 눈치게임은 방장 설정 300ms 또는 500ms다. 같은 판정창에 도착한 입력은 **동시 입력으로 그룹핑**한다.
  3. 서버는 **판정창보다 작은 도착 시각 차이를 순위 차로 쓰지 않는다.**
  4. 그룹 안의 순서가 필요한 경우에만 도착 밀리초 → 수신 순서로 결정론적으로 정렬한다([ADR-13](#adr-13--시각-표준--utc-저장--판정은-서버-단조-시계-정수-밀리초--동률은-수신-순서로-정렬)).
  5. 시간초 잡기의 오차 비교는 클라이언트 단조 시계가 잰 경과 시간이므로 지터의 영향을 받지 않는다. 1밀리초 단위 비교가 유의미하며, 완전 동률은 재대결로 간다.
- **버린 대안**: ① 원 요구 유지 — 달성할 수 없는 기준을 문서에 남기면 검증 단계에서 통과할 방법이 없다. ② 판정창을 서버가 고정 — 방장 설정 항목(0.3·0.5초)이 이미 있으므로 축을 둘로 만들 이유가 없다.
- **파급**: 요구사항 정본이 NFR-03을 재정의된 문장으로 등재한다([../03_requirements/README.md](../03_requirements/README.md)). 눈치게임 판정 규칙이 판정창 그룹핑과 일치해야 한다([../05_game_rules/README.md](../05_game_rules/README.md)). 근거와 측정 방법은 [04_time_and_timing.md](./04_time_and_timing.md)에 둔다.

## ADR-15 — 제한 시간의 주체는 서버. 클라이언트 타이머는 표시 전용

- **맥락**: 제한 시간이 끝나는 순간을 클라이언트가 판정하면 시계를 늦춘 사람이 더 오래 입력할 수 있다.
- **결정**: 모든 제한 시간은 **서버 타이머가 마감**한다. 서버는 각 단계 진입 시 **마감까지 남은 밀리초**를 함께 내려보내고, 클라이언트는 그 값으로 카운트다운을 그린다. 클라이언트가 0에 도달해도 아무 일도 일어나지 않으며 마감은 서버가 선언한다. 마감 이후 도착한 입력은 버린다.
- **버린 대안**: ① 절대 마감 시각을 내려보내기 — 클라이언트 벽시계와 서버 벽시계의 차이가 그대로 표시 오차가 된다. 남은 시간을 내려보내면 편도 지연만큼만 어긋난다. ② 클라이언트가 마감을 통지 — 조작 표면이 된다.
- **파급**: 카운트다운 표시에 편도 지연만큼의 오차가 남으며 이는 수용한다. 게임별 제한 시간 값의 정본은 [../05_game_rules/README.md](../05_game_rules/README.md)다.

## ADR-16 — 난수는 서버가 시드에서 결정론적으로 도출. 시드는 확정 전에 내려보내지 않는다

- **맥락**: 룰렛·사다리는 서버 난수로 결과를 정한다. 연출은 클라이언트가 그리므로 결과와 연출이 어긋나면 안 되고, 사후에 "정말 무작위였는가"를 확인할 수 있어야 한다.
- **결정**: 라운드 생성 시 **암호학적 난수원으로 시드를 만들고 저장**한다. 결과는 시드에서 **결정론적 의사난수로 도출**해 같은 시드면 같은 결과가 나오게 한다. **시드는 결과 확정 전에 클라이언트에 내려보내지 않는다** — 미리 내려보내면 결과를 먼저 계산할 수 있다. 확정 후 결과와 시드를 함께 내려보내 연출을 재현한다. 시드는 방 수명 동안만 보관하고 방과 함께 삭제한다.
- **버린 대안**: ① 클라이언트 난수 — 결과를 클라이언트가 만들게 되어 공정성이 무너진다. ② 시드 없이 결과만 저장 — 사후 재현·검증이 불가능하다. ③ 시드 영구 보관 — 데이터 수명 규칙과 충돌한다.
- **파급**: 게임별 시드 사용 규칙은 [../05_game_rules/README.md](../05_game_rules/README.md), 익명성·검증 관점은 [../11_fairness/01_server_authority.md](../11_fairness/01_server_authority.md)다.

## ADR-17 — 멱등은 요청 식별자 + 라운드·단계·반복 회차 일치 검사 2중으로 강제

- **맥락**: 소켓 재전송·더블 클릭·연출 중 중복 입력이 실제로 발생한다. 결선이 반복되는 게임에서는 **직전 회차의 입력이 새 회차에 도착**할 수도 있다.
- **결정**: 두 겹으로 막는다.
  1. **요청 식별자** — 클라이언트가 요청마다 식별자를 붙이고 서버는 최초 1건만 인정한다. 영속 대상(투표 등)은 DB UNIQUE로, 인메모리 대상은 라운드 상태의 처리 완료 집합으로 막는다. 재전송에는 최초 결과를 그대로 돌려준다.
  2. **문맥 일치** — 입력에 실린 라운드 식별자 · 단계 · 반복 회차가 서버의 현재 값과 모두 같아야 수용한다. 하나라도 다르면 조용히 버리고 **보낸 사람에게만** 거부를 알린다.
  - 마감 이후 도착과 명단 스냅샷에 없는 참가자의 입력도 버린다.
- **버린 대안**: ① 요청 식별자만 — 회차만 바뀐 지난 입력이 새 회차에 반영된다. ② 문맥 일치만 — 같은 회차 안의 중복 클릭을 막지 못한다.
- **파급**: 모든 클라이언트→서버 게임 입력 이벤트에 요청 식별자 필드가 붙는다([../07_api/03_socket_events.md](../07_api/03_socket_events.md)). 계약 테스트에서 같은 요청을 반복 전송해 반영 1건을 확인한다.

## ADR-18 — 트랜잭션 경계와 잠금 순서. commit 이후에만 브로드캐스트

- **맥락**: 마지막 한 자리 동시 입장 · 동시 게임 시작 · 중복 투표는 실제 경합이다. 브로드캐스트를 트랜잭션 안에서 보내면 롤백된 사실이 화면에 남는다.
- **결정**:
  - 격리 수준은 REPEATABLE READ, 경합 행(rooms · game_rounds)만 짧게 배타 잠금한다.
  - **잠금 순서는 rooms → game_rounds → participants → votes 한 방향으로 고정**해 교착을 구조적으로 줄인다.
  - **트랜잭션 안에서 소켓 전송과 외부 호출을 하지 않는다.** commit이 성공한 뒤에만 브로드캐스트한다.
  - 교착·잠금 대기 시간 초과는 트랜잭션 전체를 **최대 3회** 짧은 무작위 지연과 함께 재시도한다.
  - 길이·형식 검증은 트랜잭션 전에, 상태·권한·정원 검증은 잠금 후 다시 한다.
- **버린 대안**: ① 낙관적 갱신만 — 정원 초과 입장을 사후에 되돌려야 하고 그 사이 브로드캐스트가 나간다. ② 방 단위 전역 잠금을 길게 — 밀리초 경로가 DB 잠금에 묶인다.
- **파급**: 상세 표는 [../06_database/README.md](../06_database/README.md)가 갖고, 본 폴더는 경계 규칙만 고정한다. 재시도 횟수·교착 발생 수가 모니터링 항목이 된다.

## ADR-19 — 동점 결선·재대결은 최대 3회. 초과 시 방장이 고른다

- **맥락**: docs_legacy/requirements.md §6의 동점 처리 결정은 "단독 승자가 나올 때까지 결선을 반복"으로 정하고 반복 상한을 두지 않았으며, 같은 문서 §8이 그 규칙의 종료성을 스스로 의심하고 있었다. 킹메이커·익명 저격·시간초 잡기에는 종료하지 않는 입력 조합이 존재한다 — 전원이 같은 선택을 반복하면 결선이 끝나지 않는다.
- **결정**: 동점 결선·동점자 재대결·무효 라운드 재시작을 **최대 3회**로 제한한다. 3회에도 단독 승자가 없으면 자동 반복을 멈추고 **방장이 다음 동작을 고른다.** 반복 회차는 라운드 상태에 두고 판정 함수의 입력으로 넘긴다. 상한을 두지 않던 구 규칙은 **폐기한다.**
- **버린 대안**: ① 상한 없이 반복 — 종료가 보장되지 않는다. ② 3회 초과 시 서버 난수로 결정 — 투표로 정하기로 한 게임의 성격이 마지막에 뒤집힌다. ③ 상한을 크게(10회) — 종료는 보장되지만 실제 사용에서 지루함으로 이탈이 생긴다.
- **파급**: 판정 결과 종류에 방장 선택 대기가 추가된다([03_judgment_engine.md](./03_judgment_engine.md)). 각 게임 문서의 종료 증명이 이 상한을 근거로 쓴다([../05_game_rules/README.md](../05_game_rules/README.md)).

## ADR-20 — 서버 재기동 시 DB에 남은 방을 전량 정리한다. 상태 복구를 시도하지 않는다

- **맥락**: 진행 중 상태가 프로세스 메모리에만 있으므로 재기동하면 사라진다. 그러면 DB에는 대기·진행 상태의 방이 남고 그 방들은 **어느 소켓도 붙어 있지 않은 고아**가 된다. 초대 코드도 회수되지 않아 새 방이 그 코드를 쓸 수 없다.
- **결정**: 기동 시 **DB에 남은 방을 전량 정리**한다. 단일 인스턴스라 기동 시점의 인메모리 방 수는 0이고, 따라서 **DB에 있는 모든 방이 고아다** — 선별 기준이 필요 없다. 진행 중이던 라운드를 취소로 닫고 방을 삭제하며 하위 데이터는 함께 삭제된다. 정리가 끝나기 전에는 준비 상태를 올리지 않는다. **상태 복구를 시도하지 않는다.**
- **버린 대안**: ① 방을 남기고 재접속을 기다린다 — 재접속 경로가 없어 아무도 돌아오지 않고 초대 코드만 잠긴다. ② 스냅샷으로 복구 — 준비 상태·소켓·판정창은 스냅샷으로 되살릴 수 없고, 살릴 수 있는 부분만 살리면 참가자가 절반만 있는 방이 된다. ③ 만료 스위퍼에 맡긴다 — 최대 10분 동안 코드가 잠기고 참가자가 죽은 방에 입장한다.
- **파급**: 배포는 곧 전 방 소멸이다([ADR-24](#adr-24--배포는-다운타임을-수용한다-배포-시-진행-중-방은-사라진다)). 절차와 의사코드는 [06_memory_persistence_split.md](./06_memory_persistence_split.md)에 둔다.

## ADR-21 — 방 만료 스위퍼 — 10분 무활동 · 60초 주기 · 단일 스케줄러

- **맥락**: 방장이 브라우저를 강제 종료해 이탈 확정이 늦어지거나, 전원이 조용히 사라진 방이 DB에 남을 수 있다.
- **결정**: 방은 **방장 이탈 확정 즉시 · 마지막 참가자 이탈 즉시 · 10분 무활동** 중 먼저 오는 것으로 삭제한다. 무활동 만료는 **60초 주기 스위퍼**가 만료 시각 인덱스로 대상을 찾아 처리한다. 스위퍼는 애플리케이션 프로세스 안의 단일 스케줄러이며([ADR-02](#adr-02--단일-인스턴스--워커-1개-고정-수평-확장무중단-배포redis-미채택)) 중복 실행돼도 결과가 같도록 만든다. 삭제 전 만료 조건을 잠금 후 다시 확인한다.
- **버린 대안**: ① 별도 크론 컨테이너 — 운영 대상이 늘고 인메모리 방과 DB 방의 정리가 두 프로세스로 갈린다. ② 만료 즉시 이벤트 기반 삭제 — 마지막 활동마다 타이머를 다시 걸어야 하고 방 100개면 타이머가 100개다. 주기 스캔이 단순하다.
- **파급**: 만료 지연 상한은 주기와 같은 60초다. 만료 대상 수·삭제 성공 실패가 모니터링 항목이 된다([ADR-27](#adr-27--모니터링-최소-세트를-배포와-같은-단위로-구축한다)).

## ADR-22 — 배포 형상 — 프론트 Vercel · 백엔드 AWS EC2 · MySQL 8.4 Docker Compose. wss가 필수라 도메인·인증서가 선결 조건

- **맥락**: 프론트는 정적 SPA라 CDN이 맞고, 백엔드는 장기 연결 소켓을 유지해야 해 서버리스가 맞지 않는다.
- **결정**: 프론트엔드는 **Vercel**, 백엔드는 **AWS EC2** 한 대, DB는 같은 호스트의 **MySQL 8.4** 컨테이너(Docker Compose)다. **Vercel이 HTTPS로 서비스되므로 브라우저가 평문 WebSocket 연결을 차단한다 — 백엔드는 wss가 필수다.** 따라서 **백엔드 도메인과 TLS 인증서 발급이 첫 통합 배포의 선결 조건**이며, 이것이 없으면 로컬 개발 외에는 아무것도 동작하지 않는다.
- **버린 대안**: ① 백엔드도 서버리스 — 장기 연결과 인메모리 상태가 성립하지 않는다. ② IP 직접 접속 — 인증서를 발급할 수 없어 wss를 쓸 수 없다. ③ 관리형 DB — 방 데이터가 방 수명 동안만 존재하고 규모가 작아 비용 대비 이점이 없다.
- **파급**: 배치도·도메인·인증서 갱신·환경변수는 [07_deployment_topology.md](./07_deployment_topology.md)가 확정한다. 프론트의 소켓 주소가 빌드 시 주입되는 환경변수가 된다.

## ADR-23 — Nginx 리버스 프록시가 TLS를 끝내고 WebSocket 업그레이드를 중계한다

- **맥락**: 애플리케이션이 직접 TLS를 다루면 인증서 갱신이 배포에 묶인다. 그리고 **Nginx 기본 설정으로는 WebSocket 핸드셰이크가 실패한다** — 업그레이드 헤더를 넘기지 않기 때문이다. 대기방 진입 이후 전 기능이 소켓이라 이게 안 되면 아무것도 동작하지 않는다.
- **결정**: EC2 앞단에 **Nginx**를 두고 TLS 종단·업그레이드 헤더 중계·읽기 타임아웃·페이로드 상한을 담당시킨다. 읽기 타임아웃은 **75초**로 둔다 — 하트비트 주기 20초와 pong 대기 60초보다 커야 정상 연결이 유휴로 끊기지 않는다([ADR-08](#adr-08--연결-상태-3단계와-하트비트이탈-유예--ping-20초--타임아웃-60초--유예-참가자-30초방장-60초)).
- **버린 대안**: ① 애플리케이션 직접 TLS — 인증서 갱신마다 프로세스를 재기동해야 하고 재기동은 전 방 소멸이다. ② 프록시 없이 포트 노출 — 인증서·헤더·상한을 애플리케이션이 전부 떠안는다.
- **파급**: 설정 예시와 검증 항목은 [07_deployment_topology.md](./07_deployment_topology.md)에 둔다. 인증서 갱신은 Nginx 재적재만으로 끝나 방을 죽이지 않는다.

## ADR-24 — 배포는 다운타임을 수용한다. 배포 시 진행 중 방은 사라진다

- **맥락**: 인메모리 상태와 단일 인스턴스 때문에 무중단 배포가 원리적으로 불가능하다. 방은 익명·일회성이라 사전 공지 대상도 없다.
- **결정**: 백엔드 배포는 **다운타임을 수용한다.** 배포 순서는 이미지 준비 → 마이그레이션 1회 실행 → 프로세스 중지 → 새 프로세스 기동 → 고아 방 전량 정리 → 준비 상태 확인 → 스모크 확인이다. **중지 순간 모든 소켓이 끊기고 진행 중이던 방이 사라진다.** 배포 창은 사용이 적은 시각으로 잡는다. 프론트엔드 배포는 정적 자원 교체라 방에 영향을 주지 않는다.
- **버린 대안**: ① 새 프로세스를 띄우고 트래픽을 옮기는 방식 — 방 상태가 이전되지 않아 옮겨간 참가자가 방을 찾지 못한다. ② 배포 중 신규 방 생성만 차단하고 기존 방을 기다리기 — 10분 무활동 만료까지 최대 10분 대기해야 하고 그 사이 새 방을 못 만든다.
- **파급**: 롤백은 이전 이미지 태그 재기동이며 마이그레이션은 되돌리지 않는다([ADR-25](#adr-25--스키마-마이그레이션은-alembic으로-배포-단계에서-1회-실행한다)). 다운타임 추정과 체크리스트는 [07_deployment_topology.md](./07_deployment_topology.md)에 둔다.

## ADR-25 — 스키마 마이그레이션은 Alembic으로 배포 단계에서 1회 실행한다

- **맥락**: 애플리케이션 기동마다 마이그레이션을 실행하면 기동 실패가 스키마 상태를 애매하게 만든다. MySQL의 DDL은 암묵적 커밋이 일어나 중간 실패를 자동 롤백에 맡길 수 없다.
- **결정**: **Alembic**을 쓰고 마이그레이션은 **배포 절차의 별도 단계에서 1회만** 실행한다. 이미 적용된 리비전 파일은 수정하지 않고 새 리비전을 추가한다. 자동 생성 결과는 후보안으로만 쓰고 사람이 검토한다. 파괴적 변경 전에는 백업과 복원 절차를 먼저 검증한다. 호환이 필요한 변경은 추가 → 양쪽 호환 → 이관 → 제거 순서로 나눈다. 리비전 head가 여러 개면 배포 전에 하나로 정리한다.
- **버린 대안**: ① 기동 시 자동 마이그레이션 — 기동 실패와 스키마 실패가 구분되지 않는다. ② 수동 SQL 적용 — 적용 이력이 남지 않아 롤백 시 현재 스키마를 알 수 없다.
- **파급**: 준비 상태 점검이 DB 연결과 리비전 일치를 함께 본다. 마이그레이션 규약 상세는 [../06_database/README.md](../06_database/README.md)가 갖는다.

## ADR-26 — 부하 목표 100방·1,000연결. 단일 프로세스 수용 여부는 산술 추정으로 판정하고 실측 전에 단정하지 않는다

- **맥락**: docs_legacy/requirements.md §5 NFR-07은 동시 100방·방당 최대 10명을 잠정 목표로 두고 §8 Q-04에서 "백엔드 1차 통합 후 실측"으로 미뤄 두었다. 단일 프로세스([ADR-02](#adr-02--단일-인스턴스--워커-1개-고정-수평-확장무중단-배포redis-미채택))가 이 목표를 감당하는지 확인하지 않으면 배포 후에야 알게 된다.
- **결정**: 목표를 **동시 100방 · 1,000 WebSocket 연결**로 확정하고, 감당 여부를 **산술 추정으로 먼저 판정**한다. 추정 결과는 **견딜 것으로 보인다**이며, 전제는 ① 판정·브로드캐스트 경로에 동기 블로킹 호출이 없다 ② 같은 페이로드를 방 단위로 1회만 직렬화한다 ③ 파일 디스크립터 상한을 올린다 ④ 인스턴스 네트워크 대역폭이 100Mbps 이상이다 넷이다. **실측 전에는 달성했다고 단정하지 않는다.** 부하 시험 절차를 배포 체크리스트에 넣는다.
- **버린 대안**: ① 추정 없이 실측만 기다리기 — 병목이 구조에서 나오면 그때는 이미 만들어져 있다. ② 추정치를 확정 사실로 기록 — 검증하지 못한 것을 검증된 사실로 단정하는 것이며 문서 규약이 금지한다.
- **파급**: 계산 근거·가정·병목 후보·시험 절차는 [07_deployment_topology.md](./07_deployment_topology.md)에 둔다. 브로드캐스트 직렬화 1회 재사용이 성능 요구가 아니라 **구현 규약**이 된다([02_realtime_websocket.md](./02_realtime_websocket.md)).

## ADR-27 — 모니터링 최소 세트를 배포와 같은 단위로 구축한다

- **맥락**: 단일 인스턴스라 장애가 곧 전면 중단이고, 방이 일회성이라 사후 재현이 불가능하다. 무엇이 잘못됐는지는 그 순간의 지표로만 알 수 있다.
- **결정**: 배포와 같은 변경 단위에서 **최소 지표 세트**를 구축한다 — 프로세스 자원(CPU·메모리·파일 디스크립터) · 소켓(연결 수·비정상 종료·전송 실패·하트비트 타임아웃) · 방(활성 방 수·만료 삭제 수·고아 정리 수) · DB(연결 풀 사용률·느린 질의·교착·재시도) · 무결성(제약 위반·상태 버전 충돌) · 운영(리비전·마이그레이션 결과·백업 결과). 익명 투표 응답과 로그에 지목자 식별값이 섞이는지 샘플 점검을 정기 항목으로 둔다.
- **버린 대안**: ① 장애 후 구축 — 첫 장애의 원인을 영영 모른다. ② 풀 스택 관측 도구 도입 — 단일 호스트·MVP 규모에 비해 운영 비용이 크다.
- **파급**: 항목 표와 즉시 확인 대상은 [07_deployment_topology.md](./07_deployment_topology.md)에 둔다. 익명성 점검 항목은 [../11_fairness/01_server_authority.md](../11_fairness/01_server_authority.md)와 짝을 이룬다.

## ADR-28 — 스키마를 번호 붙은 SQL 파일로 관리하고 마이그레이션 도구를 두지 않는다

- **맥락**: 방이 일회성이고 재기동이 모든 방을 지우므로([ADR-20](#adr-20--서버-재기동-시-db에-남은-방을-전량-정리한다-상태-복구를-시도하지-않는다)) 보존해야 할 운영 데이터가 없다. 마이그레이션 도구는 **기존 데이터를 지키며 구조를 바꾸는** 문제를 푸는 물건이다. 한편 백엔드와 DB를 같은 Docker 형상으로 올리므로 스키마는 백엔드 코드가 아니라 배포 단위에서 읽을 수 있는 자리에 있어야 한다.
- **결정**: 테이블 6개를 저장소 루트의 db_migration/sql에 **테이블당 한 파일씩 번호를 붙여** 두고 리비전 관리를 두지 않는다. 적용은 번호 오름차순이며 Docker의 initdb.d가 파일명 알파벳 순으로 같은 순서를 만든다. 구조를 바꾸면 파일을 고치고 다시 적용한다. 대신 **기동 시 업무 테이블 존재를 확인**하고 없으면 기동을 멈춘다 — 리비전 대조를 두지 않는 대신의 최소 확인이다. 적용 결과는 db_migration/sql/verify.sql이 개수로 검증하고 어긋나면 오류로 멈춘다.
- **버린 대안**: ① Alembic 도입 — 지킬 데이터가 없는데 리비전 그래프·자동 생성 diff의 학습·운영 비용을 진다. 생성 컬럼 식·복합 FK·복합 UNIQUE를 자동 생성이 정확히 재현하지 못해 결과를 어차피 사람이 고쳐 쓴다. ② 단일 schema.sql — 파일 하나가 6테이블·24 CHECK를 담아 변경 지점을 리뷰에서 짚기 어렵고, 맨 앞에 DROP TABLE 블록을 두게 되어 운영에서 실수 한 번이 전건 삭제가 된다. ③ 확인 없이 기동 — 구조가 어긋난 DB에 **전건 삭제**인 기동 정리를 돌리게 된다.
- **파급**: 스키마가 바뀌면 컨테이너를 다시 만든다. 파일에 DROP TABLE을 두지 않으므로 재적용은 db_migration/apply.sh --fresh처럼 지우려는 의도를 명시적으로 밝혀야 한다. 운영 데이터를 보존해야 하는 요구가 생기면 이 결정을 먼저 뒤집는다. 파일 규약·계정·배포 절차의 정본은 [../06_database/07_migrations_seed.md](../06_database/07_migrations_seed.md)다.

## ADR-29 — memberToken은 서명 토큰이 아니라 인메모리 바인딩을 가리키는 핸들이다

- **맥락**: 권한 판정에 쓸 값을 클라이언트가 들고 다니게 하면 그 값을 신뢰하는 코드가 언젠가 들어온다. 재접속이 없고 방이 일회성이라 무상태 토큰의 이점(서버 조회 없이 검증)이 얻어지는 자리도 없다.
- **결정**: 구조 없는 난수 문자열을 발급하고 서버 메모리의 (참가자·방) 바인딩을 가리키게 한다. **바인딩에 역할을 담지 않는다** — 방장 여부는 조회한 participants.role로만 판정한다. 검증은 두 겹이다: 메모리 바인딩 조회 + DB에서 left_at 확인.
- **버린 대안**: ① JWT — 클라이언트가 파싱해 의미를 읽는 경로가 생기고, 만료 전 무효화가 어려워 강퇴·이탈과 어긋난다. ② 바인딩에 is_host 저장 — 방장 이양이 없어도 그 값을 믿는 코드가 생긴다.
- **파급**: 재기동으로 토큰이 전부 사라지는 것이 정상이다. 가리킬 방이 함께 사라지므로 정합적이다.

## ADR-30 — 외부 식별자를 접두사 붙은 난수로 발급하고 내부 PK를 노출하지 않는다

- **맥락**: BIGINT 자동 증가 PK는 방을 가로질러 연속 증가한다. API에 노출하면 두 방의 식별자 차이로 그 사이에 만들어진 참가자 수·생성 순서를 추정할 수 있다.
- **결정**: mbr_ · rnd_ · opt_ 접두사에 62진 난수 22자를 붙인 값을 API·소켓에 쓰고, 내부 PK는 어느 페이로드에도 싣지 않는다. 형식은 DB의 CHECK가 강제한다.
- **버린 대안**: ① PK 그대로 노출 — 위 추정이 가능하다. ② UUID — 하이픈 때문에 문자 집합 제약이 늘어나고 길다.
- **파급**: 접두사가 대상 종류를 말하므로 로그에서 무엇을 가리키는 값인지 바로 읽힌다.

## ADR-31 — 소켓 경로에 방 코드를 두고 토큰은 첫 프레임으로 받는다

- **맥락**: 브라우저 WebSocket API는 요청 헤더를 지정할 수 없다. 토큰을 쿼리 문자열에 담으면 프록시·접근 로그에 그대로 남는다.
- **결정**: 경로는 /ws/rooms/{code}로 두고 토큰은 연결 직후 conn:auth 프레임으로 받는다. **인증 전에는 다른 어떤 이벤트도 처리하지 않으며**, 3초 안에 오지 않으면 4408로 닫는다. 경로의 코드와 페이로드의 코드가 다르면 거절한다.
- **버린 대안**: ① 쿼리 문자열 토큰 — 로그 노출. ② 경로 없는 단일 엔드포인트 — 접근 로그와 지표에서 방을 구분할 수 없다.
- **파급**: 인증 전 구간이 생기므로 그 구간의 타임아웃과 종료 코드를 규정해야 한다([02_realtime_websocket.md](./02_realtime_websocket.md)).

## ADR-32 — 멱등 캐시를 인메모리에 둔다

- **맥락**: 멱등은 성능 대책이 아니라 판정 규칙이다([../11_fairness/03_anti_cheat.md](../11_fairness/03_anti_cheat.md)). 그러나 그 규칙이 지켜져야 하는 창은 방의 수명을 넘지 않는다.
- **결정**: Idempotency-Key를 최초 응답·본문 해시와 함께 메모리에 보관하고 방 무활동 만료와 같은 10분 뒤 버린다. 같은 키에 다른 본문이 오면 거절한다.
- **버린 대안**: ① DB 테이블 — 쓰기가 요청마다 늘고, 재기동이 방을 지우므로 남겨도 가리킬 대상이 없다. ② 보관하지 않음 — 재전송이 두 번 처리된다.
- **파급**: 주기 스위퍼가 만료 항목을 함께 청소한다.

## ADR-33 — 이탈 처리를 소켓 태스크의 수명에서 분리한다

- **맥락**: 이탈은 소켓보다 오래 산다 — 유예가 30·60초다. 그런데 처음 구현은 소켓 핸들러의 finally에서 이탈 처리를 기다렸고, **그 태스크가 취소되는 순간 열려 있던 DB 커넥션이 반납되지 않은 채 남았다.** 취소된 컨텍스트에서는 정리 코드도 끝까지 돌지 못한다.
- **결정**: 소켓 종료가 관측되면 이탈 처리를 **독립 태스크로 떼어 낸다.** 태스크 참조를 붙들어 두어 GC가 중간에 거둬 가지 않게 한다.
- **버린 대안**: ① finally에서 await — 위 누수. ② 이탈을 동기 처리 — 브로드캐스트와 DB 쓰기가 소켓 종료 경로를 막는다.
- **파급**: 소켓이 닫힌 뒤에도 유예 타이머가 살아 있어야 하므로, 방 삭제 시 그 타이머를 반드시 함께 취소한다.

## ADR-34 — 미연결 슬롯 회수를 주기 스위퍼가 아니라 가입 시점 타이머로 잰다

- **맥락**: 가입 후 15초 안에 핸드셰이크가 없으면 슬롯을 푼다. 이 값을 60초 주기 스위퍼에 맡기면 실질 회수 시간이 15~75초가 되고, **정원이 찬 방에서 그 차이는 못 들어오는 사람의 대기 시간이 된다.**
- **결정**: 가입이 커밋된 직후에 회수 타이머를 걸고, 만료 시점에 핸드셰이크 흔적이 없으면 이탈로 확정한다. 흔적은 인메모리에 남기며 **지금 붙어 있는가와 구분한다** — 붙었다 끊긴 사람은 이탈 유예가 맡는다.
- **버린 대안**: ① 스위퍼에 통합 — 위 지연. ② DB 컬럼으로 핸드셰이크 여부 기록 — 재기동으로 사라져야 정상인 값을 영속시킨다.
- **파급**: 3분 미확정 회수와 10분 만료는 성격이 주기적이라 스위퍼가 그대로 맡는다.

## ADR-35 — 방 상태 전표를 실행 가능한 단일 모듈로 둔다

- **맥락**: (상태 × 이벤트) 전표는 [05_room_state_machine.md](./05_room_state_machine.md)가 정본이며 **모든 칸을 채우라**고 규정한다. 그런데 그 판정이 서비스마다 인라인 조건문으로 흩어지면 칸이 비어도 아무도 모른다.
- **결정**: 전표를 그대로 옮긴 순수 모듈을 두고 소켓 이벤트의 **사전 게이트**로 쓴다. 빈 칸이 없음을 테스트가 강제한다. 거부·무시·버림을 구분해 담는다.
- **버린 대안**: ① 서비스별 인라인 검사만 — 전표와 구현이 조용히 갈라진다. ② 전표를 유일한 판정으로 삼기 — 정원·준비 상태는 검사와 커밋 사이에 바뀌므로 **잠근 뒤 재검증**이 여전히 필요하다.
- **파급**: 사전 게이트는 빠른 실패용이고 최종 판정은 서비스가 한다. 두 층이 같은 규칙을 보되 역할이 다르다.

## ADR-36 — 초대 코드 조회 상한을 고정 창으로 세고 전달 헤더를 기본으로 믿지 않는다

- **맥락**: 초대 코드가 숫자 6자리라 GET /api/rooms/{code}만 무차별 대입으로 방 존재 여부를 캐낼 수 있다.
- **결정**: 이 표면에만 IP 단위 분당 상한을 걸고, 넘으면 지연을 준 뒤 429로 거절한다. 창은 고정 창으로 센다. **X-Forwarded-For는 기본으로 믿지 않는다** — 프록시 없이 노출된 상태에서 믿으면 헤더를 매 요청 바꿔 상한을 그냥 우회한다.
- **버린 대안**: ① 전 표면에 상한 — 정상 사용자의 연타가 먼저 걸린다. ② 슬라이딩 창 — 창 경계의 2배 통과가 여기서는 문제되지 않는다(분당 40회로도 전수에 17일). ③ XFF 무조건 신뢰 — 위 우회.
- **파급**: 프록시 뒤에 둘 때만 신뢰 설정을 켠다. 켜지 않으면 모든 요청이 프록시 IP 하나로 묶여 상한이 전 세계 공유가 된다.

## ADR-37 — 소켓 이벤트 TS 타입을 스키마에서 생성한다

- **맥락**: REST는 FastAPI가 OpenAPI 문서를 자동 생성하므로 프론트가 타입을 뽑을 표면이 있다. **소켓에는 그런 표면이 없다.**
- **결정**: 서버의 이벤트 스키마에서 TS 타입을 생성하는 스크립트를 두고 산출물을 저장소에 함께 둔다. 생성기가 들고 있는 이벤트 목록이 라우터의 분기표와 같은지 테스트가 강제한다.
- **버린 대안**: ① 손으로 옮겨 적기 — 스키마가 바뀔 때 조용히 어긋난다. ② 프론트가 직접 정의 — 같은 규약이 두 벌이 된다.
- **파급**: 이벤트를 붙이면 생성기 목록도 같은 변경 단위에서 갱신한다.
