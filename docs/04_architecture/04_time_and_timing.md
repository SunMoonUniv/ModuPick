# 04 시간과 타이밍

> **대상**: 시각 표준 · 서버 타이머 주체 · 제한 시간 동기화 · 지터가 판정에 미치는 영향과 대응 · 시간초 예외의 검증 방법
> **작성일**: 2026-08-02
> **원천**: docs_legacy/requirements.md §3.1 G-8 · §3.4 방장 설정(판정창 0.3·0.5초 · 목표 시간 5·7·10초 · 투표 시간) · §5 NFR-01~03 · §6 설계 결정 · git 529e312 docs/db.md §19(세션 시간대 +00:00) · git ecceb11 docs/03_architecture/01_data_model.md §2.3 · [../README.md](../README.md)(전역 불변식) · [../05_game_rules/README.md](../05_game_rules/README.md)

시간은 ModuPick에서 **표시의 문제가 아니라 판정의 문제**다. 눈치게임은 누가 먼저 눌렀는가로, 시간초 잡기는 몇 밀리초 어긋났는가로 승자가 갈린다. 그래서 어느 시계로 재는가, 그 시계가 뒤로 갈 수 있는가, 네트워크가 그 값을 얼마나 왜곡하는가를 먼저 정해야 한다.

핵심은 두 문장이다. **판정에 쓰는 시각은 서버가 찍고, 서버가 관측할 수 없는 것만 클라이언트가 재되 서버가 범위를 검증한다.** 그리고 **네트워크 지터보다 작은 시각 차이를 순위 차로 주장하지 않는다.**

## 시각 표준

| 축 | 규칙 |
|----|------|
| 저장 | **UTC**로 저장한다. 서버와 DB 세션의 시간대를 +00:00으로 고정한다 |
| 표시 | 사용자 시간대로 변환해 보여 준다. 변환은 클라이언트가 한다 |
| 판정 | **프로세스 단조 시계의 정수 밀리초.** 라운드 시작을 원점으로 하는 상대 값으로 기록한다 |
| 기록 자료형 | 부동소수점 초를 쓰지 않는다. 정수 밀리초를 쓴다 |
| 벽시계의 용도 | 생성·시작·종료 시각 표시와 감사. **판정에 쓰지 않는다** |
| 동률 | 도착 밀리초가 같으면 수신 순번으로 결정론적으로 정렬한다. 난수로 가르지 않는다 |

**벽시계를 판정에 쓰지 않는 이유**는 시각 보정 때문이다. 시스템 시각은 시각 동기화로 뒤로 갈 수 있고, 그 위에서 경과 시간을 재면 음수 간격이 나온다. 단조 시계는 뒤로 가지 않으므로 간격 측정에 안전하다. 대신 단조 시계는 절대 시각이 아니라 프로세스 기동 이후의 상대 값이므로, 저장·표시용 벽시계와 **두 축을 함께 유지한다.**

## 서버 타이머 주체

**모든 제한 시간은 서버 타이머가 마감한다.** 클라이언트 타이머는 표시 전용이다(ADR-15).

| 대상 | 주체 | 값의 정본 |
|------|------|-----------|
| 게임 단계 제한 시간 | 서버 | [../05_game_rules/README.md](../05_game_rules/README.md) |
| 익명 저격 투표 시간 | 서버 | 방장 설정(기본 10초 · 5~60초) |
| 시간초 잡기 제한 시간 | 서버 | 목표 시간 + 3초 |
| 눈치게임 라운드 제한 시간 | 서버 | 방장 설정(10·15·20초) |
| 킹메이커 제출·투표 시간 | 서버 | 제출 2분 · 투표 1분 |
| 규칙 가이드 3초 · 결과 전환 3초 | **클라이언트** | 판정과 무관한 연출 지연이라 예외다 |
| 방 10분 무활동 만료 | 서버 스위퍼 | [06_memory_persistence_split.md](./06_memory_persistence_split.md) |
| 하트비트·이탈 유예 | 서버 | [02_realtime_websocket.md](./02_realtime_websocket.md) |

- 클라이언트 카운트다운이 0에 도달해도 **아무 일도 일어나지 않는다.** 마감은 서버가 선언하고 그때 판정이 돌아간다.
- 마감 이후 도착한 입력은 버린다. 마감 직전에 눌렀지만 지연으로 늦게 도착한 입력도 마찬가지다 — 이것이 서버 도착 시각 기준의 대가이며, 게임 설계가 제한 시간에 여유를 두어 흡수한다.
- 서버 타이머는 라운드 상태에 핸들로 매달아 두고, 단계가 바뀌거나 조기 판정이 일어나면 **반드시 취소한다.** 취소하지 않으면 지난 단계의 타이머가 새 단계를 마감시킨다.

## 제한 시간 동기화

```
단계 진입 시 서버가 내려보내는 값
    phase              현재 단계
    remaining_ms       마감까지 남은 밀리초        ← 절대 시각이 아니라 남은 시간이다
    duration_ms        이 단계의 전체 길이         ← 진행 막대 표시에 쓴다

클라이언트
    t0 = performance.now()                        # 수신 시점의 단조 시계
    남은 시간 = remaining_ms - (performance.now() - t0)
    0에 도달하면 대기 표시로 바꾸고 기다린다       # 마감을 선언하지 않는다
```

**절대 마감 시각을 내려보내지 않는다.** 절대 시각을 쓰면 클라이언트 벽시계와 서버 벽시계의 차이가 그대로 표시 오차가 되고, 사용자가 기기 시각을 바꾸면 카운트다운이 어긋난다. 남은 시간을 내려보내면 오차는 **편도 지연만큼**으로 제한된다.

표시 오차의 크기는 편도 지연(추정 25~50밀리초)이며 이는 수용한다. 카운트다운이 0.05초 빨리 끝나 보이는 것은 판정에 영향을 주지 않는다 — 판정은 서버가 하기 때문이다.

## 지터가 판정에 미치는 영향

### 문제

같은 순간에 두 사람이 버튼을 눌러도 서버에 도착하는 시각은 회선 상태에 따라 갈린다. 모바일 네트워크의 왕복 지연 편차, 곧 **지터는 50~100밀리초 수준**이다(일반적 관측이며 본 문서군의 실측값이 아니다). 이 값은 사람의 반응 시간 차이보다 크지 않지만, **밀리초 단위 순위 판정보다는 훨씬 크다.**

즉 서버 도착 시각이 10밀리초 차이라는 사실은 두 사람이 10밀리초 차이로 눌렀다는 뜻이 아니다. **회선이 10밀리초만큼 달랐다는 뜻이다.**

### 대응 — NFR-03 재정의

docs_legacy/requirements.md §5의 NFR-03은 "시간 기반 판정은 정수 밀리초로 기록하고, 눈치 동시 판정은 서버 도착 시각 기준 ±10ms 이내로 구분한다"고 적었다. **뒷부분은 달성할 수 없다.** 지터가 그보다 크기 때문에 어떤 구현으로도 만족시킬 수 없고, 만족시켰다고 주장하면 그것은 회선 차이를 실력 차이로 읽은 것이다.

다음으로 재정의한다(ADR-14).

| # | 재정의된 기준 |
|:-:|--------------|
| 1 | 시간 기반 판정은 **정수 밀리초로 기록한다**(원 요구의 이 부분은 유지한다) |
| 2 | **동시 판정의 단위는 게임 설정의 판정창이다** — 눈치게임은 방장이 고른 300밀리초 또는 500밀리초다. 같은 판정창에 도착한 입력은 **동시 입력으로 그룹핑**한다 |
| 3 | 서버는 **판정창보다 작은 도착 시각 차이를 순위 차로 쓰지 않는다** |
| 4 | 그룹 안의 순서가 규칙상 필요할 때만 도착 밀리초 → 수신 순번으로 결정론적으로 정렬한다 |
| 5 | **시간초 잡기의 오차 비교는 이 제한을 받지 않는다.** 경과 시간을 클라이언트 단조 시계가 재므로 지터가 값에 실리지 않는다. 1밀리초 단위 비교가 유의미하며 완전 동률은 재대결로 간다 |

**판정창을 새로 만들지 않았다.** 눈치게임의 방장 설정에 이미 0.3초·0.5초 판정창이 있고(docs_legacy/requirements.md §3.4), 재정의는 그 값을 동시성 판정의 단위로 승격한 것이다. 축을 둘로 만들지 않기 위해서다.

### 판정창 그룹핑

```
group_by_window(inputs, window_ms):
    # inputs는 arrived_ms 오름차순, 같은 값이면 seq 오름차순으로 정렬돼 있다
    groups = []
    for x in inputs:
        opened = opened_ms_of(last(groups))
        if groups and arrived_ms_of(x) - opened < window_ms:
            add_member(last(groups), x)       # 열려 있는 창 안 → 동시 입력
        else:
            groups += [ Group(opened_ms = arrived_ms_of(x), members = [x]) ]
    return groups
```

- 창은 **첫 입력이 도착한 시점에 열리고** 그때부터 window_ms 동안 유지된다. 뒤 입력이 도착할 때마다 창을 연장하지 않는다 — 연장하면 입력이 촘촘히 이어질 때 창이 무한히 길어진다.
- 그룹이 판정의 단위다. 눈치게임에서 **혼자인 그룹은 안전 확정**, **둘 이상인 그룹은 겹친 것**으로 본다.
- 창 길이를 방장이 고르므로 같은 방 안에서는 전원에게 같은 기준이 적용된다.

### 지터가 남기는 잔여 오차

| 항목 | 영향 | 처리 |
|------|------|------|
| 회선이 느린 참가자 | 도착이 늦어 다른 그룹으로 갈릴 수 있다 | 판정창이 300·500밀리초라 지터 50~100밀리초를 흡수한다. 그보다 큰 지연은 흡수하지 못하며 이를 수용한다 |
| 마감 직전 입력 | 지연으로 마감 이후 도착하면 버려진다 | 게임별 제한 시간에 여유를 둔다 |
| 결과 전환 시각 편차 | 브로드캐스트가 수신자마다 다른 시각에 도착한다 | 방 단위 1회 직렬화 · 확인 응답 없는 팬아웃으로 편차를 전송 시간 차로 제한한다 |
| 클라이언트 렌더 지연 | 기기 성능 차이로 화면 표시가 늦어진다 | 판정과 무관하다. 결과는 이미 확정돼 있다 |

## 시간초 잡기 예외의 검증

**클라이언트가 만든 값을 판정에 쓰는 자리는 여기 하나뿐이다.** 사람이 체감한 경과 시간을 재는 게임이라 서버 도착 시각으로는 게임이 성립하지 않는다 — 왕복 지연이 오차에 그대로 실려 회선이 빠른 사람이 이기게 된다.

### 측정과 검증

```
[클라이언트]
    시작 버튼 → start_mono = performance.now()   # 단조 시계. 시스템 시각 변경에 영향받지 않는다
    정지 버튼 → stop_mono  = performance.now()
    elapsed_client = round(stop_mono - start_mono)        # 정수 밀리초
    서버로 시작 이벤트와 정지 이벤트를 각각 보내고, 정지 이벤트에 elapsed_client를 싣는다

[서버]
    observed = arrived_ms(정지) - arrived_ms(시작)        # 서버가 관측한 간격
    MARGIN   = 300                                        # 밀리초

    ① 두 이벤트가 모두 도착했는가                → 아니면 미입력 처리
    ② 순서가 시작 → 정지인가                     → 아니면 거부
    ③ observed - MARGIN <= elapsed_client <= observed + MARGIN  → 아니면 거부
    ④ 0 < elapsed_client <= limit_ms             → 아니면 거부   (limit_ms = 목표 + 3초)
    거부된 입력은 무효로 처리하고 게임별 미입력 기본값으로 대체한다

    error = abs(elapsed_client - target_ms)               # 이 값으로 순위를 매긴다
```

### 허용 오차 ±300밀리초의 근거

**값의 정본은 [../05_game_rules/05_timer.md](../05_game_rules/05_timer.md)이며 본 절은 그 값을 아키텍처 관점에서 싣는다.** 두 문서가 어긋나면 게임 규칙이 우선한다.

- 클라이언트가 잰 경과 시간과 서버가 관측한 간격의 차이는 **시작 이벤트의 편도 지연과 정지 이벤트의 편도 지연 차이**다.
- 편도 지터를 50~100밀리초로 보면 두 이벤트에 걸쳐 최대 약 200밀리초가 벌어질 수 있다.
- 여기에 1.5배 여유를 둔 **300밀리초**를 허용 오차로 쓴다. 더 좁히면 회선이 불안정한 정상 참가자가 거부되고, 더 넓히면 조작 여지가 커진다.

### 이 예외가 남기는 위협

**허용 범위 안에서의 조작은 서버가 잡지 못한다.** 목표 5초·허용 300밀리초면 최대 6퍼센트를 속일 수 있고, 오차가 촘촘한 판에서는 순위를 바꿀 수 있는 크기다. 이는 예외를 두는 대가이며 다음으로 제한한다.

- 범위 밖 값은 **무효**이며 미입력 기본값으로 대체된다 — 큰 조작은 이득이 아니라 손해가 된다.
- 시작 이벤트를 보내지 않고 정지만 보내는 경로를 막는다(검증 ①·②).
- 동률은 재대결로 가므로 조작으로 만든 완전 일치는 승리를 확정하지 못한다.
- 위협 등재와 잔여 위험 서술은 [../11_fairness/01_server_authority.md](../11_fairness/01_server_authority.md)가 갖는다.

## 실시간성 목표의 측정

| 목표 | 측정 지점 | 측정 방법 |
|------|-----------|-----------|
| 실시간 반영 1초 이내 | 서버 브로드캐스트 발행 시각 → 클라이언트 수신 시각 | 이벤트에 발행 시각을 실어 보내고 수신 측에서 차이를 기록한다. 방 10명 기준 상위 95퍼센트 값으로 판정한다. **렌더 완료까지를 포함하지 않는다** — 기기 성능이 섞이면 무엇을 개선해야 하는지 알 수 없다 |
| 결과 동시성 0.5초 이내 | 같은 이벤트의 수신 시각 최댓값 − 최솟값 | 같은 방 참가자들의 수신 시각을 모아 편차를 계산한다 |
| 판정 기록 정수 밀리초 | 저장된 판정 시간 자료형 | 스키마 검사와 계약 테스트 |
| 동시 입력 그룹핑 | 판정창 안 입력이 같은 그룹인가 | 도착 시각을 주입한 판정 함수 단위 테스트 |

판정 결과는 [07_deployment_topology.md](./07_deployment_topology.md)의 비기능 목표 판정 표에 싣는다.
