# 06 인메모리↔DB 경계

> **대상**: 저장 경계의 정본 · 데이터별 소재 표 · 정합 유지 규칙 · 서버 재시작 시 고아 방 정리 절차 · 방 만료 스위퍼
> **작성일**: 2026-08-02
> **원천**: git 529e312 docs/db.md §10(실시간 상태·연결 종료) · §11~12(상태 머신·트랜잭션) · §20~21(연결·성능·보관 삭제) · git ecceb11 docs/03_architecture/01_data_model.md · docs_legacy/requirements.md §5 NFR-08·NFR-09 · §6 설계 결정 · frontend/src/lib/store.ts · [../README.md](../README.md)(전역 불변식 — 상태 경계)

ModuPick의 데이터는 **세 곳**에 나뉜다 — 서버 프로세스 메모리 · MySQL · 사용자 브라우저. 나누는 기준은 하나다. **밀리초 판정에 쓰는 것은 메모리에 두고, 방이 살아 있는 동안 여러 요청이 경합하며 남겨야 하는 것만 DB에 쓴다.** 브라우저에는 서버가 알 필요가 없는 것만 둔다.

이 경계가 이 서비스의 다른 제약을 거의 전부 만든다 — 단일 인스턴스·워커 1개(ADR-02) · 무중단 배포 포기(ADR-24) · 재기동 시 방 소멸(ADR-20)이 전부 여기서 나온다. 대신 얻는 것은 **판정 경로에 DB 왕복이 없다**는 사실이며, 그것이 게임 6종 중 절반의 성립 조건이다.

## 경계 원칙

| # | 원칙 |
|:-:|------|
| 1 | **밀리초 판정 경로에 DB 왕복을 넣지 않는다.** 입력 도착 시각·판정창 그룹핑·생존자 명단은 메모리에서만 다룬다 |
| 2 | **DB에 기록하는 입력은 집계용 표(votes)뿐이다.** 시간 판정 입력은 메모리에서 처리하고 확정 결과만 남긴다 |
| 3 | **영속 데이터의 정본은 MySQL이다.** 메모리의 사본은 읽기 가속용이며 쓰기는 항상 커밋을 거친다 |
| 4 | **인메모리 전용 데이터는 DB에 쓰지 않는다.** 재기동으로 사라지는 것이 정상 동작이다 |
| 5 | **재기동 후 상태 복구를 시도하지 않는다.** 살릴 수 없는 것이 있으므로 절반만 살리지 않는다 |
| 6 | **방이 사라지면 흔적을 남기지 않는다.** 참가자·라운드·선택지·투표·결과·시드가 함께 삭제된다 |

## 데이터별 소재

| 데이터 | 소재 | 수명 | 이유 |
|--------|------|------|------|
| 방 메타 — 제목 · 정원 · 초대 코드 · 방장 · 상태 · 상태 버전 · 마지막 활동 시각 | **MySQL**(정본) + 메모리 사본 | 방 삭제까지 | 초대 코드 유일성과 정원 초과를 DB 제약으로 막는다 |
| 참가자 — 닉네임 · 아바타 · 소개 태그 · 방장 여부 · 입장·퇴장 시각 | **MySQL**(정본) + 메모리 사본 | 방 삭제까지 | 같은 방 안 닉네임·아바타 중복을 제약으로 막는다 |
| 라운드 — 게임 종류 · 방장 설정 · 시드 · 시작 시각 · 종료 상태 | **MySQL** | 방 삭제까지 | 결과와 함께 남아야 사후 확인이 된다 |
| 선택지 — 킹메이커 안건 · 사다리 항목 | **MySQL** | 방 삭제까지 | 투표가 참조하는 대상이라 제약이 필요하다 |
| 안건 작성자 매핑 | **MySQL** | 방 삭제까지 | 자기 안건 투표 차단에 필요하다. **클라이언트에 내려보내지 않는다**(공개 설정과 개표 후는 예외) |
| 투표·지목 | **MySQL** | 방 삭제까지 | 중복 투표와 재전송을 UNIQUE로 막는다 |
| 확정 결과 — 승자 · 배정 · 개표 · 결과 본문 | **MySQL** | 방 삭제까지 | 방에 있는 동안 지난 판을 다시 볼 수 있어야 한다 |
| 소켓 연결 · 소켓↔참가자 바인딩 | **메모리 전용** | 소켓 종료까지 | 프로세스 자원이라 영속 대상이 아니다 |
| 연결 상태 3단계 · 유예 타이머 | **메모리 전용** | 이탈 확정까지 | 재기동하면 모든 연결이 끊기므로 남길 값이 없다 |
| 준비 상태 | **메모리 전용** | 방 삭제·대기방 복귀까지 | 재기동 후 복원해도 화면이 없는 사람의 준비 상태가 된다 |
| 라운드 단계 · 마감 시각 · 반복 회차 · 타이머 핸들 | **메모리 전용** | 라운드 종료까지 | 밀리초 경로다 |
| 입력 도착 시각 배열 · 수신 순번 | **메모리 전용** | 판정 확정까지 | 밀리초 경로다. 개별 입력 시각을 DB에 쓰지 않는다 |
| 판정창 그룹 · 생존자 명단 | **메모리 전용** | 라운드 종료까지 | 밀리초 경로다 |
| 명단 스냅샷 | **메모리 전용**(라운드 상태) | 라운드 종료까지 | 확정 결과에 참가자 식별자가 함께 저장돼 사후 확인이 된다 |
| 채팅 메시지 | **브라우저 로컬 저장소** | 브라우저에 남는 동안 | 서버에 대화 기록을 쌓지 않는다 |
| 규칙 가이드 다시 보지 않기 | **브라우저 로컬 저장소** | 브라우저에 남는 동안 | 서버가 알 필요 없는 개인 설정이다 |
| 타이머 틱 · 애니메이션 프레임 | **저장하지 않는다** | — | 서버 시각과 시드로 클라이언트가 계산한다 |

**메모리 사본을 두는 대상은 방 메타와 참가자 둘뿐이다.** 소켓 이벤트마다 명단을 DB에서 읽으면 브로드캐스트 경로에 질의가 붙는다. 사본은 커밋 직후에만 갱신하며 사본에서 시작하는 쓰기 경로를 만들지 않는다.

## 정합 유지 규칙

```
쓰기 순서 — 예외 없이 이 순서다
  1. 형식·길이 검증          (트랜잭션 밖)
  2. 트랜잭션 시작
       경합 행 잠금 (rooms → game_rounds → participants → votes 한 방향)
       상태·권한·정원 재검증   ← 잠금 이후에 다시 본다
       영속 쓰기
     커밋
  3. 메모리 사본 갱신
  4. 방 상태 버전 증가
  5. 브로드캐스트
```

| 규칙 | 내용 |
|------|------|
| 커밋 후 발행 | 브로드캐스트는 커밋 이후에만 한다. 롤백된 사실을 화면에 남기지 않는다 |
| 트랜잭션 안 금지 | 트랜잭션 안에서 소켓 전송·외부 호출·긴 계산을 하지 않는다 |
| 잠금 방향 고정 | 잠금 순서를 한 방향으로 고정해 교착을 구조적으로 줄인다 |
| 재검증 위치 | 상태·권한·정원은 **잠금 이후에 다시** 본다. 잠금 전 검사는 빠른 실패용이다 |
| 재시도 | 교착·잠금 대기 초과는 트랜잭션 전체를 최대 3회 짧은 무작위 지연과 함께 재시도한다 |
| 상태 버전 | 증가는 커밋 이후 한 곳에서만 한다. 메모리 값과 DB 컬럼이 갈라지지 않게 한다 |
| 세션 수명 | 소켓 하나가 DB 세션 하나를 계속 점유하지 않는다. 이벤트 처리마다 짧게 열고 즉시 반납한다 |
| 사본 신뢰 경계 | 메모리 사본은 표시·라우팅에만 쓴다. **정원·중복·멱등 판정은 DB 제약이 한다** |
| 삭제 | 참가자 행을 지우지 않고 퇴장 시각을 갱신한다. 물리 삭제는 방 삭제 시 하위 전파로만 일어난다 |

**메모리와 DB가 어긋날 수 있는 유일한 창은 커밋과 사본 갱신 사이다.** 단일 프로세스·단일 워커라 그 사이에 다른 요청이 끼어들 수 있지만, 판정에 쓰는 값은 전부 DB 제약이 최종 결정하므로 어긋난 사본이 만드는 것은 표시 지연뿐이다.

## 서버 재시작 시 고아 방 정리

### 문제

진행 중 상태가 프로세스 메모리에만 있으므로 재기동하면 사라진다. 그런데 **DB에는 대기·진행·결과 상태의 방이 그대로 남는다.** 그 방들은 어떤 소켓도 붙어 있지 않은 **고아**이며, 정리하지 않으면 세 가지 문제가 생긴다.

1. **초대 코드가 잠긴다.** 삭제되지 않은 방이 코드를 점유해 새 방이 같은 코드를 쓸 수 없다.
2. **참가자가 죽은 방에 입장한다.** 방 코드 검증은 DB를 보므로 통과하고, 핸드셰이크 후에는 아무도 없는 방에 혼자 있게 된다.
3. **10분 무활동 만료까지 남는다.** 스위퍼에 맡기면 최대 10분 동안 위 상태가 이어진다.

### 정리 절차

```
on_startup():
    1. DB 연결과 마이그레이션 리비전 일치를 확인한다
       불일치면 기동을 중단한다                       # 잘못된 스키마로 데이터를 지우지 않는다

    2. 정리 대상을 고른다
       대상 = rooms 전건
       # 단일 인스턴스이므로 기동 시점의 인메모리 방 수는 0이다.
       # 따라서 DB에 있는 모든 방이 고아다 — 선별 기준이 필요 없다.

    3. 배치(100건 단위)로 삭제한다
       for batch in chunks(대상, 100):
           for room_id in batch:
               트랜잭션:
                   SELECT ... FROM rooms WHERE id = room_id FOR UPDATE
                   UPDATE game_rounds SET 취소 WHERE room_id = room_id AND 진행 중
                   DELETE FROM rooms WHERE id = room_id      # 하위 데이터는 함께 삭제된다
               커밋
       # 실패한 건은 최대 3회 재시도하고, 그래도 실패하면 기록만 남긴다.
       # 남은 건은 만료 스위퍼가 다시 대상으로 잡으므로 기동을 막지 않는다.

    4. 정리 건수와 실패 건수를 로그로 남긴다

    5. 준비 상태를 올린다                              # 정리가 끝나기 전에는 트래픽을 받지 않는다
```

| 규칙 | 내용 | 근거 |
|------|------|------|
| 전량 삭제 | 대기·진행·결과를 가리지 않고 전부 지운다 | 상태와 무관하게 붙어 있는 소켓이 0이다 |
| 복구 시도 금지 | 스냅샷 복구를 하지 않는다 | 준비 상태·소켓 바인딩·판정창은 복원할 수 없다. 절반만 살리면 참가자가 절반뿐인 방이 된다 |
| 준비 상태를 나중에 | 정리 완료 후에만 트래픽을 받는다 | 정리 도중 만들어진 새 방이 삭제 대상에 섞이지 않게 한다 |
| 멱등 | 다시 실행해도 결과가 같다 | 이미 삭제된 방의 재요청은 성공으로 처리한다 |
| 기록 | 정리 건수를 지표로 남긴다 | 예기치 않은 재기동을 사후에 알 수 있는 유일한 흔적이다 |

**참가자에게는 알릴 방법이 없다.** 재기동 순간 모든 소켓이 끊기고 클라이언트는 연결이 끊겼다는 사실만 안다. 프론트는 재연결을 시도하지 않고 **표지 화면으로 돌아가 다시 입장해야 한다고 안내한다** — 재접속 경로가 없기 때문이다(ADR-09).

**정리 시간은 방 100개 기준 1초 미만으로 추정한다.** 방당 트랜잭션 1건이고 삭제는 기본 키 조회 후 하위 전파다. 실측 전에는 추정으로 적는다.

## 방 만료 스위퍼

| 항목 | 값 |
|------|-----|
| 주기 | **60초** |
| 대상 | 마지막 활동 이후 **10분**이 지난 방 |
| 조회 | 만료 시각 인덱스를 사용한다. 전건 스캔을 하지 않는다 |
| 처리 | 방 행 잠금 → 만료 조건 재확인 → 진행 중 라운드 취소 → 방 삭제 → 남은 소켓에 사유 통지 후 종료 |
| 실행 주체 | 애플리케이션 프로세스 안의 단일 스케줄러(ADR-21) |
| 중복 안전 | 중복 실행돼도 결과가 같도록 만든다 |
| 만료 지연 상한 | 주기와 같은 60초. 최대 10분 60초 후에 삭제된다 |

무활동으로 세는 사건과 세지 않는 사건의 정본은 [05_room_state_machine.md](./05_room_state_machine.md)다. **하트비트는 활동이 아니다** — 아무도 조작하지 않는 방이 소켓만 붙어 있다는 이유로 영원히 살아남지 않게 한다.

방장 이탈과 마지막 참가자 이탈은 스위퍼를 기다리지 않고 **요청 트랜잭션 안에서 즉시 삭제**한다.

| 규칙 | 내용 |
|------|------|
| 수집 범위 | 이메일·전화번호·계정을 수집하지 않는다. 닉네임·아바타·소개 태그만 방 수명 동안 보관한다 |
| 삭제 | 방이 사라지면 참가자·라운드·선택지·투표·결과·시드가 함께 삭제된다 |
| 채팅 | 서버에 저장하지 않는다. 각자 브라우저에 남으며 방을 나가면 그 방의 키를 지운다 |
| 복구 | 삭제된 방 데이터를 사용자에게 복구해 주는 기능을 두지 않는다 |
| 백업 | 운영 백업은 1일 1회와 파괴적 마이그레이션 직전에 받는다. 백업에는 방 수명 동안의 데이터가 포함되므로 보존 기간을 짧게 둔다 |
| 로그 | 초대 코드·소개 태그·DB 비밀값이 로그에 남지 않는지 표본 점검한다 |
| 익명성 | 익명 게임의 제출자·지목자 식별 정보는 공개 설정이 켜지고 개표가 끝난 뒤에만 응답에 들어간다 |
